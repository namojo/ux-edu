# CX/UX 팀 하네스 바이브코딩 교육 — "말로 팀을 만들어 내 업무를 시키는 사람 되기"

## 개요

| 항목 | 내용 |
|------|------|
| 대상 | 회사 CX/UX 팀원 — **코딩 경험 없음**, Claude Code·revfactory/harness 첫 사용 |
| 목표 | AI 도구 사용자가 아니라 **"하네스 구성해줘"로 에이전트 팀을 만들어 자기 반복 업무를 시키고, 결과로 팀을 진화시키는 팀 설계자**가 되는 것 |
| 형태 | 반나절 워크샵 × 3회 시리즈 (회당 약 4시간, 90분 모듈 2개 + 쉬는 시간·정리) |
| 중심 도구 | **revfactory/harness** — Claude Code 기초는 하네스로 진입하기 위한 최소 계단으로만 다룬다 |
| 라이프사이클(척추) | 교육 전체가 하네스 **설치 → 구성(바이브코딩) → 진화(하네스 회고)** 3단계를 따라 흐른다. L1=설치+첫 구성, L2=사례로 구성 반복(+매 팀에 진화 1회), L3=직접 구성+진화 집대성. **진화는 마지막 한 번의 이벤트가 아니라 L2 내내 반복하는 습관**으로 설계했다 |
| 산출물 원칙 | 모든 모듈은 **학습자가 가져가는 실물**로 끝난다. L1은 "내 손으로 만든 첫 팀", L2부터는 **자기 실무의 하네스 + 그 첫 실행 결과** |
| 핸즈온 비율 | 모듈당 실습 ≥ 50% (도입·시연 ≤30분 / 실습 ≥45분 / 공유·정리 15분) |

### 전제(가정) — 교육 형태 미지정에 따른 기본값

교육 기간·형태가 지정되지 않아 `ux-edu-program` 스킬의 **기본 3레벨 체계(반나절 × 3회 시리즈)** 로 설계했다. 실제 운영 시 아래 가정을 확정·조정해야 한다.

- **일정**: 주 1회 × 3주 연속 권장(회차 사이에 "자기 업무에 하네스를 적용"하는 숙제가 있어 간격이 필요). 하루 몰아서도 가능하나 L3 과제는 별도 시간이 필요하다.
- **인원**: 회당 8~12명, 강사 1 + 실습 보조(TA) 1. 비개발자 대상이라 플러그인 설치·권한 창·하네스 생성 대기에서 막히는 사람을 즉시 붙잡아 줘야 이탈이 없다.
- **환경 (선결 조건)**: 교육 전 각자 노트북에 **Claude Code 설치 완료**. 미설치자는 M1 도입에서 다 함께 설치. revfactory/harness 플러그인은 M1 실습 안에서 설치한다(설치 자체가 첫 실습).
- **데이터**: L2부터는 학습자가 **자기 프로젝트의 실제 데이터(익명화된 인터뷰·리뷰·VoC)** 를 지참해야 산출물이 실무로 이어진다. 사전 안내 필수.

### 실습 재료 연결

- **활용 사례집 10편** — 최종 위치 `usecases/{slug}.md`. 각 사례는 **하네스 중심 구조**(0단계 설치 → 2단계 "하네스 구성해줘" 팀 구성 프롬프트 → 3단계 실행 → 4단계 진화). **사례의 2단계 팀 구성 프롬프트가 곧 실습 스크립트**다.
- **완성 MVP 예시** — `mvp/onboarding-smoke/` (카페 온보딩, 더블클릭 실행). MVP 팀이 만들어내는 결과물의 실물 견본.
- **도구 레퍼런스** — 설치 명령·트리거 문구는 `.claude/skills/ux-ai-usecase/references/revfactory-harness-guide.md`를 글자 단위로 인용한다(학습자가 복붙한다).
- **harness-100** — 미리 만들어진 100개 팀 하네스. "처음부터 만들지 말고 가까운 것을 설치해 고쳐 쓰는 출발점"으로 M2·L3에서 소개.

> **사례집 재생산 중 대비**: 사례집이 아직 하네스 중심 구조로 완성되기 전이면, 각 L2 모듈 실습은 사례의 2단계 프롬프트 대신 강사가 배포하는 임시 구성 프롬프트로 진행 가능하다. 사례 완성 후 각 모듈 명세의 "사용 사례" 경로로 교체한다.

**라이프사이클 매핑(설치·구성·진화)**:
- **설치** — `first-contact`(플러그인 설치) → `first-harness`(첫 구성 + **"프롬프트 한 번이냐, 팀이냐" 판단** = 하네스가 과한 경우 감별).
- **구성(바이브코딩)** — `voc-team`·`research-persona-team`·`mvp-team`에서 사례를 대본으로 "하네스 구성해줘"를 반복 → `design-my-harness`에서 사례 없이 스스로 설계.
- **진화(하네스 회고)** — L2 세 모듈 각각의 끝에 `하네스 회고` 1회를 심어 **진화를 매번 연습**하고, `design-my-harness`에서 자기 팀을 실제로 진화시켜 집대성한다.

## 모듈별 명세

### `first-contact`: Claude Code 열고 하네스 설치까지

- **레벨 / 시간**: L1 / 90분 (도입·시연 30분 — 실습 45분 — 공유·정리 15분)
- **선수 조건**: 없음. 단, Claude Code 설치가 되어 있어야 함(미설치자는 도입 30분에 다 함께 설치).
- **학습 목표**: 터미널을 열어 작업 폴더로 이동해 `claude`를 켜고, 폴더 안 파일을 읽혀 첫 결과를 받는 전 과정을 혼자 해낸다. 그리고 revfactory/harness 플러그인을 설치해 **다음 모듈에서 팀을 만들 준비를 끝낸다**. 이 모듈은 "AI 도구 다루기"가 목적이 아니라 **하네스로 가는 최소 진입 계단**이다 — 기초에 오래 머물지 않는다.
- **시간 배분**: 도입·시연 30분(터미널 열기·경로 이동 미러링) — 실습 45분(파일 읽히기 + 플러그인 설치) — 공유·정리 15분
- **실습 설계**:
  1. (다 함께) 작업 폴더 만들기 → Finder 우클릭 "폴더에서 새 터미널 열기" 또는 `cd`로 이동 → `claude` 실행. 강사 화면 미러링.
  2. 강사 배포 샘플(짧은 리뷰 20건)을 폴더에 넣고 `이 파일 읽고 무슨 내용인지 3줄로 요약해줘` 입력. 권한 확인 창 대응을 함께 체험(첫 막힘 지점).
  3. `방금 요약을 표로 다시 보여줘`로 "대화가 이어진다"를 체감(후속 프롬프트 감각).
  4. **하네스 설치**: `revfactory-harness-guide.md`의 설치 명령을 그대로 복붙 실행 — `/plugin marketplace add revfactory/harness` → `/plugin install harness@harness-marketplace`. 설치가 되었는지 확인하는 법 안내.
- **사용할 사례 / 입력 데이터**: 특정 사례에 종속되지 않는 워밍업. 입력은 강사 배포 공용 샘플(리뷰 20건). 학습자 자기 데이터는 아직 요구하지 않음(첫 성공 경험에 집중).
- **구성할 하네스**: 없음 — 이 모듈은 하네스를 **설치**까지만 한다(구성은 다음 모듈).
- **제작할 자료**: 실습가이드(화면 단위 절차 + 권한 창·경로 함정 박스 + 플러그인 설치 확인 함정 박스), 슬라이드개요(강사 시연용), 핸드아웃(터미널 열기·`cd`·권한 창·설치 명령 치트시트 1장)
- **성공 기준**: 모든 학습자가 자기 노트북에서 `claude`를 켜 파일을 읽혀 요약을 1회 받고, revfactory/harness 플러그인 설치를 완료한다(설치 확인 메시지까지 도달).

### `first-harness`: "하네스 구성해줘" — 내 손으로 만든 첫 팀

- **레벨 / 시간**: L1 / 90분 (도입·시연 25분 — 실습 50분 — 공유·정리 15분)
- **선수 조건**: `first-contact` 수료(Claude Code 실행·파일 읽히기 + 하네스 플러그인 설치 완료).
- **학습 목표**: 자연어 한 문장으로 **첫 하네스를 구성**하고 실행해, "코드를 쓰는 게 아니라 팀을 말로 설계하고 팀이 일한다"를 첫날 몸으로 겪는다. 하네스가 만든 팀에 **검증 담당 에이전트**가 들어 있음을 관찰해, 이후 모든 실습에 흐르는 검증 습관의 뿌리를 놓는다. 이 "내가 팀을 만들었다" 경험이 프로그램 전체의 후크다. 동시에 **"프롬프트 한 번이면 될 일과 팀으로 만들 일"을 가려내는 판단**(하네스가 과한 경우 감별)을 첫날에 심어, 무엇이든 팀부터 만들려는 오남용을 예방한다.
- **시간 배분**: 도입·시연 25분(A/B 근거 데이터 + `.claude/agents/`·`.claude/skills/` 생성 구조 미리보기) — 실습 50분(첫 구성·실행·팀 구조 관찰) — 공유·정리 15분
- **실습 설계**:
  1. (도입) 하네스가 왜 좋은가 — 근거 데이터 인용(품질 49.5→79.3, 분산 −32%, "저자 측정·소표본" 단서 함께). `revfactory-harness-guide.md`의 "하네스가 생성하는 것" 폴더 구조를 강사 화면으로 미리보기.
  2. 강사 배포 공용 데이터(리뷰 모음)로, `revfactory-harness-guide.md`의 "좋은 구성 프롬프트" 형태를 복붙해 `하네스 구성해줘: ... 팀` 실행. 생성 대기(수 분)가 정상임을 함께 체험.
  3. 생성이 끝나면 `.claude/agents/` 폴더를 열어 만들어진 팀원 파일(예: 수집·분석·**검증**·리포트)을 눈으로 확인 — "이 팀에는 검증 담당이 있다"를 짚는다(Producer-Reviewer 패턴 첫 소개).
  4. 오케스트레이터 트리거 문구로 팀을 **실행**해 첫 결과물을 받는다. 새 세션에서 트리거로 다시 돌려 "구축 1회, 실행 반복" 구조를 체감.
  5. **"프롬프트 한 번이냐, 팀이냐" 판단**: 같은 데이터에 프롬프트 한 방(`이 리뷰에서 불만 주제 5개만 뽑아줘`)을 던져 보고, 방금 만든 팀의 결과와 비교한다. "이번 한 번"이면 프롬프트가 빠르고, "매번 같은 형식으로 반복 + 검증 필요"면 팀이 이긴다 — `usecases/voc-mining.md`의 "하네스가 과한 경우" 절을 판단 기준 교재로 사용. 이어서 **harness-100**(처음부터 만들지 않고 가까운 팀을 설치해 고쳐 쓰는 출발점)을 짧게 소개.
- **사용할 사례 / 입력 데이터**: 특정 사례 전편을 재현하기보다, 사례집의 **2단계 팀 구성 프롬프트 형태**를 축약한 공용 예제로 첫 구성을 경험한다(가장 단순한 VoC 요약 팀 권장). "프롬프트냐 팀이냐" 판단은 `usecases/voc-mining.md`의 "하네스가 과한 경우" 절 활용. 입력은 강사 배포 공용 데이터.
- **구성할 하네스**: **첫 하네스** — 공용 데이터를 다루는 단순 분석 팀(수집·분석·검증·리포트 수준). 학습자가 처음으로 "내 손으로 만든 팀"을 갖는다.
- **제작할 자료**: 실습가이드(구성 프롬프트 복붙 → 생성 대기 → 팀 폴더 확인 → 실행 절차 + "생성 결과가 세션마다 조금씩 달라도 정상" 함정 박스 + "생성 대기 시간" 함정 박스), 핸드아웃(설치·트리거 문구 치트시트 + 팀 아키텍처 6패턴 한 줄 요약 + **"프롬프트냐 팀이냐" 판단 기준** — 반복성·형식 고정·검증 필요 3항목), 슬라이드개요(근거 데이터·하네스 개념·생성 구조·프롬프트 vs 팀 판단 강사용)
- **성공 기준**: 모든 학습자가 `하네스 구성해줘`로 팀을 1개 생성하고, `.claude/agents/`에서 검증 담당을 포함한 팀원 구성을 확인하며, 오케스트레이터 트리거로 실행해 첫 결과물을 받아 화면에 띄운다.

### `voc-team`: VoC 분석 팀을 만들어 내 리뷰 돌리기

- **레벨 / 시간**: L2 / 90분 (도입·시연 25분 — 실습 50분 — 공유·정리 15분)
- **선수 조건**: L1 2개 모듈 수료. **자기 서비스의 실제 리뷰/CS 티켓(익명화)** 지참 — 미지참자는 강사 배포 대체 데이터 사용(단, 산출물이 실무로 안 이어지므로 지참을 강력 권장).
- **학습 목표**: 자기 VoC를 다루는 **분석 팀을 직접 구성·실행**해, 주제별 분류·대표 원문·건수가 담긴 개선 기회 리포트를 자기 업무에 가져갈 초안으로 만든다. 팀의 **검증(인용 검증) 담당**이 내놓은 결과를 사람이 원문 대조로 최종 확인하는 흐름을 몸에 익힌다.
- **시간 배분**: 도입·시연 25분(voc-mining 사례의 팀 미리보기·2단계 프롬프트 해설) — 실습 50분(자기 데이터로 구성·실행·검증) — 공유·정리 15분
- **실습 설계**:
  1. 지참한 리뷰/티켓을 `reviews.txt`로 폴더에 정리(엑셀 열 복사 붙여넣기 포함, 별점 열 포함 여부 확인).
  2. `usecases/voc-mining.md`의 **2단계 팀 구성 프롬프트**에서 `{중괄호}`만 자기 서비스로 바꿔 `하네스 구성해줘` 실행 → VoC 분석 팀 생성.
  3. 팀을 실행해 주제별 개선 기회 표를 받고, 후속 프롬프트로 관심 주제 1개를 세부 유형으로 더 판다.
  4. **검증**: 팀의 인용 검증 담당이 표시한 대표 인용 1건 이상을 학습자가 실제 원문에서 `Cmd/Ctrl+F`로 대조(환각 점검) + 개인정보 잔존 확인. 결과를 `improvement.md`로 저장.
  5. (진화 맛보기) `usecases/voc-mining.md` 4단계 예시로 `하네스 회고: ...` 피드백을 한 번 넣어 리포트 형식이 바뀌는 것을 관찰.
- **사용할 사례 / 입력 데이터**: 주교재 `usecases/voc-mining.md`(하네스 중심 구조). 입력은 학습자 자기 VoC(익명화).
- **구성할 하네스**: **VoC 분석 팀** — 수집→주제 분류→인용 검증→분기 비교 리포트 (Pipeline + Producer-Reviewer). 검증 담당 필수.
- **제작할 자료**: 실습가이드(사례의 팀 구성 프롬프트를 자기 데이터에 적용하는 절차 + 별점 없는 경우 분기 안내 + 검증 대조 절차), 워크시트("내 VoC 준비 체크리스트" — 데이터 출처·기간·익명화·별점 유무 기입란)
- **성공 기준**: 학습자가 자기 VoC로 분석 팀을 구성·실행해 주제별 개선 기회 표(대표 인용·건수 포함)를 파일로 저장하고, 인용 1건을 원본 대조로 검증한다.

### `research-persona-team`: 리서치 종합 팀 → 페르소나 팀 잇기

- **레벨 / 시간**: L2 / 90분 (도입·시연 30분 — 실습 45분 — 공유·정리 15분)
- **선수 조건**: L1 2개 모듈 수료 + `voc-team` 권장(자기 데이터로 팀 돌리기에 익숙해진 상태). **자기 인터뷰 요약·설문 응답(익명화)** 지참.
- **학습 목표**: 두 하네스를 연결하는 워크플로우를 경험한다 — 리서치 종합 팀의 출력이 페르소나 팀의 입력이 되어, 자기 인터뷰에서 어피니티 종합 → 페르소나 2종 + 저니맵 초안까지 잇는다. "하나의 팀 출력이 다음 팀 입력이 된다"는 파이프라인 사고를 익힌다(L2 도달 기준 = 사례 2개 이상 재현).
- **시간 배분**: 도입·시연 30분(두 사례의 팀 미리보기 + 연결 지점 해설) — 실습 45분(두 팀 구성·연결 실행) — 공유·정리 15분
- **실습 설계**:
  1. 인터뷰를 참가자별 파일(`P1.txt`…) 또는 한 파일(`research.txt`)로 정리(익명화 표기).
  2. `usecases/research-synthesis.md`의 팀 구성 프롬프트로 **리서치 종합 팀**을 구성·실행 → 어피니티 그룹 + 핵심 인사이트를 `synthesis.md`로 저장.
  3. `usecases/persona-journey.md`의 팀 구성 프롬프트로 **페르소나 팀**을 구성하고, `synthesis.md`를 입력으로 실행 → 페르소나 2종 + 저니맵 생성("한 팀의 출력이 다음 팀의 입력" 체감).
  4. **검증**: 페르소나 각 칸의 `(P3)` 근거 번호를 페르소나 팀의 검증 담당 표시와 함께 원문에서 대조해 스테레오타입 누출(근거 없는 상상)을 잡는다.
  5. **(진화 습관)** `하네스 회고: 페르소나 각 항목에 근거 참가자 번호를 반드시 붙이고, 근거 없는 칸은 [추정]으로 표시하도록 검증 담당을 개선해줘` 식 피드백을 1회 넣어 팀이 수정되는 것을 관찰한다(L2 내내 반복하는 진화 연습).
- **사용할 사례 / 입력 데이터**: 주교재 2편 `usecases/research-synthesis.md` → `usecases/persona-journey.md`(연결). 입력은 학습자 자기 인터뷰/설문(익명화).
- **구성할 하네스**: **리서치 종합 팀**(수집→어피니티 그룹핑→인사이트 추출→검증) + **페르소나 팀**(종합본 입력→페르소나 생성→근거 검증→저니맵). 두 하네스를 순차 연결(Pipeline).
- **제작할 자료**: 실습가이드(두 팀 구성 + synthesis 출력을 persona 입력으로 넘기는 연결 절차 + 근거 대조 절차 + 하네스 회고 1회 절차), 워크시트("페르소나 근거 대조 시트" — 페르소나 항목별 근거 번호·원문 확인 여부 기입란)
- **성공 기준**: 학습자가 자기 데이터로 종합 팀·페르소나 팀을 각각 구성·실행해 종합본 + 페르소나 2종 + 저니맵을 만들고, 페르소나 1개 이상의 근거 번호를 원문 대조로 검증한다.

### `mvp-team`: MVP 팀으로 클릭되는 시제품 만들기

- **레벨 / 시간**: L2 / 90분 (도입·시연 30분 — 실습 45분 — 공유·정리 15분)
- **선수 조건**: L1 2개 모듈 수료. 검증하고 싶은 **자기 서비스의 화면 흐름 아이디어**(예: 온보딩, 특정 기능 플로우)를 머릿속/메모로 준비.
- **학습 목표**: 백엔드·개발 없이, 사용성 테스트에 바로 쓸 수 있는 클릭 가능한 HTML MVP를 만들어내는 팀을 구성·실행하고, 자연어 수정 요청으로 다듬는 법을 익힌다. MVP는 완성품이 아니라 테스트 도구임을 명확히 한다.
- **시간 배분**: 도입·시연 30분(완성 예시 체험 + mvp-prototype 사례의 팀 미리보기) — 실습 45분(자기 아이디어로 팀 구성·생성·수정) — 공유·정리 15분
- **실습 설계**:
  1. 완성 예시 `mvp/onboarding-smoke/index.html`을 더블클릭해 "결과물이 이런 것"을 먼저 체험(환영→취향→홈→주문→완료 클릭 완주).
  2. `usecases/mvp-prototype.md`의 팀 구성 프롬프트로 자기 아이디어의 화면 흐름을 3~4단계로 서술해 **MVP 프로토타입 팀**을 구성·실행 → HTML MVP 생성.
  3. 브라우저에서 열어 클릭해 보고, "이 화면에 예상 픽업 시간 추가해줘" 식 자연어 수정 요청으로 다듬기.
  4. "검증할 수 있는 것 / 없는 것"을 스스로 적어 사용성 테스트 범위를 정의.
  5. **(진화 습관 — 수정 vs 진화 구분)** 일회성 화면 수정(3번)은 자연어 요청으로 끝내되, 매번 반복될 요구는 `하네스 회고: 주문 완료 화면에 예상 픽업 시간을 기본 포함하도록 MVP 팀을 개선해줘`처럼 팀 자체를 진화시킨다. "이번만 고칠 일 vs 팀에 심을 일"을 가른다.
- **사용할 사례 / 입력 데이터**: 주교재 `usecases/mvp-prototype.md` + 완성 예시 `mvp/onboarding-smoke/`. 입력은 학습자 자기 서비스 아이디어(데이터 불필요 — 사례 없이도 진행 가능한 유일한 L2 모듈).
- **구성할 하네스**: **MVP 프로토타입 팀** — 화면 흐름 설계→HTML 생성→클릭 가능성·접근성 점검(검증) (Producer-Reviewer). 입력은 자연어 화면 서술.
- **제작할 자료**: 실습가이드(예시 체험 → 팀 구성·생성 → 수정 절차 + 수정 vs 진화(하네스 회고) 구분 절차), 핸드아웃("MVP 수정 요청 문구 모음" — 화면 추가·요소 변경 자연어 예시 치트시트)
- **성공 기준**: 학습자가 자기 아이디어의 화면 3개 이상을 클릭으로 오가는 HTML MVP를 팀으로 만들어 브라우저에서 완주하고, 수정 요청 1건을 반영한다.

### `design-my-harness`: 내 반복 업무를 팀 구조로 직접 설계·진화

- **레벨 / 시간**: L3 / 90분 + 과제(1~2주 뒤 산출물 리뷰)
- **선수 조건**: L2 모듈 최소 2개 수료(사례 하네스를 자기 데이터로 2회 이상 구성·실행해 본 상태). "매번 같은 방식으로 반복하는 내 업무" 1개를 지목할 수 있어야 함.
- **학습 목표**: 사례를 따라 구성하던 단계를 넘어, **자기 반복 업무를 스스로 역할 분해·검증 단계로 설계**해 `하네스 구성해줘`로 만들고, 실행 결과가 아쉬우면 `하네스 회고`로 팀을 **진화**시킨다. "한 프롬프트로 다 끝내기"에서 "역할 분해 + 검증 담당 + 키워 가는 자산"으로 사고를 전환한다.
- **시간 배분**: 도입·시연 30분(기존 하네스 구조 관찰 + 역할 분해·진화 개념) — 실습 45분(캔버스 작성 + 자기 하네스 구성·실행) — 공유·정리 15분
- **실습 설계**:
  1. (도입) 이 프로젝트의 `.claude/agents/`·`.claude/skills/` 구성 또는 앞선 모듈에서 만든 팀을 실물로 열어 "역할 나뉜 AI 팀 + 오케스트레이터"가 어떻게 생겼는지 관찰. harness-100의 이웃 하네스를 설치해 고쳐 쓰는 대안도 소개.
  2. 자기 반복 업무를 **역할 3~5개로 쪼개는 캔버스**를 채운다(예: 수집→분류→검증→리포트). 그중 **검증 담당**(근거 대조·개인정보 점검)을 반드시 포함 — 사람이 지겨워하지만 꼭 해야 하는 일을 팀에 태우는 것이 하네스의 핵심 이점.
  3. 캔버스를 그대로 `하네스 구성해줘: ...` 프롬프트로 옮겨 자기 하네스를 실제로 구성하고, 자기 데이터로 1회 실행.
  4. 실행 결과의 아쉬운 점을 `하네스 회고: ...`로 피드백해 팀이 수정되는 것을 관찰(진화 체험).
  5. (과제) 다음 실무 라운드에 이 하네스를 실제로 한 번 돌려 보고, 결과와 진화 이력을 1~2주 뒤 산출물 리뷰로 공유.
- **사용할 사례 / 입력 데이터**: 모든 사례의 "한 걸음 더"(팀 확장·진화) 섹션 + 이 프로젝트 하네스 구성(교보재) + harness-100. 입력은 학습자 자기 반복 업무 명세와 데이터.
- **구성할 하네스**: **학습자가 직접 설계한 하네스** — 자기 반복 업무를 역할 3~5개(검증 담당 포함)로 분해한 팀. 사례를 베끼지 않고 스스로 도메인·역할·검증을 정의한다.
- **제작할 자료**: 실습가이드(하네스 구조 관찰 → 역할 분해 → 구성·실행 → 진화 절차 + "생성 결과 편차 정상" 함정 박스), 워크시트("반복 업무 → 역할 분해 캔버스" — 업무명·반복 주기·역할별 담당·검증 단계·구성 프롬프트 초안 기입란), 슬라이드개요(하네스 개념·6패턴·진화·이 프로젝트 실물 예시 강사용)
- **성공 기준**: 학습자가 자기 반복 업무를 역할 3~5개(검증 담당 포함)로 분해한 캔버스를 완성하고, 그것으로 하네스를 실제 구성·1회 실행하며, `하네스 회고` 피드백을 1회 반영한다. 과제: 다음 라운드 실행 후 결과·진화 이력을 리뷰 제출.

## 효과 측정

- 평가는 시험이 아니라 **산출물 리뷰** — L1은 "구성한 첫 팀 + 첫 실행 결과", L2 이후는 "**자기 업무의 하네스 구성물 + 실행 결과**"가 평가 대상.
- 프로그램 종료 설문 3문항: ① 이번 주 실무에 하네스를 쓸 것인가(의향) ② 가장 유용한 사례는(선호) ③ 막힌 지점은(개선 입력). ③은 하네스 진화(evolve)의 입력이 된다.
