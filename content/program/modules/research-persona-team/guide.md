# 실습 가이드 — 리서치 종합 팀 → 페르소나 팀 잇기

> L2 · 90분 모듈 (도입·시연 30분 — **이 가이드는 실습 45분 구간** — 공유·정리 15분)
> 선수 조건: L1 2개 모듈 수료 + `voc-team` 권장. **자기 인터뷰 요약·설문 응답(익명화)** 지참.
> ⏱ 두 번(2·4단계)의 팀 생성 대기 시간 때문에 45분에 살짝 못 미쳐도 정상입니다. 7단계(회고)는 정리 시간에 이어서 해도 괜찮습니다.

## 오늘 만드는 것

오늘은 하네스(AI 에이전트 팀) **두 개**를 만들어 이어 붙입니다.

```
[내 인터뷰 자료] → 리서치 종합 팀 → synthesis.md → 페르소나 팀 → 페르소나 2종 + 저니맵
```

**"한 팀의 결과물이 다음 팀의 재료가 된다"** — 이것이 오늘의 핵심 감각입니다. 팀을 하나만 쓰는 게 아니라, 팀 여러 개를 이어서 파이프라인(작업이 순서대로 넘어가며 처리되는 흐름)으로 쓰는 법을 익힙니다.

| 순서 | 만드는 것 | 결과 파일 |
|------|-----------|-----------|
| ① | 리서치 종합 팀 (하네스 #1) | `synthesis.md` |
| ② | 페르소나 팀 (하네스 #2) | `persona-journey.md` (페르소나 2종 + 저니맵) |

오늘 실습이 끝나면 이 두 파일과, 근거 대조를 마친 워크시트 1장을 가지고 갑니다.

---

## 시작 전 확인

- [ ] 이전 모듈에서 revfactory/harness 플러그인을 설치했다 (확인용: Claude Code 대화창에 `/plugin`을 입력했을 때 harness가 목록에 보이면 OK)
- [ ] 내 인터뷰 요약·설문 응답(익명화된 것)을 노트북에 가지고 왔다
- [ ] 미지참 시: 강사가 배포하는 대체 인터뷰 샘플을 사용합니다. 이 경우 오늘 만든 팀은 그대로 두고, 다음에 내 데이터로 다시 돌리면 됩니다(구축은 1회, 실행은 반복이므로 어렵지 않습니다).

---

## 1단계: 인터뷰 자료 정리 (5분)

1. 작업 폴더를 하나 만듭니다. 예: 바탕화면에 `2026_리서치_페르소나` 폴더.
2. 그 안에 `input`이라는 폴더를 하나 더 만듭니다.
3. 인터뷰 요약·설문 응답을 `input` 폴더 안에 텍스트 파일로 넣습니다. 둘 중 편한 방식으로:
   - **참가자별로 나누기**: `P1.txt`, `P2.txt`, `P3.txt` … 파일마다 한 참가자.
   - **한 파일로 모으기**: `research.txt` 하나에 전부 넣되, 참가자 구분을 `[P1]`, `[P2]`처럼 표시.
   - 워드·PDF라면 "다른 이름으로 저장 → 텍스트(.txt)"로 바꿔서 넣습니다.
4. **익명화 확인**: 실명·연락처·회사명이 파일 안에 남아있지 않은지 눈으로 한 번 훑습니다. `[P1]` 같은 익명 표기만 남기고 실명은 직접 지웁니다 — 팀에게 맡기지 말고 이 단계에서 사람이 직접 지우는 것이 가장 안전합니다.
5. 이 폴더 안에서 Claude Code를 켭니다: 터미널을 열고 `cd `를 입력한 뒤 폴더를 터미널 창에 끌어다 놓고 Enter → `claude` 입력 후 Enter.

> 💡 **이렇게 나오면 정상입니다**: Claude Code를 처음 켤 때 "이 폴더에 대한 접근을 허용하시겠습니까?" 같은 권한 확인 창이 뜰 수 있습니다. 내가 방금 만든 내 작업 폴더가 맞다면 허용(Allow/Yes)하면 됩니다.

---

## 2단계: 리서치 종합 팀 구성 (10분)

`usecases/research-synthesis.md` 사례의 팀 구성 프롬프트입니다. `{중괄호}` 부분만 내 상황으로 바꿔 통째로 복사해 붙여넣으세요.

```
하네스 구성해줘: 사용자 인터뷰 녹취록을 종합하는 리서치 분석 팀이 필요해.
input 폴더의 녹취 텍스트 파일들을 입력하면,
(1) 발언을 화자·시점 단위로 정리하고, 각 인용과 인사이트에는 그 발언을 한 참가자 번호(P1, P2…)를 반드시 붙여서 저장하고
(2) 어피니티 그룹핑으로 주제별 테마를 묶고
(3) 리포트에 넣을 인용문이 원본 녹취록에 실제로 있는지 대조 검증하고
(4) 테마별 인사이트 + 검증된 인용 + 근거 개수가 담긴 인사이트 리포트를 마크다운으로 저장
해주는 팀으로. 우리 제품은 {내 서비스}이고, 이번 인터뷰 주제는 {인터뷰 주제}야.
검증에서 원본 녹취록에 실제로 있는 인용은 ✅검증됨으로, 원본에 없는 인용은 ⚠️[출처 불명]으로 각각 표시하도록 해줘.
결과 파일 이름은 synthesis.md로 저장해줘.
```

> 마지막 줄(`결과 파일 이름은 synthesis.md로 저장해줘`)은 다음 단계에서 페르소나 팀에게 그대로 넘길 수 있도록 파일명을 미리 맞춰두는 부분입니다. 사례 원문에는 없던 한 줄을 오늘 실습을 위해 덧붙인 것입니다.

Enter를 누르면 하네스가 팀을 만들기 시작합니다.

> 💡 **이렇게 나오면 정상입니다**: 화면에 아무 변화 없이 수십 초~수 분간 멈춘 것처럼 보일 수 있습니다. 하네스가 팀원 파일(`.claude/agents/`)과 작업 방법 파일(`.claude/skills/`)을 만드는 중입니다. 중간에 창을 닫지 말고 기다리세요.

구성이 끝나면 하네스가 **"이런 팀을 만들었습니다"** 요약과 팀원 표, 그리고 **실행할 때 쓸 문구**를 알려줍니다. 팀원이 collector(수집), clusterer(그룹핑), quote-verifier(**검증**), reporter(리포트) 네 명으로 보이면 정상입니다. 그 실행 문구를 3단계에서 씁니다.

---

## 3단계: 리서치 종합 팀 실행 (7분)

하네스가 알려준 실행 문구를 대화창에 붙여넣습니다. 잘 안 보이면 아래 문구를 그대로 써도 됩니다:

```
인터뷰 종합 실행해줘. input 폴더의 녹취록으로 인사이트 리포트를 만들어서 synthesis.md로 저장해줘.
```

팀이 순서대로 일해 테마별 인사이트 + 검증된 인용이 담긴 리포트를 만듭니다. 결과 예시:

```markdown
## 테마 1. 결제 마지막 단계의 '숨은 비용' 충격 (근거 발언 18개 / 참여자 7명)
- "배송비가 마지막에 붙어서 배신감 들었어요" — P1 ✅검증됨
```

> 💡 **이렇게 나오면 정상입니다**: `⚠️[출처 불명]` 표시가 몇 건 섞여 나올 수 있습니다. 검증 담당이 원문에서 못 찾은 인용을 걸러낸 흔적이니 정상입니다 — 나중에 원할 때 원문을 다시 확인하면 됩니다.

> ⚠️ **이럴 땐 이렇게**: 작업 폴더에 `synthesis.md`가 안 보이면, 다른 이름(예: `insight-report.md`)으로 저장됐을 수 있습니다. 대화창에 `방금 만든 리포트 파일 이름을 synthesis.md로 바꿔줘`라고 한 번 더 요청하세요. 이후 단계는 모두 이 파일 이름을 기준으로 진행됩니다.

`synthesis.md` 파일을 열어 테마·인사이트·인용이 잘 담겼는지 훑어봅니다. 여기까지가 **하네스 #1**입니다.

---

## 4단계: 페르소나 팀 구성 (10분)

`usecases/persona-journey.md` 사례의 팀 구성 프롬프트를 **오늘의 연결 구조에 맞게 조정**한 버전입니다. 원본 사례는 원본 인터뷰 파일(`research.txt`)을 직접 입력받지만, 오늘은 **synthesis.md — 방금 하네스 #1이 만든 결과물** — 을 입력으로 씁니다. 그래서 원본에 있던 "리서치 정리 담당"(원본을 정리·익명화하는 역할)은 뺐습니다 — 그 일은 이미 종합 팀과 1단계에서 끝났기 때문입니다.

`{중괄호}` 부분만 내 서비스로 바꿔 복사해 붙여넣으세요:

```
하네스 구성해줘: 사용자 리서치 데이터에서 페르소나와 저니맵 초안을 만드는 페르소나 팀이 필요해.
리서치 종합 팀이 만든 인사이트 리포트 파일(synthesis.md)을 입력하면 아래 순서로 일하는 팀으로 짜줘.

① 페르소나 작성 담당: synthesis.md의 테마별 인사이트와 인용을 바탕으로, 행동·니즈가 뚜렷이 갈리는 무리를 찾아 페르소나 2종을 만든다. 유형을 미리 정하지 말고 실제 내용에서 자연스럽게 묶는다. 각 페르소나의 모든 항목(별칭·대표 인용문·기본 정보·목표·페인포인트)에 근거 참가자 번호(P3처럼)를 반드시 붙인다.
② 근거 검증 담당: 작성 담당이 붙인 근거 번호가 synthesis.md 원문에 실제로 있는지 한 칸씩 대조한다. 근거가 없는 칸은 '데이터 없음' 또는 [추정]으로 강제 표시하고, synthesis.md에 없는 특성을 상식으로 채운 페르소나는 작성 담당에게 반려해 다시 만들게 한다.
③ 저니맵 작성 담당: 검증을 통과한 첫 번째 페르소나 기준으로 이 서비스 사용 과정을 4~6단계로 나눈다. 단계별 표(단계|사용자 행동|감정(한 단어+1~5점)|페인포인트|기회)로 만들고, 감정 점수와 페인포인트에도 근거 참가자 번호를 붙인다.

근거 없는 페르소나는 반드시 걸러지는 생성-검증(Producer-Reviewer) 구조로 짜줘.
synthesis.md에 없는 정보는 절대 지어내지 않는 것이 이 팀의 최우선 규칙이야.
검증 담당이 반려·수정하거나 [추정]/'데이터 없음'으로 표시한 내역을,
리포트 끝에 「검증 로그」 섹션으로 반드시 함께 남겨줘 — 사람이 무엇이 걸러졌는지 확인할 흔적이야.
우리 서비스는 {내 서비스}야.
결과는 마크다운 리포트 파일(persona-journey.md)로 저장해줘.
```

> 💡 **이렇게 나오면 정상입니다**: 이번에도 구성에 수십 초~수 분이 걸립니다. 팀원이 페르소나 작성 담당(Producer), 근거 검증 담당(Reviewer), 저니맵 작성 담당 세 명으로 보이면 정상입니다 — 작성 담당과 검증 담당이 **분리**되어 있다는 점을 `.claude/agents/` 폴더에서 확인해 보세요.

---

## 5단계: 페르소나 팀 실행 (6분)

하네스가 알려준 실행 문구를 붙여넣습니다. 안 보이면 아래처럼 씁니다:

```
synthesis.md로 페르소나 만들어줘. 이건 우리 {내 서비스} 사용자 데이터야.
```

`persona-journey.md` 파일에 페르소나 2종, 각 페르소나의 대표 인용·기본 정보·목표·페인포인트(모두 근거 번호 포함), 저니맵 표, 그리고 맨 끝에 **검증 로그**가 담겨 나옵니다.

> 💡 **이렇게 나오면 정상입니다**: 같은 synthesis.md를 넣어도 실행할 때마다 페르소나의 표현·구성이 조금씩 달라질 수 있습니다. AI 특성상 정상입니다 — 중요한 건 근거 번호가 매번 붙어 있는지입니다.

> ⚠️ **이럴 땐 이렇게**: 작업 폴더에 `persona-journey.md`가 안 보이면, 다른 이름으로 저장됐을 수 있습니다. 대화창에 `방금 만든 리포트 파일 이름을 persona-journey.md로 바꿔줘`라고 한 번 더 요청하세요. 이후 단계(근거 대조, 산출물 체크리스트)는 모두 이 파일 이름을 기준으로 진행됩니다.

---

## 6단계: 근거 대조 검증 (8분)

페르소나 팀에는 검증 담당이 있지만, **최종 확인은 사람 몫**입니다. `worksheet.md`(페르소나 근거 대조 시트)를 펴고 아래 순서로 진행하세요.

1. `persona-journey.md`에서 페르소나 항목 중 **2~3개**를 고릅니다(예: 대표 인용문, 페인포인트 1개).
2. 각 항목 옆에 붙은 근거 번호(`(P3)` 같은 표기)를 확인합니다.
3. `synthesis.md`에서 근거 번호를 찾습니다. 둘 중 하나만 하면 됩니다.
   - A) 메모장/텍스트 편집기로 파일을 열었다면 `Cmd+F`(Mac) 또는 `Ctrl+F`(Windows)로 `P3` 같은 근거 번호를 검색합니다.
   - B) 편집기 없이 확인하려면 Claude Code 대화창에 `synthesis.md에서 P3 관련 내용 찾아서 보여줘`라고 요청해 답변을 확인합니다.
4. 정말 그 참가자가 그 내용을 말한 것으로 되어 있는지 확인하고, 워크시트에 있음/없음/추정을 체크합니다.
5. `persona-journey.md` 맨 끝의 **검증 로그**도 함께 읽어, 팀이 이미 걸러낸 항목이 무엇인지 확인합니다.

> ⚠️ **이럴 땐 이렇게**: `P3`로 검색했는데 안 잡히면, `P03`처럼 앞에 0이 붙은 표기로 저장됐을 수 있습니다. 앞의 0을 빼거나(P03→P3) 붙여서(P3→P03) 한 번 더 검색해 보세요. 그래도 안 잡히면 검증 담당이 놓친 항목이니, 워크시트에 "없음"으로 표시하고 다음 단계(하네스 회고)에서 팀에게 알려줄 재료로 남겨둡니다.

> ⚠️ **주의(함정): 페르소나·저니맵은 초안이지 결론이 아닙니다**
> - 오늘 만든 페르소나·저니맵은 **1차 초안**입니다. 실제 리서치 분석을 대체하지 않습니다.
> - 인터뷰 수가 적으면 팀이 사실상 같은 사람을 억지로 페르소나 2종으로 쪼갤 수 있습니다. 두 페르소나의 목표·페인포인트가 실제로 갈리는지, 뒷받침 참가자가 겹치지 않는지 한 번 보세요.
> - 소수(예: 1~2명)만 말한 강한 신호(접근성 문제 등)는 "대표적이지 않다"며 페르소나에서 빠질 수 있습니다. 검증 로그에 안 담긴 소수 의견도 훑어보고, 중요하면 별도로 기록하세요.
> - 이 결과를 동료·이해관계자와 공유할 때는 **"AI 초안, 사람 검토 필요"**와 사용한 데이터 범위(인터뷰 몇 건인지)를 함께 표기하세요. 확정 결과처럼 보이지 않게 하는 것이 중요합니다.

## 7단계: 하네스 회고 — 팀 진화 1회 (4분)

결과에서 확인한 아쉬운 점을 팀에게 말로 전달합니다. 아래 문구를 그대로 입력하세요:

```
하네스 회고: 페르소나 각 항목에 근거 참가자 번호를 반드시 붙이고, 근거 없는 칸은 [추정]으로 표시하도록 검증 담당을 개선해줘.
```

> 이 팀은 이미 구성 프롬프트에 이 규칙을 넣어 두었지만, "진화 연습"으로 한 번 더 요청해 팀의 스킬 정의 파일(`.claude/skills/`)이 어떻게 더 구체적으로 바뀌는지 관찰하는 것이 이번 단계의 목적입니다. 6단계에서 "없음"으로 표시한 항목이 있다면, 그 항목을 구체적으로 언급하며 회고 문구를 바꿔 써도 좋습니다. 예: `하네스 회고: 저니맵 3단계 감정 점수에 근거 번호가 안 붙어 있었어. 저니맵 작성 담당이 감정 점수마다 근거 참가자 번호를 빠짐없이 붙이도록 개선해줘.`

다음 실행부터 반영됩니다. **구축은 1회, 실행은 매번** — 다음 리서치 라운드에는 `input` 폴더와 `synthesis.md`만 새로 바꿔 넣고 3·5단계 문구를 다시 실행하면 됩니다.

> 💡 시간이 부족하면 이 단계는 정리 시간에 이어서 해도 괜찮습니다. 다만 오늘 안에 한 번은 `하네스 회고:` 문구를 직접 입력해 팀이 바뀌는 것을 눈으로 봐야 합니다 — L2 전체에서 반복하는 습관입니다.
