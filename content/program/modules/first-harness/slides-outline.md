# 슬라이드 개요 (강사용) — `first-harness`

도입·시연 25분 분량. 슬라이드 제목 + 말할 요점. 실습 50분·정리 15분은 `guide.md` 진행으로 대체(별도 슬라이드 불필요).

---

### 슬라이드 1 — 오늘의 한 문장
**제목**: 오늘, 내 손으로 첫 팀을 만듭니다

- 지난 시간(`first-contact`)엔 Claude Code에게 "이거 해줘"를 한 번씩 시켰다.
- 오늘부터는 "이런 일을 하는 팀을 만들어줘"라고 말하면 팀이 만들어진다.
- 이 경험이 오늘 하루, 그리고 이 교육 전체의 핵심이다 — "AI 도구를 쓰는 사람"이 아니라 "팀을 설계하는 사람"이 되는 첫걸음.
- 오늘 끝에는 여러분 노트북에 실제로 작동하는 팀 하나가 남아 있다.

---

### 슬라이드 2 — 근거: 왜 팀으로 시키면 더 나은가
**제목**: 혼자 시키는 것 vs 팀에게 시키는 것

- A/B 비교 연구 인용(출처: revfactory/claude-code-harness, n=15, **저자 측정·소표본** — 참고용 수치임을 명시하고 시작): 결과물 품질 점수 49.5 → 79.3 (+60%), 결과의 들쭉날쭉함(분산) −32%.
- 특히 작업이 복잡할수록(단계가 많을수록) 개선 폭이 커진다는 경향을 짚는다.
- 말할 포인트: "이 숫자 자체를 외우라는 게 아니다. '역할을 나누고 검증 단계를 넣으면 결과가 더 안정적으로 좋아진다'는 방향성을 기억하면 된다."

---

### 슬라이드 3 — 하네스란 무엇인가
**제목**: 하네스 = 팀을 자동으로 만들어 주는 도구

- 정의: Claude Code용 에이전트 팀 아키텍처 팩토리. 자연어로 도메인을 설명하면 전문 에이전트 팀(`.claude/agents/`)과 팀의 작업 방법(`.claude/skills/`)을 자동 생성.
- 핵심 문장(칠판에 크게): **"코드를 쓰는 게 아니라 팀을 말로 설계하고, 팀이 일한다."**
- 지난 시간에 이미 설치를 완료했음을 확인하고 넘어간다(미완료자 있으면 이 자리에서 재설치).

---

### 슬라이드 4 — 하네스가 만드는 구조 미리보기
**제목**: 버튼을 누르면 이런 폴더가 생깁니다

```
내 작업 폴더/
├── .claude/
│   ├── agents/   ← 팀원 정의 (예: collector.md, classifier.md, verifier.md, reporter.md)
│   └── skills/   ← 팀의 작업 방법 + 오케스트레이터(팀장 역할)
```

- 실제로 이 프로젝트의 `.claude/agents/` 폴더를 화면 공유로 열어 실물을 보여준다(가능하면).
- 용어 두 개를 짚는다: 팀원(에이전트) / 오케스트레이터(트리거 문구로 부르는 팀장 역할).
- "구축은 1회, 실행은 반복" — 오늘 만든 팀은 오늘만 쓰고 버리는 게 아니라 앞으로 계속 재사용한다는 것을 강조.

---

### 슬라이드 5 — 오늘 만들 팀 미리보기 + 구성 프롬프트 해설
**제목**: 오늘 만들 팀: 리뷰 분석 팀

- `usecases/voc-mining.md` 팀 구성 프롬프트를 화면에 띄우고, 오늘 쓸 단순화 버전과 나란히 비교 설명 (CS 티켓·설문·분기 비교는 오늘 뺐다고 명시).
- 프롬프트 3요소를 짚는다: **무엇을 하는 팀인지 / 입력 / 원하는 산출물.**
- 강사가 직접 트리거를 입력해 생성 과정을 라이브로 시연 — 화면에 파일이 하나씩 생기는 것을 보여주고, 대기 시간(수 분)이 정상임을 미리 예고해 둔다.

---

### 슬라이드 6 — 오늘의 핵심: 검증 담당이 있는 팀
**제목**: 이 팀에는 "의심하는 팀원"이 따로 있다

- 시연에서 생성된 `.claude/agents/`를 열어, verifier(검증 담당) 파일을 함께 읽는다.
- Producer-Reviewer 패턴 소개: 만드는 담당과 검증하는 담당을 구조적으로 분리.
- 말할 포인트: "AI는 그럴듯한 인용문을 지어낼 수 있다(환각). 사람이 매번 다 확인하기는 어렵다. 그래서 팀 안에 확인 전담을 심어 둔다 — 오늘 이후 모든 실습에서 이 구조를 계속 확인하게 될 것이다."

---

### 슬라이드 7 — "프롬프트 한 번이냐, 팀이냐"
**제목**: 팀을 만드는 게 항상 정답은 아니다

- 오남용 경고: 뭐든지 팀부터 만들려 하지 않도록, 오늘 판단 기준을 심어 둔다.
- 판단 기준 3가지 제시: ① 반복성 ② 형식 고정 ③ 검증 필요 — 2개 이상이면 팀, 아니면 프롬프트 한 번.
- `usecases/voc-mining.md`의 "하네스가 과한 경우" 절을 화면에 띄워 함께 읽는다.
- 실습에서 학습자가 직접 프롬프트 한 번 vs 팀 결과를 비교해 볼 것임을 예고.
