# 실습 가이드 — 내 반복 업무를 팀 구조로 직접 설계·진화

| 항목 | 내용 |
|------|------|
| 레벨 / 시간 | L3 / 90분 + 과제(1~2주 뒤 산출물 리뷰) |
| 선수 조건 | L2 모듈 2개 이상 수료(`voc-team`, `research-persona-team`, `mvp-team` 중 2개). "매번 같은 방식으로 반복하는 내 업무" 1개를 미리 정해서 오늘 가져오기 |
| 오늘 가져가는 것 | 내 업무를 3~5개 역할로 쪼갠 캔버스 + 실제로 구성·1회 실행한 나만의 하네스 + 진화(하네스 회고) 1회 반영 결과 |

> 지금까지는 사례집이 만들어 둔 구성 프롬프트를 복붙해서 팀을 만들었습니다. 오늘은 그 프롬프트를 **내가 직접 씁니다.** 사례를 베끼는 마지막 날이자, 내 업무를 스스로 설계하는 첫날입니다.

---

## 준비물 체크 (시작 전)

- [ ] Claude Code 실행 가능 + revfactory/harness 플러그인 설치 완료 (`first-contact`에서 끝냄)
- [ ] "매번 같은 방식으로 반복하는 내 업무" 1개 — 예: 매주 CS 티켓 정리, 매월 경쟁사 스크린샷 비교, 매 스프린트 사용성 테스트 메모 정리 등. **떠오르지 않으면 1단계 도입 내용을 다시 훑어보며 예시 업무를 참고해 찾아보세요.**
- [ ] 워크시트(`worksheet.md`) 출력본 또는 화면
- [ ] (있으면) 그 업무에 쓰는 실제 데이터 파일 1건 — 오늘은 데이터 정확도보다 **역할 분해 자체가 목표**라서 없어도 진행 가능
- [ ] 데이터가 없다면: 함께 제공되는 표본 데이터 `sample-usability-notes.txt`(사용성 테스트 세션 노트 6건)를 내려받아 두세요. "매 스프린트 사용성 테스트 메모를 이슈 목록으로 정리한다"는 반복 업무를 가정한 파일로, 수집 → 분류 → 검증 → 리포트 흐름을 그대로 돌려볼 수 있습니다. 앞 모듈의 대체 데이터(`sample-reviews-appstore.txt`, `sample-interview-p1.txt` 등)를 그대로 재사용해도 괜찮습니다.

## 1단계 — 하네스 구조 관찰하기 (도입·예시, 약 30분)

### 1-1. 이 프로젝트 자체가 하네스로 만들어졌다는 사실 관찰 (10분)

지금 여러분이 보고 있는 이 실습 가이드, 사례집, MVP 예시 — 이 교육 프로그램 전체가 사실 **revfactory/harness로 만든 팀**이 만든 결과물입니다. 이 프로젝트 폴더를 직접 열어 아래 구조를 확인하세요.

```
ux-edu/                                ← 이 교육 프로그램의 프로젝트 폴더
├── .claude/
│   ├── agents/                        ← 팀원 정의
│   │   ├── curriculum-designer.md     (커리큘럼 설계 담당)
│   │   ├── edu-material-writer.md     (자료 제작 담당 — 지금 이 가이드를 만든 팀원)
│   │   ├── ux-case-researcher.md      (사례 조사·작성 담당)
│   │   ├── mvp-builder.md             (MVP 구현 담당)
│   │   └── ux-enablement-reviewer.md  (검증 담당 — 읽기 전용, 수정 권한 없음)
│   └── skills/
│       └── ux-enablement/SKILL.md     ← 오케스트레이터(팀장 역할) 스킬
├── content/                           ← 팀이 만들어 낸 산출물 (커리큘럼·모듈·사례집·MVP 예시)
└── docs/                              ← 위 산출물로 빌드한 교육 사이트
```

> 저장소를 내려받았다면(자료실의 **전체 ZIP** 또는 `git clone`) 이 파일들이 그대로 들어 있습니다. 사이트에서 보고 있다면 [GitHub 저장소의 `.claude/` 폴더](https://github.com/namojo/ux-edu/tree/main/.claude)에서 바로 열어볼 수 있습니다. `.claude`처럼 점으로 시작하는 폴더는 탐색기·Finder에서 숨겨져 있으니, 안 보이면 맥은 `Cmd+Shift+.`를 누르거나 Claude Code 대화창에 `.claude/agents 폴더에 뭐가 있는지 보여줘`라고 물어보세요.

**짚고 넘어갈 3가지:**

1. **역할이 나뉘어 있다** — "교육 자료 만들어줘" 한 명이 다 하는 게 아니라, 설계(curriculum-designer)·제작(edu-material-writer)·검수(ux-enablement-reviewer)가 서로 다른 팀원입니다.
2. **검증 담당은 수정 권한이 없다** — `ux-enablement-reviewer.md`를 열어 보면 `tools: Read, Grep, Glob, Bash, WebFetch`라고만 적혀 있고 `Edit`·`Write`가 없습니다. 검증 담당이 직접 고치면 "내가 만들고 내가 검사한" 게 되어 버리니, 구조적으로 손을 묶어 둔 겁니다. 오늘 여러분의 캔버스에도 이 원칙을 그대로 적용합니다.
3. **오케스트레이터가 순서를 지휘한다** — `ux-enablement/SKILL.md`가 "누구를 먼저 부르고, 검수가 반려하면 어떻게 재작업시킬지"를 정의합니다. 이게 `.claude/agents/`의 팀원들을 실제로 움직이는 트리거 지점입니다.

> 💡 **관찰 팁**: 파일을 다 읽을 필요는 없습니다. 각 `.md` 파일 맨 위 1~5줄(역할 설명)과 `tools:` 줄만 봐도 "이 팀원이 뭘 하고, 뭘 할 수 없는지"가 보입니다.

이미 만든 팀이 있는 분(직전 모듈에서 만든 VoC 팀, 페르소나 팀, MVP 팀 등)은 자기 `.claude/agents/` 폴더를 열어 같은 방식으로 관찰해도 좋습니다.

### 1-2. 역할 분해 개념 정리 (10분)

- 반복 업무를 팀으로 만들 때 흔히 나오는 역할: **수집 → 처리/분류 → 검증 → 산출**. 여기에 필요하면 "비교"나 "배포" 역할을 더합니다.
- **검증 담당은 선택이 아니라 필수입니다.** AI는 그럴듯한 내용을 지어내거나(환각), 형식은 맞지만 내용이 틀린 결과를 낼 수 있습니다. 검증 역할이 없으면 이 위험을 팀 구조로 막을 방법이 없습니다.
- 팀 아키텍처 6패턴 중 오늘 가장 많이 쓰이는 것: **Pipeline**(수집→분류→검증→리포트를 순서대로) 과 **Producer-Reviewer**(만드는 사람과 검사하는 사람을 짝짓기). 두 개를 섞어도 됩니다.

### 1-3. harness-100 — 만들지 않고 설치해서 고쳐 쓰는 대안 (10분)

모든 업무를 처음부터 설계할 필요는 없습니다. [revfactory/harness-100](https://github.com/revfactory/harness-100)은 10개 도메인, 100개의 팀 하네스를 미리 만들어 둔 모음입니다.

- 내 업무와 **비슷한 팀이 이미 있다면**: harness-100에서 설치한 뒤 `하네스 회고`로 내 상황에 맞게 고쳐 쓰는 편이 빠릅니다.
- 내 업무가 **회사·팀 특유의 형식이나 판단 기준**이 강하다면(우리 회사만의 분류 체계, 우리 팀만의 리포트 양식 등): 오늘처럼 직접 설계하는 편이 낫습니다.
- 오늘 실습은 **직접 설계 경로로 진행**합니다. 다만 harness-100을 먼저 살펴보고 "이거랑 비슷한데?" 싶은 게 있으면 워크시트 과제란에 적어 두세요 — 다음에 더 빠른 경로로 쓸 수 있습니다.

> 🛠️ **이럴 땐 이렇게**: harness-100에 정확히 맞는 팀이 없어도 정상입니다. UX/CX 업무는 회사마다 형식이 달라서, 100% 일치는 오히려 드뭅니다. "70% 맞고 30%는 회고로 고친다"는 감각으로 접근하세요.

## 2단계 — 반복 업무 → 역할 분해 캔버스 작성 (실습, 약 15분)

`worksheet.md`를 펴고 아래 순서로 채웁니다. (자세한 작성 요령은 워크시트 안내를 따르세요.)

> 💡 **이 단계가 오늘 가장 어렵습니다**: 백지에서 업무 선정 → 3~6단계 서술 → 3~5역할 묶기 → 검증 담당 정의까지 한 번에 다 채우려 하지 말고, 도입 1-2에서 본 예시 업무를 참고해 절반쯤 먼저 채워 보세요. 시간이 빠듯하면 3단계(20분) 초반 일부를 캔버스 마무리에 유연하게 써도 됩니다. 시간에 쫓겨 검증 담당 칸을 형식적으로 채우고 넘어가지 않는 것이 핵심입니다.

1. **업무명 + 반복 주기**를 한 줄로 적습니다. (예: "매주 월요일, 지난주 CS 티켓 50~100건 정리해 팀 채널에 공유")
2. 그 업무를 **지금 혼자 어떤 순서로 처리하는지** 3~6단계로 적어 봅니다. (예: 티켓 다운로드 → 눈으로 읽기 → 유형별 색칠 → 요약 작성 → 공유)
3. 그 단계들을 **3~5개 역할**로 묶습니다. 이때 **검증 담당 역할을 반드시 하나 포함**하세요 — "내가 지금 지겨워서 대충 넘어가는 확인 작업"이 검증 담당의 후보로 가장 좋습니다.

> 💡 **막히면 이렇게 물어보세요**: 캔버스 칸이 잘 안 채워지면, Claude Code에게 아래를 붙여넣어 물어봐도 됩니다. 제안을 그대로 쓰지 말고, 내 업무 감각과 맞는지 검토한 뒤 캔버스에 옮기세요.

```
내가 이런 반복 업무를 해: {업무 설명}.
이 업무를 팀으로 나눈다면 역할을 몇 개로, 어떻게 나누는 게 좋을지 제안해줘.
검증 담당 역할도 꼭 포함해서 제안해줘.
```

## 3단계 — 캔버스를 구성 프롬프트로 옮기고 실행 (실습, 약 20분)

### 3-1. 구성 프롬프트 작성

워크시트에 채운 캔버스를 아래 틀에 옮겨 적습니다. `{ }` 부분을 캔버스 내용으로 바꾸세요.

```
하네스 구성해줘: {업무명}을 처리하는 팀이 필요해.
{입력 데이터/형태}을 입력하면,
(1) {역할1이 하는 일}
(2) {역할2가 하는 일}
(3) {검증 담당이 확인하는 일 — 무엇을 원문 대조/기준 대조하는지 구체적으로}
(4) {역할4가 하는 일, 있다면}
까지 만들어주는 팀으로 만들어줘.
결과는 {원하는 산출 형식 — 예: 마크다운 리포트, 표}로 저장해줘.
```

> 캔버스에서 역할을 5개(역할 5)까지 나눴다면 `(4)` 아래에 `(5) {역할5가 하는 일}` 줄을 하나 더 추가하세요. 슬롯 개수는 캔버스의 역할 개수와 맞추면 됩니다.

> 💡 **좋은 프롬프트 vs 아쉬운 프롬프트**
> - 아쉬운 예: `하네스 구성해줘: CS 티켓 정리하는 팀`  → 너무 짧아서 팀이 알아서 추측합니다.
> - 좋은 예: 무엇을 입력받고, 역할별로 무엇을 하고, 검증 담당이 정확히 무엇을 대조하고, 결과를 어떤 형식으로 저장할지까지 구체적으로 적은 것.
> 사례집의 모든 2단계 프롬프트([VoC 분석 팀](../../../usecases/voc-mining.md), [MVP 프로토타입 팀](../../../usecases/mvp-prototype.md) 등)가 이 형태를 따릅니다. 지금까지 복붙해 온 프롬프트가 곧 오늘 직접 쓰는 프롬프트의 모범 답안입니다.

### 3-2. 구성 실행

작성한 프롬프트를 Claude Code 대화창에 붙여넣고 실행합니다.

> 💡 **이렇게 나오면 정상입니다**: 생성까지 수 분이 걸립니다. 화면에 파일 생성 로그가 쭉 올라가면 잘 진행되는 중입니다. 중간에 멈춘 것처럼 보여도 기다려 주세요.

생성이 끝나면 `.claude/agents/` 폴더를 열어 몇 개의 역할이 만들어졌는지, 검증 담당이 포함됐는지 확인합니다. 하네스는 로그 맨 마지막 부분에 **"이제 이렇게 실행하세요" 식의 한 문장(실행 트리거 문구)**을 알려줍니다. 이 문장을 그대로 복사해 워크시트 4번 칸에 받아 적으세요.

> 💡 **이렇게 나오면 정상입니다**: 캔버스에 적은 역할 이름과 실제 생성된 팀원 파일명이 완전히 똑같지 않을 수 있습니다(예: "정리 담당"이라고 적었는데 파일명은 `organizer.md`). 하네스가 이름을 다듬어 생성하는 것은 정상입니다. 역할의 **개수와 기능**이 캔버스와 맞는지만 확인하면 됩니다.
>
> 🛠️ **이럴 땐 이렇게**: 검증 담당이 빠진 채 생성됐다면, 새 프롬프트를 다시 쓰지 말고 바로 4단계의 `하네스 회고`로 "검증 담당을 추가해줘"라고 요청하세요. 처음부터 다시 만드는 것보다 빠릅니다.
>
> 🛠️ **트리거 문구를 로그에서 못 찾겠으면**: 생성 로그가 길어서 한눈에 안 보일 수 있습니다. 이 순서로 시도하세요.
> 1. 화면을 위로 스크롤해 「~ 실행해줘」, 「~ 해줘」처럼 따옴표나 코드 블록 안에 든 한 문장을 찾습니다. 보통 로그의 맨 끝, "이제 이렇게 실행하세요" 같은 안내 바로 아래에 있습니다.
> 2. 못 찾겠으면 그냥 대화창에 「{업무명} 실행해줘」라고 직접 입력해 보세요 — 사례집 예시(예: 「VoC 분석 실행해줘」 = 도메인 이름 + "실행해줘")와 같은 규칙으로 대부분 동작합니다.
> 3. 그래도 반응이 없거나 오류가 나면 에러 메시지를 그대로 복사해 Claude Code에 붙여넣고 "이 에러 어떻게 해결해?"라고 물어보세요. 해결이 안 되면 사내 헬프 채널에 문의하세요.

### 3-3. 실행

새 세션을 엽니다. **`/clear`를 우선 권장**합니다 — 같은 폴더에 머무르므로 안전합니다. `claude`를 재실행하는 방법을 쓴다면, **반드시 하네스를 만든 그 프로젝트 폴더에서 켜야 합니다**(다른 폴더에서 켜면 방금 만든 팀이 보이지 않습니다). 새 세션에서 방금 받아 적은 트리거 문구를 입력합니다. 자기 데이터가 있으면 함께 넣고, 없으면 함께 제공되는 표본 데이터 `sample-usability-notes.txt`로 진행합니다. **어느 쪽이든**: 데이터 파일을 작업 폴더(하네스가 생성된 프로젝트 폴더)에 먼저 넣은 뒤, 트리거 문구 뒤에 "{파일명}으로 실행해줘"처럼 파일명을 함께 말해 주세요. (예: "VoC 분석 실행해줘, reviews.txt로" / "세션 노트 정리 실행해줘, sample-usability-notes.txt로")

> 💡 **이렇게 나오면 정상입니다**: 세션마다 결과의 문장 표현이나 분류 개수가 조금씩 달라질 수 있습니다. 매번 완전히 똑같은 결과가 나오지 않는 것이 정상입니다 — 팀 구조(역할·검증 단계)가 매번 같은 방식으로 동작하는지가 중요하지, 결과 문구가 토씨 하나까지 같을 필요는 없습니다.

## 4단계 — 하네스 회고: 진화 연습 (실습, 약 10분)

방금 받은 결과에서 아쉬운 점 하나를 찾습니다(형식이 안 맞다, 검증이 허술하다, 특정 항목이 빠졌다 등). 워크시트의 진화 프롬프트 칸을 채운 뒤 아래 틀로 실제 입력합니다.

```
하네스 회고: {아쉬운 점}. {어떤 팀원을} {어떻게} 개선해줘.
```

예시:
```
하네스 회고: 검증 담당이 원문 대조 없이 "확인됨"이라고만 써. 대표 인용은 반드시
원문에서 찾은 문장을 그대로 인용하고, 못 찾으면 [원문 미확인]으로 표시하도록
검증 담당을 개선해줘.
```

입력 후 `.claude/agents/`의 해당 팀원 파일이 수정된 걸 확인하고, 다시 트리거 문구로 실행해 반영 여부를 확인합니다.

> 💡 **이렇게 나오면 정상입니다**: 회고 한 번으로 모든 게 완벽해지지 않을 수 있습니다. 여러 번 나눠 회고하는 것이 정상입니다 — 오늘은 1회 반영까지만 확인하면 충분합니다.

---

## 5단계 — 공유·정리 (15분)

- **공유 (약 10분)**: 오늘 만든 캔버스와 트리거 문구를 다시 훑어보며, "어떤 역할을 몇 개로 나눴는지"보다 "검증 담당이 정확히 뭘 대조하는지"를 한 줄로 정리해 봅니다 — 가장 자주 허술해지는 지점입니다. 그룹 스터디로 진행 중이라면 서로의 캔버스를 보여주고 이야기해도 좋습니다.
- **과제 안내·마무리 (약 5분)**: 아래 과제 내용과 제출 방식을 확인하고, 오늘 설치(`first-contact`) → 첫 구성(`first-harness`) → 사례로 반복(L2) → 직접 설계(오늘)로 이어진 여정을 짧게 정리합니다.

---

## 과제 (1~2주 뒤 산출물 리뷰)

1. 오늘 만든 하네스를 **다음 실무 라운드에 실제로 한 번 더 돌려 보세요.** (예: 다음 주 CS 티켓으로 다시 실행)
2. 실행하면서 또 아쉬운 점이 나오면 `하네스 회고`를 한 번 더 넣어 보세요 — 오늘 배운 진화 습관을 실무에서 반복하는 것이 이 과제의 핵심입니다.
3. 아래를 정리해 리뷰에 제출합니다:
   - 두 번째 실행 결과 (파일)
   - 추가로 넣은 `하네스 회고` 문장과, 그 결과 무엇이 바뀌었는지
   - 막힌 점이 있었다면 무엇이었는지 (하네스 진화의 다음 입력이 됩니다)

> 이 과제는 "완벽한 팀을 한 번에 만드는 것"이 목표가 아닙니다. **키워 가는 자산으로 하네스를 계속 손보는 습관**이 목표입니다.
