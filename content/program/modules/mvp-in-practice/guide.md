# 실습 가이드 — 내 아이디어를 클릭되는 시제품으로

> 모듈 `mvp-in-practice` · L2 · 90분 · 3회차(마지막 모듈)

이 가이드는 화면에 보이는 순서 그대로 따라가면 됩니다. 강사 없이 혼자 다시 해도 똑같이 따라 할 수 있게 썼습니다.

---

## 0. 이 모듈에서 만드는 것

당신의 서비스 아이디어를 **코드 없이**, 클릭해서 화면을 넘겨볼 수 있는 HTML 시제품(MVP)으로 만듭니다. 사용성 테스트에 바로 쓸 수 있는 수준의 결과물이 목표입니다.

> **바이브 코딩(vibe coding)이란?** 코드를 직접 쓰지 않고, 자연어(일상 말)로 원하는 화면·동작을 요청해 AI가 그 자리에서 프로그램을 만들어주는 방식입니다. 오늘 STEP 2~3에서 이 방식으로 시제품을 직접 만들어봅니다.

| 항목 | 내용 |
|------|------|
| 선수 조건 | L1 2개 모듈(`first-contact`, `prompt-and-verify`) 수료 |
| 준비물 | 검증하고 싶은 **자기 서비스의 화면 흐름 아이디어** (메모 형태로 미리 정리해 오면 가장 좋습니다) |
| 사용 사례 교재 | `usecases/mvp-prototype.md` |
| 완성 예시 | `mvp/onboarding-smoke/index.html` |
| 최종 산출물 | 자기 아이디어의 화면 3개 이상을 클릭으로 오갈 수 있는 `index.html` 1개 + 수정 요청 1건 반영 |

**진행 순서와 시간 배분**

| 단계 | 내용 | 시간 |
|------|------|------|
| 도입·시연 | "바이브 코딩"이 뭔지, 오늘 무엇을 만드는지 강사 설명 + 시연 | 30분 |
| STEP 1 | 완성 예시 먼저 체험하기 | 5분 |
| STEP 2 | 내 아이디어로 첫 시제품 만들기 | 15분 |
| STEP 3 | 브라우저에서 열어 완주 + 말로 수정하기 | 15분 |
| STEP 4 | 검증 범위 정리하기 | 10분 |
| 공유·정리 | 몇 명 발표 + 다음 회차(`my-harness`) 안내 | 15분 |

## STEP 1. 완성 예시 먼저 체험하기 (5분)

말로만 설명을 들으면 "클릭되는 시제품"이 정확히 뭔지 감이 안 옵니다. 완성된 결과물을 먼저 눌러봅니다.

1. 강사가 배포한(또는 다운로드한) 교육자료 폴더를 엽니다. 그 안의 `mvp` 폴더 → `onboarding-smoke` 폴더로 들어가면 완성 예시 파일이 있습니다.
2. `index.html` 파일을 **더블클릭**합니다. → 기본 브라우저가 열리면서 휴대폰 모양 화면이 가운데에 나타납니다.
3. 아래 순서대로 끝까지 클릭해 완주합니다.

   `환영 화면` → `시작하기` → `취향 선택(복수 선택 가능 — 하나 이상 눌러야 아래 저장 버튼이 활성화됩니다)` → `내 취향 저장하기` → `홈(추천 노출)` → `음료 카드 탭` → `주문 완료`

4. 완주했다면 같은 폴더의 `README.md`를 열어 봅니다. 이 시제품이 "무엇을 검증하려고 만든 것인지", "무엇은 검증할 수 없는지"가 항목별로 정리되어 있습니다. STEP 4에서 당신도 이런 정리를 만들게 됩니다.

> 💡 **더블클릭했는데 코드처럼 보이는 화면이 뜨면?**
> 브라우저가 아니라 텍스트 편집기로 열린 것입니다. 파일을 다시 우클릭 → `연결 프로그램` → `Chrome`(또는 `Safari`, `Edge` 등 브라우저)을 선택하세요.

## STEP 2. 내 아이디어로 첫 시제품 만들기 (15분)

### 2-1. 재료 정리 (프롬프트에 그대로 넣을 4가지)

미리 준비해 온 메모가 있다면 그대로 쓰고, 없다면 지금 아래 빈칸을 채우세요. 이 정리가 결과물 품질의 8할을 좌우합니다 — AI는 흐름을 상상해주지 않고, 당신이 준 흐름만 화면으로 옮깁니다.

```
무슨 서비스인가:
누가 쓰나:
검증할 핵심 흐름 (화면 순서 3~5단계, 화살표로):
이 프로토타입으로 확인하고 싶은 것 1가지:
```

### 2-2. 작업 폴더 만들고 Claude Code 켜기

1. 바탕화면(또는 문서 폴더)에 새 폴더를 만듭니다. 예: `mvp-내서비스명`
2. 그 폴더를 **우클릭 → "폴더에서 새로운 터미널 열기"**(맥) / 폴더 열고 주소창에 `cmd` 입력 후 엔터(윈도우)로 터미널을 엽니다.
3. 터미널에 `claude`를 입력해 Claude Code를 켭니다.

> 💡 **터미널 위치가 그 폴더인지 헷갈리면?**
> 걱정하지 말고 그냥 아무 데서나 `claude`를 켠 뒤, 첫 문장으로 이렇게 지정하세요.
> `이 대화에서 만드는 파일은 전부 바탕화면의 mvp-내서비스명 폴더에 넣어줘.`
> 이러면 터미널 시작 위치와 무관하게 원하는 폴더에 파일이 생깁니다.

### 2-3. 복붙 프롬프트 실행

아래를 그대로 복사해 붙여넣고, `{중괄호}` 부분만 2-1에서 정리한 내용으로 바꿔서 실행하세요. (`usecases/mvp-prototype.md`와 동일한 프롬프트입니다.)

```
사용성 테스트에 쓸 클릭 가능한 HTML 프로토타입을 만들어줘. 나는 코드를 모르니까,
결과는 index.html 파일 하나로 만들어서 더블클릭하면 브라우저에서 바로 열리게 해줘.

- 서비스: {내 서비스 이름/설명}
- 사용자: {누가 쓰는지}
- 검증할 핵심 흐름(이 순서대로 화면 전환): {화면1 → 화면2 → 화면3 → ...}
- 이 프로토타입으로 확인하고 싶은 것: {확인하고 싶은 것 1가지}

조건:
1. 화면은 위 흐름에 필요한 4~5개만. 전체 앱을 다 만들지 마.
2. 모바일 화면처럼 보이게, 데스크톱에서 열어도 가운데에 휴대폰 프레임으로 표시해줘.
3. 로그인·결제·서버 연결은 만들지 마. 버튼을 누르면 다음 화면으로 넘어가는 것까지만.
4. 데이터는 실제로 있을 법한 그럴듯한 한국어 더미로 채워줘. (테스트1, 홍길동 같은 티나는 값 말고)
5. 모든 버튼은 어딘가로 이어져야 해. 막다른 화면 없이 뒤로가기나 홈 버튼을 넣어줘.
6. 인터넷 없이도 열려야 하니까 외부 이미지·폰트 링크는 쓰지 말고, 그림은 이모지나 색 도형으로 대체해줘.

다 만들면, 비개발자인 내가 읽을 수 있게 "화면 순서 / 이 시제품으로 검증되는 것과 안 되는 것 /
수정 요청하는 법"을 담은 README.md도 같이 만들어줘.
```

> 💡 **권한 확인 창이 뜨면?**
> Claude Code가 파일을 새로 만들거나 폴더에 쓰기 전에 "이 작업을 허용할까요?" 라고 물어봅니다. 내가 요청한 작업(시제품 만들기)이 맞으니 **허용**을 선택하면 됩니다. 매번 물어보는 게 번거로우면 "이번 세션에서는 계속 허용"을 선택해도 됩니다.

> 💡 **1~2분 정도 화면에 진행 표시만 뜨고 멈춘 것 같으면?**
> 정상입니다. 화면 여러 개와 스타일을 한 번에 만드는 작업이라 시간이 걸립니다. 커서가 깜빡이고 있다면 계속 작업 중인 것이니 기다리세요.

작업이 끝나면 Claude Code가 만든 화면 목록을 텍스트로 요약해 보여줍니다. (예: "환영 화면 → 취향 선택 → 홈 → 주문 완료, 총 4개 화면을 만들었습니다.")

> 💡 **화면 개수가 내가 적은 흐름 단계 수보다 적게 나오면?**
> 오류가 아닙니다. 비슷한 화면(예: "주문"과 "완료")을 한 화면으로 합쳐서 효율적으로 만드는 경우가 흔합니다. STEP 3에서 실제로 눌러보고 이상하면 그때 나눠 달라고 요청하면 됩니다.

## STEP 3. 브라우저에서 열어 완주 + 말로 수정하기 (15분)

### 3-1. 결과 확인

1. 방금 만들어진 폴더에서 `index.html`을 찾아 **더블클릭**합니다.
   - 또는 Claude Code에게 `방금 만든 프로토타입을 브라우저에서 열어줘`라고 요청해도 됩니다.
2. 처음부터 끝까지, **모든 버튼을 한 번씩** 눌러 화면이 끊기지 않고 이어지는지 확인합니다. 뒤로가기 버튼도 눌러보세요.

> 💡 **버튼을 눌렀는데 아무 반응이 없으면?**
> 막다른 화면이 하나 남은 것입니다. AI가 실수로 빠뜨렸을 수 있습니다. Claude Code로 돌아가 `{화면 이름}에서 버튼을 눌러도 다음으로 안 넘어가. 확인해서 고쳐줘`라고 요청하면 바로잡아 줍니다.

### 3-2. 말로 수정하기 (수정 요청 1건 이상)

마음에 안 드는 부분을 자연어로 요청해 고칩니다. 예시:

- `{화면 이름}에 예상 픽업 시간(예: 5분 뒤) 안내를 추가해줘.`
- `{화면 이름}이 너무 밋밋해. 카드마다 이모지를 넣고 선택하면 색이 진해지게 해줘.`
- `{화면 이름}의 버튼 문구를 더 눈에 띄게 크게 바꿔줘.`

**요청할 때 반드시 이 문장을 붙이세요**: `기존 화면 구조는 그대로 두고, 말한 부분만 고쳐줘.` — 이래야 이후 사용성 테스트 결과를 이전 버전과 비교할 수 있습니다. (더 다양한 수정 문구는 핸드아웃 참고)

수정이 끝나면 `index.html`을 다시 더블클릭하거나 브라우저에서 새로고침(F5 / Cmd+R)해 바뀐 점을 확인합니다.

> 💡 **새로고침해도 그대로면?**
> 파일이 다른 위치에 다시 만들어졌을 수 있습니다. Claude Code에게 `방금 수정한 index.html이 어디 있는지 알려줘`라고 물어보세요.

## STEP 4. 검증 범위 정리하기 (10분)

MVP는 완성품이 아니라 **테스트 도구**입니다. 무엇을 검증할 수 있고, 무엇은 안 되는지 스스로 적어봅니다. 아래 빈칸을 채우세요. (완성 예시의 `README.md`에 정리된 "검증할 수 있는 것 / 없는 것" 항목을 참고해도 좋습니다.)

```
이 시제품으로 검증할 수 있는 것:
1.
2.

이 시제품으로 검증할 수 없는 것 (의도적으로 뺀 것):
1.
2.
```

정리가 끝나면 Claude Code에게 이렇게 요청해 README.md에 반영할 수도 있습니다.

```
지금까지 얘기한 내용을 바탕으로 README.md의 "검증할 수 있는 것 / 없는 것" 항목을
내가 방금 정리한 내용으로 업데이트해줘.
```

## 꼭 사람이 확인하세요 (공유·정리 시간에 함께 짚기)

- **"열리고 클릭된다"와 "흐름이 좋다"는 다른 문제입니다.** 흐름의 타당성은 반드시 사람이, 되도록 실제 사용성 테스트로 검증하세요.
- **더미 데이터는 전부 지어낸 값(환각)입니다.** 참가자나 이해관계자에게 보여줄 때 "실제 데이터 아님"을 꼭 알려주세요.
- **접근성은 자동으로 챙겨지지 않습니다.** 필요하면 `이 화면들 색 대비랑 키보드 조작 접근성 관점에서 문제 있는 곳 짚어줘`라고 이어서 물어보세요.
- **이건 시제품이지 제품이 아닙니다.** 새로고침하면 상태가 초기화됩니다. "이대로 출시"가 아니라 "흐름을 검증했으니 이제 제대로 개발하자"가 다음 단계입니다.
