# 화면 HTML(또는 화면 설명)에서 접근성 문제 뽑아 개선안까지 받기

| 항목 | 내용 |
|------|------|
| 영역 | 접근성 점검 (a11y-audit) |
| 난이도 | 중급 |
| 소요 시간 | 약 30~40분 |
| 준비물 | 점검할 화면의 HTML 파일 1개(또는 화면을 글로 자세히 적은 설명 파일), Claude Code가 설치된 컴퓨터 |

## 이런 상황에서 쓰세요

디자인 시안이나 개발된 화면을 두고 "이거 접근성 괜찮나요?"라는 질문을 받았을 때, 무엇부터 봐야 할지 막막합니다. 색 대비, 대체 텍스트, 키보드 이동, 폼 라벨… 체크리스트는 길고 용어는 어렵고, 전문 감리를 맡기면 2~4주에 비용도 큽니다. 그렇다고 그냥 넘기면 나중에 "스크린리더로 결제가 안 된다"는 민원이 들어옵니다. 이 사례는 화면의 HTML(또는 화면 설명)을 AI에게 1차로 훑게 해서, WCAG(웹 콘텐츠 접근성 지침 — 장애가 있는 사용자도 웹을 쓸 수 있게 하는 국제 표준) 관점의 이슈 목록과 심각도, 개선안 초안을 빠르게 받는 방법입니다. 사람은 처음부터 다 뒤지는 대신, AI가 짚어준 곳을 검토·판단하는 데 집중합니다.

> a11y는 "accessibility(접근성)"를 줄여 부르는 업계 표기입니다. a와 y 사이 글자가 11개라 a11y로 씁니다.

## 따라 하기

### 1단계: 준비

점검할 화면을 **파일 하나**로 준비합니다. 두 가지 경우가 있습니다.

**경우 A — HTML 파일이 있을 때(권장, 더 정확함)**
1. 바탕화면이나 문서 폴더에 작업용 폴더를 하나 만듭니다. 예: `a11y-점검-결제화면`
2. 점검할 화면의 HTML 파일을 그 폴더에 넣습니다. 개발자에게 "이 화면 HTML 파일 하나만 주세요"라고 요청하거나, 크롬 브라우저에서 화면을 연 뒤 마우스 오른쪽 클릭 → "페이지 소스 보기"의 내용을 복사해 메모장에 붙여넣고 `checkout.html`로 저장하면 됩니다.

> 저장할 때 주의(중요): 윈도우 메모장에서는 저장할 때 '파일 형식'을 '모든 파일(*.*)'로 바꾼 뒤 파일명을 `checkout.html`로 적어야 합니다(그냥 저장하면 `checkout.html.txt`가 되어 Claude Code가 파일을 못 찾습니다). 맥 텍스트편집은 상단 메뉴 `포맷 → 일반 텍스트로 만들기`를 먼저 누른 뒤 저장하세요. 저장이 헷갈리면, 앞서 안내한 대로 개발자에게 HTML 파일을 직접 받는 경로를 우선 권합니다.

> 주의: 요즘 결제·로그인 화면은 자바스크립트로 그려지는 경우가 많아, "페이지 소스 보기"로 나오는 원본 HTML이 실제 눈에 보이는 화면과 다를 수 있습니다(화면에 있는 라벨·버튼이 소스에는 없을 수 있음). 이러면 점검 결과가 화면과 어긋날 수 있으니, 가능하면 개발자에게 **실제로 그려진 HTML 파일**을 받는 편이 정확합니다.

**경우 B — HTML이 없고 시안·화면만 있을 때**
1. 같은 방식으로 폴더를 만들고, 화면을 **글로 자세히 묘사한 설명**을 `screen.txt`(메모장으로 만든 텍스트 파일)로 저장합니다. 예: "상단에 로고 이미지, 그 아래 '주문하기' 파란 버튼(글자 흰색), 이메일 입력칸에는 라벨 없이 회색 안내문구만 있음, 하단에 빨간 글씨로 에러 표시…" 처럼 색·순서·이미지·버튼을 있는 그대로 적습니다.

> 경우 B는 사람이 본 것만 적히므로 놓치는 부분이 생깁니다. 가능하면 경우 A(HTML)로 하세요. HTML에는 눈에 안 보이는 정보(대체 텍스트, 라벨 연결 등)가 들어 있어 AI가 훨씬 정확하게 봅니다.

**경우 A든 B든 — 파일을 폴더에 넣었으면 마지막으로 이렇게 실행합니다**

Claude Code는 그 폴더 안의 파일을 읽고 쓸 수 있는 AI 도구이고, **터미널**(명령어를 입력하는 검은 창)에서 켭니다. 이때 "만든 폴더 안에서" 터미널을 열어야 Claude Code가 그 파일을 찾을 수 있습니다. 코딩을 안 해봤어도 되는 가장 쉬운 방법 두 가지 중 하나를 쓰세요.

- **방법 1 (클릭만으로, 추천):** 만든 폴더를 파인더(맥)나 파일 탐색기(윈도우)에서 엽니다. 폴더 안 빈 공간에서 마우스 오른쪽 클릭 → "터미널에서 열기"(맥) 또는 "터미널에서 열기 / 여기서 명령 창 열기"(윈도우)를 고릅니다. 그러면 이동할 필요 없이 **바로 그 폴더에서** 터미널이 열립니다.
- **방법 2 (드래그로):** 터미널을 먼저 켠 뒤, `cd`(폴더를 이동하는 명령)를 치고 한 칸 띄웁니다. 그다음 만든 폴더를 마우스로 집어 터미널 창 안으로 끌어다 놓으면 폴더 경로가 자동으로 입력됩니다. Enter를 누르면 그 폴더로 들어갑니다.

폴더 안에 들어온 상태에서 `claude` 라고 입력하고 Enter를 누르면 Claude Code가 켜집니다.

### 2단계: 프롬프트 입력

아래를 복사해 붙여넣고, {중괄호} 부분만 바꾸세요:

```
checkout.html 파일을 읽어줘. 이건 {우리 쇼핑 앱의 결제 화면}이야.

이 화면을 WCAG 2.2 AA 기준으로 접근성 점검해줘. 다음 규칙을 지켜줘:

1. 발견한 문제를 표로 정리해줘. 각 행에: (a) 문제 요약, (b) 관련된 화면 요소(어떤 버튼/이미지/입력칸인지 구체적으로), (c) 위반으로 의심되는 WCAG 항목 번호와 이름(예: 1.1.1 비텍스트 콘텐츠), (d) 심각도(높음/중간/낮음), (e) 개선안 한 줄.
2. 심각도는 "이 문제 때문에 특정 사용자가 아예 그 기능을 못 쓰는가"를 기준으로 매겨줘. 결제·로그인 같은 핵심 동작을 막으면 높음.
3. 심각도 높음부터 위로 정렬해줘.
4. 표 아래에, 개선안 중 3개를 골라 "고치기 전 → 고친 후" 코드 예시를 짧게 보여줘.
5. 마지막에 "이 도구만으로는 확인할 수 없어 사람이 직접 테스트해야 하는 항목"을 따로 목록으로 적어줘.

HTML에 실제로 없는 문제는 지어내지 마. 판단이 애매하면 '확인 필요'로 표시하고 왜 애매한지 적어줘.
```

> 경우 B(설명 파일)라면 첫 줄을 `screen.txt 파일을 읽어줘. 이건 우리 결제 화면을 글로 묘사한 거야.` 로 바꾸고, 4번의 코드 예시 항목은 `개선안 3개를 골라 "지금 상태 → 이렇게 바꾸세요"로 구체적으로 설명해줘.` 로 바꾸세요.

### 3단계: 결과 확인

이런 식의 결과가 나옵니다(내용은 예시입니다):

| 심각도 | 문제 요약 | 관련 요소 | WCAG 항목 | 개선안 |
|--------|-----------|-----------|-----------|--------|
| 높음 | 이메일 입력칸에 라벨이 없어 스크린리더가 무엇을 입력하는 칸인지 못 읽음 | `<input type="email">` (placeholder만 있음) | 1.3.1 정보와 관계, 4.1.2 이름·역할·값 | `<label>`을 붙이거나 `aria-label` 추가 |
| 높음 | '주문하기' 파란 버튼의 글자색·배경 대비가 부족해 저시력 사용자가 못 읽음 | 파란(#5B9BD5) 배경 + 흰 글자 | 1.4.3 명암 대비 | 배경을 더 진한 파랑(#1F5FA8 등)으로 조정 |
| 중간 | 로고 이미지에 대체 텍스트가 비어 있음 | `<img src="logo.png" alt="">` | 1.1.1 비텍스트 콘텐츠 | `alt="OO몰 홈"` 처럼 의미 있는 대체 텍스트 |
| 중간 | 에러 메시지를 빨간색으로만 표시해 색을 못 구분하는 사용자가 놓침 | "필수 항목입니다" 빨간 글씨 | 1.4.1 색의 사용 | 아이콘/텍스트("오류:")를 함께 표시 |

그리고 표 아래에 "고치기 전 → 고친 후" 코드 예시가 나옵니다. 예:

```
[고치기 전]
<input type="email" placeholder="이메일">

[고친 후]
<label for="email">이메일</label>
<input type="email" id="email" placeholder="예: name@mail.com">
```

마지막에 "사람이 직접 테스트해야 하는 항목"이 따로 나옵니다. 예:
> - 키보드 Tab 키만으로 결제까지 끝까지 이동되는지 (초점 순서는 실제로 눌러봐야 확인 가능)
> - 대체 텍스트가 "의미 있게" 쓰였는지 (문법상 채워져 있어도 내용이 엉뚱할 수 있음)
> - 실제 스크린리더로 읽었을 때 자연스러운지

### 4단계: 다듬기

첫 결과가 나오면 후속 프롬프트로 원하는 방향으로 좁혀 갑니다. 아래처럼 이어서 입력하면 됩니다:

- `심각도 '높음' 항목만 골라서, 개발자에게 전달할 수 있게 각각 "무엇을·왜·어떻게" 3줄로 정리해줘.`
- `이 결과 전체를 a11y-report.md 파일로 저장해줘. 표는 그대로 두고, 맨 위에 '핵심 3가지 먼저 고치기' 요약을 붙여줘.`

두 번째처럼 파일로 저장(`a11y-report.md`는 마크다운, 즉 표·제목을 기호로 표현한 텍스트 파일)해 두면 개발·디자인 팀에 그대로 공유하거나 다음 점검 때 비교할 수 있습니다.

## 꼭 사람이 확인하세요

- **AI만으로는 접근성 문제의 절반 이상을 놓칩니다.** 자동 점검이 잘 잡는 건 색 대비, 라벨 누락, 대체 텍스트 유무처럼 "기계가 규칙으로 판정 가능한" 문제입니다. 반대로 초점(포커스) 순서, 키보드만으로 끝까지 되는지, 화면을 확대했을 때 깨지는지, 도움말이 일관되게 있는지 같은 **판단이 필요한 항목은 사람이 실제로 조작해봐야** 합니다. 업계 조사에 따라 자동 점검이 잡아내는 위반은 전체의 30~40% 수준이고, 나머지 절반 이상은 사람 검토가 필요하다고 봅니다(아래 참고 링크의 [자동 vs 수동 점검 비교](https://testparty.ai/blog/automated-wcag-2-1-testing-ai-implementation-guide-2025) 참조). AI 결과는 "출발점"이지 "합격증"이 아닙니다.
- **WCAG 항목 번호를 그대로 믿지 말고 한 번 대조하세요.** AI가 문제는 맞게 짚어도 "1.4.3"을 "1.4.11"로 잘못 붙이는 식의 오류(환각)가 있을 수 있습니다. 보고서에 넣기 전, 번호와 이름이 맞는지 [W3C WCAG 공식 문서](https://www.w3.org/TR/WCAG22/)에서 한 번 확인하세요.
- **대체 텍스트가 "채워졌는지"와 "제대로인지"는 다릅니다.** AI는 `alt`가 비었다는 건 잘 잡지만, `alt="이미지"`처럼 채워졌으나 무의미한 경우는 통과로 볼 수 있습니다. 이미지가 실제로 전달해야 할 의미를 사람이 판단해 채워야 합니다.
- **경우 B(설명 파일)는 놓친 게 많습니다.** 사람 눈에 안 보이는 코드 속 문제(라벨 연결, ARIA 속성 등)는 설명에 안 적히면 AI도 모릅니다. 설명 기반 결과는 "눈에 보이는 수준의 1차 점검"으로만 쓰세요.
- **최종 판정은 실제 보조기술로.** 가능하면 스크린리더(윈도우 NVDA, 맥 보이스오버 — 화면을 소리로 읽어주는 무료 프로그램)로 핵심 플로우를 한 번 통과시켜 보는 것이 가장 확실합니다.

## 한 걸음 더

접근성 점검이 매 스프린트·매 배포마다 반복된다면, 매번 프롬프트를 붙여넣는 대신 **에이전트 팀(하네스)** 으로 승격할 가치가 있습니다. 하네스는 역할이 나뉜 AI들이 순서대로 일하는 작은 팀입니다. 예를 들어:

- **수집 담당**: 이번에 바뀐 화면들의 HTML을 모아 한 폴더로 정리
- **자동 점검 담당**: 위 2단계 프롬프트를 고정 규칙으로 실행해 화면별 이슈 표 생성
- **검증 담당**: WCAG 항목 번호가 실제 지침과 맞는지 대조하고, "사람이 직접 테스트할 항목"을 체크리스트로 뽑아 담당자에게 배정
- **리포트 담당**: 지난 배포 대비 새로 생긴 이슈·해결된 이슈를 비교한 요약본 작성

이렇게 만들어 두면 배포 전마다 화면만 넣고 실행하면 같은 형식의 점검 리포트가 나오고, 사람은 "직접 테스트할 항목"에만 집중하면 됩니다. "매번 같은 기준으로, 같은 형식의 점검이 필요하다"가 반복될 때가 하네스로 만들 시점입니다.

*참고 동향: WCAG 2.2는 2025년 10월 국제표준(ISO/IEC 40500:2025)으로 채택되어 공공·조달 영역의 공식 기준이 되었습니다. 업계에서는 자동 점검(빠르게 다량 검출) + 사람 수동 점검(판단 필요 항목)을 함께 쓰는 하이브리드 방식을 권장하며, 이 사례의 "AI 1차 점검 → 사람 검토·실기 테스트" 흐름이 그 방식과 같습니다.
