# 카피 팀 하네스를 만들어 마이크로카피 시안 생성·톤 검수·비교표를 한 번에 돌리기

| 항목 | 내용 |
|------|------|
| 영역 | UX 라이팅 |
| 난이도 | 중급 |
| 소요 시간 | 구축 약 20분 + 실행 회당 약 8~12분 |
| 준비물 | ① 톤앤매너 가이드(우리 팀 문서 또는 아래 예시로 즉석 작성), ② 카피가 들어갈 화면 맥락 메모, ③ revfactory/harness 설치(아래 0단계) |
| 팀 패턴 | **Producer-Reviewer** — 시안을 "만드는 사람"과 규칙으로 "검수하는 사람"을 서로 다른 팀원으로 분리하는 구조. 만든 사람이 자기 글을 검수하면 무르게 넘어가기 때문에, 검수자를 떼어 놓는 것이 이 팀의 핵심입니다. |

## 이런 상황에서 쓰세요

버튼 라벨 하나, 에러 메시지 한 줄을 두고 반나절씩 고민한 적이 있을 겁니다. "결제 실패"라고만 띄우면 불친절하고, 길게 쓰면 버튼 안에 안 들어가고, 겨우 썼더니 다른 화면 말투와 안 맞습니다. 시안을 여러 개 뽑아 비교하고 싶은데 혼자 짜내면 3~4개에서 막히고, 팀 톤앤매너 가이드("사과는 하되 변명하지 않는다", "버튼은 동사로 시작한다" 같은 규칙)를 매번 하나하나 대조하는 것도 지치는 일입니다.

여기서 진짜 문제는 **한 사람(또는 한 번의 프롬프트)이 시안도 뽑고 검수도 하면, 자기가 뽑은 시안에 후하게 점수를 준다**는 점입니다. 그래서 이 사례는 시안을 뽑는 팀원과 규칙으로 깐깐하게 검수하는 팀원을 아예 분리합니다. 화면이 릴리스마다 계속 생기고, 매번 같은 톤 규칙으로 같은 형식의 검수표가 필요하다면 — 매번 프롬프트를 새로 붙여넣는 대신 이 작업을 하는 **작은 AI 팀(하네스)** 을 한 번 만들어 두고 반복 실행하는 편이 낫습니다.

## 팀 미리보기

하네스가 만들어 줄 팀은 이렇습니다:

| 팀원 | 역할 |
|------|------|
| copywriter (시안 생성 담당) | 화면 맥락을 받아, 서로 다른 결(정중·간결·친근·안심)로 마이크로카피 시안 N종(예시에서는 8종)을 뽑는다. **규칙 검수는 하지 않는다** — 오직 만들기만 한다. |
| tone-reviewer (톤 검수 담당) | `tone-guide.txt`의 규칙을 기준으로 각 시안이 규칙을 지켰는지 O/X로 판정하고, X면 어떤 규칙을 어겼는지 사유를 적는다. 생성 담당과 분리된 **독립 검수자**. |
| policy-flagger (정책 플래그 담당) | 환불·요금·법적 표현("요금이 청구되지 않습니다" 등)이 들어간 문장을 뽑아 "사람 확인 필요"로 표시한다. AI가 지어낸 정책 문구를 잡아내는 안전장치. |
| compiler (비교표 담당) | 검수 결과를 종합해 **대안 비교표**를 만들고, 규칙을 가장 잘 지킨 추천 시안 2종을 사유와 함께 뽑는다. |

앞의 둘(copywriter → tone-reviewer)이 Producer-Reviewer의 핵심 쌍이고, 뒤의 둘은 안전·정리를 돕는 보조입니다.

## 따라 하기

### 0단계: 하네스 설치 (처음 한 번만)

Claude Code(폴더 안 파일을 읽고 쓰는 AI 도구) 대화창에 아래 두 줄을 차례로 붙여넣습니다:

```
/plugin marketplace add revfactory/harness
/plugin install harness@harness-marketplace
```

이미 harness를 설치해 다른 사례를 해봤다면 이 단계는 건너뜁니다. (`/plugin`은 Claude Code에 기능을 추가하는 확장을 관리하는 명령입니다.) 플러그인 설치는 폴더와 무관하게 처음 한 번만 하면 되고, 어느 Claude Code 세션에서 해도 전체에 적용됩니다. Claude Code를 아직 켜지 않았다면 1단계 4번의 방법으로 먼저 켠 뒤 이 두 줄을 입력해도 됩니다.

### 1단계: 준비

1. 바탕화면이나 문서 폴더에 작업용 폴더를 하나 만듭니다. 예: `uxwriting-copyteam`
2. 그 폴더 안에 **톤앤매너 가이드**를 텍스트 파일로 저장합니다. 파일 이름은 `tone-guide.txt`. Windows는 메모장, Mac은 TextEdit(기본 텍스트편집기)을 씁니다. **주의:** Mac의 TextEdit은 기본값이 서식 있는 문서(.rtf)라 그대로 저장하면 `.txt`가 안 됩니다. 상단 메뉴 `서식 → 일반 텍스트로 만들기(Make Plain Text)`를 먼저 누른 뒤 저장하세요. 우리 팀 가이드가 있으면 핵심 규칙만 붙여넣고, 없으면 아래를 그대로 써도 됩니다:

   ```
   [우리 서비스 톤앤매너 규칙]
   1. 사용자를 탓하지 않는다. "잘못된 입력입니다"(X) → "이메일 형식을 다시 확인해 주세요"(O)
   2. 사과는 한 번, 짧게. 변명·기술 용어(서버, 세션, 토큰)는 쓰지 않는다.
   3. 버튼 라벨은 동사로 시작하고, 공백 제외 최대 6자. "확인"보다 "다시 시도" 선호.
   4. 다음에 뭘 하면 되는지 항상 알려준다(해결 행동 제시).
   5. 존댓말, 담백하게. 느낌표·이모지는 축하/성공 상황에서만.
   ```

3. 카피가 들어갈 **화면 맥락**을 한 문단으로 메모해 둡니다(파일로 저장하지 않고 실행할 때 바로 써도 됩니다). 예: "결제 단계에서 카드 한도 초과로 결제가 거절된 상황. 사용자는 장바구니로 돌아가거나 다른 카드로 재시도할 수 있음."
4. **1단계에서 만든 폴더 안에서** 터미널(명령어를 입력하는 검은 창)을 열고 `claude`를 입력해 Claude Code를 켭니다. 이 폴더 안에서 켜야 뒤에서 만든 팀이 `tone-guide.txt`를 찾을 수 있습니다.
   - **macOS**: Spotlight(⌘+Space)에 `terminal`을 입력해 터미널(검은 명령어 입력 창)을 엽니다 → 창에 `cd `를 입력하고 한 칸 띄운 뒤, 만든 폴더를 터미널 창 안으로 드래그하면 경로가 자동 입력됩니다 → Enter → `claude` 입력 후 Enter를 누르면 Claude Code가 켜집니다. (Finder 우클릭 → 서비스 → '폴더에서 새로운 터미널 열기' 메뉴가 보인다면 그걸 써도 됩니다 — 단, 이 메뉴는 기본값으로 꺼져 있는 Mac이 많습니다.)
   - **Windows:** 폴더를 연 상태에서 위쪽 주소창을 클릭해 글자를 지우고 `cmd`를 입력한 뒤 Enter.

### 2단계: 팀 구성 (바이브코딩)

이 단계가 사례의 심장입니다. **코드를 쓰는 게 아니라, 원하는 팀을 말로 설명하면** 하네스가 팀을 만들어 줍니다. 아래를 **그대로 복사해 붙여넣으세요** — 그대로도 동작합니다. 톤 가이드 파일명(`tone-guide.txt`)이나 시안 개수(8종)를 바꾸고 싶다면 그 부분만 고치면 됩니다:

```
하네스 구성해줘: UX 라이팅 카피 팀이 필요해.

같은 폴더의 tone-guide.txt(우리 서비스 톤앤매너 규칙)와 내가 주는 화면 맥락을 입력으로 받아,
다음 순서로 일하는 팀으로 만들어줘.

1) 시안 생성 담당: 화면 맥락을 받아 마이크로카피 시안 8종을 뽑는다.
   각 시안은 (제목 한 줄 / 본문 한 줄 / 버튼 라벨 1~2개)로 구성하고,
   서로 다른 결로 뽑는다 — 정중함 2 / 간결함 2 / 친근함 2 / 안심 2. 이 담당은 검수는 하지 않는다.
2) 톤 검수 담당: tone-guide.txt의 규칙 1~5를 기준으로 각 시안을 O/X로 판정하고,
   X면 어긴 규칙과 사유를 한 줄로 적는다. 생성 담당과 반드시 분리된 독립 검수자로 만들어줘.
3) 정책 플래그 담당: 환불·요금·법적 표현이 들어간 문장을 뽑아 "사람 확인 필요"로 표시한다.
   없는 사실(고객센터 번호, 환불 정책 등)은 지어내지 말고 [대괄호] 자리로 남기게 한다.
4) 비교표 담당: 검수 결과를 종합해 시안 대안 비교표(마크다운)를 만들고,
   규칙을 가장 잘 지킨 추천 2종을 사유와 함께 뽑아 파일로 저장한다.

생성과 검수를 분리하는 Producer-Reviewer 구조로 만들고, 결과는 마크다운 표로 저장해줘.
```

잠시 후 프로젝트 폴더 안 `.claude/agents/` 폴더에 팀원 파일들(예: `copywriter.md`, `tone-reviewer.md`, `policy-flagger.md`, `compiler.md`)이, `.claude/skills/`에 팀의 작업 방법과 이들을 순서대로 부르는 오케스트레이터(팀을 지휘하는 스킬)가 생깁니다. 하네스는 마지막에 "이런 팀을 만들었고, 이 문구로 실행하세요"라는 요약을 보여 줍니다 — **그 요약의 실행 문구를 그대로 다음 단계에 씁니다.** ("에이전트"는 하나의 역할을 맡은 AI 팀원, "스킬"은 그 팀원이 따르는 작업 지침서라고 보면 됩니다.)

### 3단계: 팀 실행

새 작업을 시킬 때는 하네스가 알려준 트리거 문구(예: 아래)를 대화창에 붙여넣습니다:

```
카피 팀 실행해줘. 화면 맥락은 이거야:
결제 단계에서 카드 한도 초과로 결제가 거절된 상황. 사용자는 장바구니로 돌아가거나 다른 카드로 재시도할 수 있음.
```

그러면 시안 생성 담당이 8종을 뽑고 → 톤 검수 담당이 규칙으로 대조하고 → 정책 플래그 담당이 위험 문장을 표시하고 → 비교표 담당이 정리합니다. 이런 식의 결과가 나옵니다(실제로는 8종·규칙 5개 열이 모두 나오지만, 아래는 **8종 중 4종, 규칙 열 일부(1·3·4)만 발췌**한 예시입니다):

| # | 결 | 제목 | 본문 | 버튼 | 규칙1 안탓하기 | 규칙3 동사·6자 | 규칙4 다음행동 |
|---|-----|------|------|------|:---:|:---:|:---:|
| 1 | 정중함 | 결제가 완료되지 않았어요 | 카드 한도를 초과한 것 같아요. 다른 카드로 다시 시도해 주세요. | 다시 시도 / 장바구니로 | O | O* | O |
| 2 | 간결함 | 결제 거절됨 | 다른 결제 수단을 이용해 주세요. | 다시 시도 | O | O | O |
| 3 | 친근함 | 앗, 결제가 막혔네요 | 카드 한도를 확인하거나 다른 카드로 결제해 볼까요? | 다시 시도 | O | O | O |
| 4 | 안심 | 아직 결제되지 않았어요 | 요금은 청구되지 않았으니 안심하세요. 다른 카드로 진행할 수 있어요. | 다른 카드로 | O | △ AI는 7자로 셈 | O |

> \* 1행 규칙3의 O는 버튼 두 개 중 하나만 기준으로 느슨하게 통과시킨 예입니다. "다시 시도"는 동사 시작·6자 조건을 모두 지키지만, "장바구니로"는 동사로 시작하지 않는 목적지 표현이라 엄격히는 위반입니다. 검수 담당이 버튼 하나라도 지키면 O로 판정한 사례로 보시면 됩니다.

> **정책 플래그 담당의 표시**
> - #4 본문 "요금은 청구되지 않았으니" → **사람 확인 필요**: 실제 결제 로직상 승인 거절 시 청구가 잡히지 않는지 개발/정책 담당 확인 요망.

> **비교표 담당의 추천 2종**
> - **#1 (정중함)**: 규칙 1·2·4·5를 지킵니다. 버튼 "장바구니로"는 글자 수는 통과하지만 동사로 시작하지 않는 목적지 표현입니다 — 엄격히 지키려면 "장바구니 담기"로.
> - **#4 (안심)**: "요금은 청구되지 않았다"는 안심 문구가 결제 실패의 불안을 크게 줄입니다. 단 정책 플래그가 붙은 문장이라, 사실 확인 전에는 확정하지 마세요.

위 표 4번 행의 **△ 표시는 일부러 남긴 함정**입니다. 톤 검수 담당은 버튼 "다른 카드로"를 "7자라 규칙 위반(△)"으로 판정했지만, 직접 세어 보면 공백 제외 5자(다·른·카·드·로)로 **글자 수 조건은 지킵니다.** AI가 한글 글자 수를 잘못 센 예입니다. 규칙 3이 공백 포함인지 제외인지를 `tone-guide.txt`에 못박아 두면 이런 혼선이 줄어듭니다("꼭 사람이 확인하세요" 첫 항목과 이어집니다). 참고로 "다른 카드로"는 관형사 "다른"으로 시작해 **동사 시작 조건도 별도로 위반**합니다 — 규칙3은 "동사로 시작" + "공백 제외 6자" 두 조건을 모두 지켜야 O이므로, 글자 수만 맞다고 O가 되는 건 아닙니다.

**Producer-Reviewer가 왜 유리한가:** 시안 생성 담당은 "잘 뽑는 것"에만, 톤 검수 담당은 "규칙 위반을 잡는 것"에만 집중합니다. 한 번의 프롬프트로 생성과 검수를 함께 시키면 AI가 자기 시안에 후한 점수를 주는 경향이 있는데, 역할을 나누면 검수자가 더 깐깐하게 X를 답니다.

### 4단계: 팀 다듬기 (진화)

결과가 아쉬운 부분은 팀에게 말로 피드백합니다. 아래처럼 대화창에 입력하면 팀원 정의가 수정되어 **다음 실행부터** 반영됩니다:

- `하네스 회고: 톤 검수 담당이 버튼 글자 수를 자꾸 틀려. 규칙3은 "공백 제외 6자"라는 걸 못박고, 글자 수를 셀 때 각 글자를 하나씩 나열해서 세도록 검수 담당을 고쳐줘.`
- `하네스 회고: 검수 담당이 "동사로 시작"을 느슨하게 봐. "장바구니로"처럼 조사 '로/으로'로 끝나는 목적지 표현은 동사 시작이 아니라고 명확히 판정하게 규칙을 강화해줘.`
- `하네스 회고: 비교표에 "지난 릴리스에 쓴 카피와 말투가 다른 곳"을 표시하는 일관성 검수 담당을 한 명 추가해줘.`

**구축은 1회, 실행은 매번** — 다음 화면(온보딩, 빈 화면 안내 등)이 생기면 3단계 실행 문구의 화면 맥락 한 줄만 바꿔 다시 돌리면 같은 형식의 시안 세트와 검수표가 나옵니다.

## 꼭 사람이 확인하세요

- **규칙 준수 O/X 판정을 그대로 믿지 마세요.** 톤 검수 담당도 결국 AI라, "이 정도면 동사"라고 느슨하게 보거나 한글 글자 수를 잘못 셉니다(위 △ 사례). 추천 시안만이라도 버튼 글자 수를 직접 세고, "탓하지 않는가"는 사람 감각으로 다시 읽으세요. Producer-Reviewer 구조는 검수를 **더 잘하게** 하지만 **완벽하게** 하지는 못합니다.
- **브랜드 뉘앙스는 AI가 놓칩니다.** "친근함"을 지시하면 반말·과한 이모지·유행어로 흐를 수 있는데, 우리 브랜드엔 안 맞을 수 있습니다. 결(정중/친근 등)은 방향 참고용이고, 최종 선택은 "이게 우리 서비스다운가"로 사람이 판단하세요.
- **법적·정책 문구는 반드시 검증하세요.** "요금은 청구되지 않았어요", "환불됩니다" 같은 문장은 실제 결제/환불 로직과 다르면 큰 문제가 됩니다. 정책 플래그 담당이 뽑아 준 "사람 확인 필요" 항목은 개발·정책 담당과 반드시 대조하세요. AI가 없는 정책을 지어내지 않았는지도 살피세요(프롬프트에서 대괄호 자리로 남기게 한 이유입니다).
- **접근성·번역을 잊지 마세요.** 화면에 예쁘게 들어가도 스크린리더로 읽으면 어색하거나, 영어로 번역하면 버튼이 길어질 수 있습니다. 다국어 서비스라면 시안 확정 전에 번역 길이도 가늠하세요.
- **N종을 다 쓰려 하지 마세요.** 8종은 고르기 위한 재료입니다. 최종은 1~2개로 좁히고, 가능하면 A/B 테스트로 실제 사용자 반응을 확인하는 것이 정석입니다.

## 하네스가 과한 경우

지금 딱 한 화면의 에러 메시지 한 줄만 급하게 필요하다면, 팀을 만들 것 없이 프롬프트 한 번이면 충분합니다:

```
tone-guide.txt를 읽고, "결제 한도 초과로 거절된 상황"의 에러 메시지 시안 5종을 결별로 뽑아
규칙 1~5 준수 여부를 표로 대조하고 추천 2개를 골라줘.
```

**판단 기준은 반복성입니다.** 같은 톤 규칙으로, 같은 형식의 검수표가 화면마다·릴리스마다 계속 필요하다면 그때가 하네스로 승격할 시점입니다. 한 번 쓰고 말 카피에 팀을 짜는 건 배보다 배꼽이 큽니다.

## 한 걸음 더

- **일관성 검수관 추가(중급→심화):** 지난 릴리스 카피 모음(`past-copy.txt`)을 하나 넣어 두고, "같은 상황인데 말투가 다른 곳"을 찾는 팀원을 추가하면, 화면 간 톤이 따로 노는 문제까지 잡습니다(4단계 세 번째 회고 예시).
- **가이드 자체를 자산으로:** 톤 검수 담당의 품질은 `tone-guide.txt`가 얼마나 명확한지에 좌우됩니다. 규칙이 애매하면(공백 포함/제외, 동사 시작의 정의) 검수도 흔들립니다 — 가이드를 또렷하게 다듬는 것이 이 하네스의 사전 투자입니다.
- **가까운 하네스에서 출발:** 처음부터 만들기 부담스러우면 [revfactory/harness-100](https://github.com/revfactory/harness-100)(10개 도메인 100개 팀 하네스)에서 UX 라이팅에 가까운 팀을 설치해 수정하는 방법도 있습니다.

> 참고: 하네스 도입 효과에 관한 저자 측정 A/B 연구([revfactory/claude-code-harness](https://github.com/revfactory/claude-code-harness), n=15)에서는 품질 점수 49.5 → 79.3(+60%), 분산 −32%로 보고되었습니다(저자 측정, 소표본 — 참고치로만).
