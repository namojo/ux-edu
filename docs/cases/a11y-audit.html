접근성 점검 팀을 만들어 릴리스마다 WCAG 점검 자동화하기

따라 하기릴리스마다 화면 접근성을 점검할 때
항목 내용
영역 접근성 점검 (a11y-audit)
난이도 중급
소요 시간 구축 약 30분(처음 한 번) + 실행 회당 약 15분
준비물 점검할 화면의 HTML 파일들(또는 화면을 글로 자세히 적은 설명 파일), revfactory/harness 설치(아래 0단계)
팀 패턴 Pipeline(순차) + Producer-Reviewer(생성-검증) 결합 — 스캔 → 판정 → 개선안을 순서대로 넘기고, 마지막에 검증 담당이 판정을 되짚고 재검 체크리스트를 만드는 구조

a11y는 "accessibility(접근성)"를 줄여 부르는 업계 표기입니다. a와 y 사이 글자가 11개라 a11y로 씁니다. WCAG(웹 콘텐츠 접근성 지침)는 장애가 있는 사용자도 웹을 쓸 수 있게 하는 국제 표준입니다.

이런 상황에서 쓰세요

릴리스(배포)가 한 번 나갈 때마다 바뀐 화면들의 접근성을 다시 점검해야 합니다. 색 대비, 대체 텍스트, 폼 라벨, 키보드 이동… 체크리스트는 길고 용어는 어렵고, 매번 같은 걸 처음부터 손으로 훑습니다. 전문 감리를 맡기면 화면 10~20개에 2~4주가 걸리고 비용도 큽니다. 그렇다고 넘기면 "스크린리더로 결제가 안 된다"는 민원이 나중에 들어옵니다.

이게 매 릴리스마다 반복된다면, 매번 프롬프트를 새로 쓰는 대신 점검을 대신 돌려 줄 작은 AI 팀(하네스) 을 한 번 만들어 두는 게 낫습니다. 다음 릴리스부터는 바뀐 화면 파일만 폴더에 넣고 "점검 실행"이라고 말하면, 늘 같은 기준·같은 형식의 리포트가 나옵니다. 사람은 처음부터 다 뒤지는 대신, AI가 짚어준 곳과 "사람이 직접 테스트할 항목"에만 집중합니다.

팀 미리보기

하네스가 만들어 줄 팀은 이렇습니다:

팀원 역할
스캐너 폴더 안 화면 HTML(또는 설명 파일)을 읽어, 이미지·버튼·입력칸·색 등 접근성과 관련된 요소를 요소별로 뽑아 정리
WCAG 판정관 뽑힌 요소를 WCAG 2.2 AA 기준으로 대조해 위반 의심 항목과 심각도(높음/중간/낮음)를 판정
개선안 작성 위반마다 "고치기 전 → 고친 후" 개선안을 작성. 코드가 있으면 코드로, 없으면 말로
검증·재검 담당(verifier) 판정관이 붙인 WCAG 항목 번호가 실제 지침과 맞는지 대조하고, "기계로는 판정 못 해 사람이 직접 테스트해야 하는 항목"을 체크리스트로 뽑음. 개선 후 다시 넣으면 해결/미해결을 재검

왜 검증 담당이 따로 있나요: AI는 문제는 맞게 짚어도 "1.4.3"을 "1.4.11"로 잘못 붙이는 실수(환각)를 합니다. 판정하는 AI와 되짚는 AI를 나누면 이런 실수를 서로 걸러 냅니다. 이게 Producer-Reviewer(생성-검증) 패턴입니다.

따라 하기

0단계: 하네스 설치 확인 (처음 한 번만)

이 사례는 revfactory/harness가 설치되어 있어야 합니다. 설치는 전체 사례집을 통틀어 처음 한 번만 하면 됩니다 — 아직이라면 하네스 설치 안내를 따라 하세요 (약 2분).

  • 설치 확인: Claude Code 대화창에 /plugin을 입력해 목록에 harness가 보이면 준비 완료. 이미 설치했다면 바로 1단계로 넘어갑니다.

1단계: 준비

점검할 화면을 파일로 폴더 하나에 모읍니다.

  1. 바탕화면이나 문서 폴더에 작업용 폴더를 만듭니다. 예: a11y-점검-2026-08릴리스
  2. 그 안에 screens라는 하위 폴더를 만들고, 이번에 바뀐 화면의 HTML 파일들을 넣습니다. 개발자에게 "이번 릴리스에 바뀐 화면 HTML 파일들만 주세요"라고 요청하는 게 가장 정확합니다.

HTML을 받기 어렵다면(시안·화면만 있을 때): 화면을 글로 자세히 묘사한 설명을 checkout.txt 같은 텍스트 파일로 저장해 screens 폴더에 넣습니다. 예: "상단에 로고 이미지, 그 아래 '주문하기' 파란 버튼(글자 흰색), 이메일 입력칸에는 라벨 없이 회색 안내문구만 있음, 하단에 빨간 글씨로 에러 표시…" 처럼 색·순서·이미지·버튼을 있는 그대로 적습니다.

HTML이 더 정확합니다(권장). HTML에는 눈에 안 보이는 정보(대체 텍스트, 라벨 연결 등)가 들어 있어 AI가 훨씬 정확하게 봅니다. 설명 파일은 사람 눈에 보인 것만 적히므로 놓치는 게 많습니다. 저장 시 주의: 윈도우 메모장은 저장할 때 '파일 형식'을 '모든 파일(*.*)'로 바꿔야 checkout.txt.txt가 되지 않습니다. 헷갈리면 개발자에게 파일을 직접 받는 편이 안전합니다.

  1. 폴더 안에서 Claude Code를 켭니다. 터미널(명령어를 입력하는 검은 창)에서 켜는데, "만든 폴더 안에서" 열어야 AI가 그 파일들을 찾습니다. - macOS: Spotlight(⌘+Space)에 terminal을 입력해 터미널을 엽니다 → 창에 cd를 입력하고 한 칸 띄운 뒤, 만든 폴더를 터미널 창 안으로 드래그하면 경로가 자동 입력됩니다 → Enter → claude 입력 후 Enter를 누르면 켜집니다. (Finder 우클릭 → 서비스 → '폴더에서 새로운 터미널 열기' 메뉴가 보인다면 그걸 써도 됩니다 — 단, 이 메뉴는 기본값으로 꺼져 있는 Mac이 많습니다.) - Windows: 만든 폴더를 파일 탐색기에서 열고, 폴더 안 빈 공간에서 마우스 오른쪽 클릭 → "터미널에서 열기"를 고릅니다. 그 창에 claude라고 입력하고 Enter를 누르면 켜집니다.

2단계: 팀 구성 (바이브코딩)

아래를 그대로 복사해 붙여넣으세요. (폴더명을 screens가 아닌 다른 이름으로 만들었다면 그 이름만 바꾸세요.)

복사해서 쓰세요
하네스 구성해줘: 릴리스마다 반복되는 웹 접근성 점검을 대신 돌릴 접근성 점검 팀이 필요해.
screens 폴더 안의 화면 HTML(또는 화면을 글로 묘사한 설명 파일)을 입력하면 이렇게 일하는 팀으로 만들어줘:

1) 스캐너: 폴더 안 화면들을 읽어, 이미지·버튼·입력칸·색 대비·라벨 등 접근성 관련 요소를 화면별로 뽑아 정리.
2) WCAG 판정관: 뽑힌 요소를 WCAG 2.2 AA 기준으로 대조해, 위반 의심 항목을 표로 만들어줘.
   각 행에 (a) 문제 요약 (b) 관련 화면 요소(어떤 버튼/이미지/입력칸인지 구체적으로)
   (c) 의심되는 WCAG 항목 번호와 이름 (d) 심각도(높음/중간/낮음) (e) 개선안 한 줄.
   심각도는 "이 문제로 특정 사용자가 그 기능을 아예 못 쓰는가"로 매기고, 결제·로그인 같은 핵심 동작을 막으면 높음. 높음부터 정렬.
3) 개선안 작성: 심각도 높음·중간 항목에서 "고치기 전 → 고친 후" 예시를 만들어줘. HTML이면 코드로, 설명 파일이면 말로.
4) 검증·재검 담당: WCAG 항목 번호가 실제 지침과 맞는지 대조하고, 기계로는 판정 못 해 사람이 직접 테스트해야 하는 항목(초점 순서, 키보드 통과, 확대 시 깨짐, 스크린리더 낭독 등)을 체크리스트로 따로 뽑아줘.

규칙: HTML/설명에 실제로 없는 문제는 지어내지 마. 애매하면 '확인 필요'로 표시하고 왜 애매한지 적어줘.
결과는 화면별 리포트 하나로 묶어 마크다운 파일로 저장해줘. 다음 릴리스 때 이전 결과와 비교할 수 있게.

잠시 후 .claude/agents/ 폴더에 팀원 파일들(스캐너·판정관·개선안·검증 담당)이, .claude/skills/에 팀의 작업 방법과 실행 방법(오케스트레이터)이 생깁니다.

폴더가 생겼는지 직접 확인할 필요는 없습니다. 하네스가 마지막에 "이런 팀을 만들었고, 이렇게 실행하세요" 라는 요약과 실행용 문구를 보여 줍니다. 그 문구를 다음 단계에서 쓰면 됩니다.

3단계: 팀 실행

새 대화에서 하네스가 알려 준 실행 문구(예: 접근성 점검 실행해줘)를 입력하면 팀이 순서대로 일합니다. 이런 식의 결과가 나옵니다(내용은 예시입니다):

checkout.html — 위반 표 (심각도 높은 순)

심각도 문제 요약 관련 요소 WCAG 항목 개선안
높음 이메일 입력칸에 라벨이 없어 스크린리더가 무엇을 입력하는 칸인지 못 읽음 <input type="email"> (placeholder만 있음) 1.3.1 정보와 관계, 4.1.2 이름·역할·값 <label> 연결 또는 aria-label 추가
높음 '주문하기' 버튼의 글자·배경 대비 부족(저시력 사용자가 못 읽음) 파란(#5B9BD5) 배경 + 흰 글자, 약 2.9:1 1.4.3 명암 대비(AA는 4.5:1 이상) 배경을 더 진한 파랑(#1F5FA8 등)으로
중간 로고 이미지 대체 텍스트가 비어 있음 <img src="logo.png" alt=""> 1.1.1 비텍스트 콘텐츠 alt="OO몰 홈" 등 의미 있는 대체 텍스트
중간 에러를 빨간색으로만 표시(색 구분 못 하는 사용자가 놓침) "필수 항목입니다" 빨간 글씨 1.4.1 색의 사용 아이콘/"오류:" 텍스트를 함께 표시

ARIA: 화면 요소의 이름·역할을 스크린리더(화면 내용을 소리로 읽어 주는 보조 프로그램)에 알려 주기 위해 HTML에 다는 보조 표시입니다(예: aria-label). placeholder: 입력칸 안에 흐리게 보이다 입력하면 사라지는 안내 문구입니다. 위 표의 위반 사례처럼, placeholder만으로는 라벨을 대신하지 못합니다.

개선안 예시(고치기 전 → 고친 후)

복사해서 쓰세요
[고치기 전]
<input type="email" placeholder="이메일">

[고친 후]
<label for="email">이메일</label>
<input type="email" id="email" placeholder="예: name@mail.com">

검증·재검 담당이 뽑은 "사람이 직접 테스트할 항목" 체크리스트

  • [ ] 키보드 Tab 키만으로 결제까지 끝까지 이동되는지(초점 순서는 실제로 눌러봐야 확인)
  • [ ] 화면을 200% 확대했을 때 버튼·글자가 잘리거나 겹치지 않는지
  • [ ] 대체 텍스트가 "의미 있게" 쓰였는지(문법상 채워져 있어도 내용이 엉뚱할 수 있음)
  • [ ] 실제 스크린리더(NVDA/보이스오버)로 핵심 플로우를 읽었을 때 자연스러운지

WCAG 항목 번호 대조 결과: 위 4건 모두 항목 번호·이름이 지침과 일치함을 확인.

그리고 화면별 리포트가 하나의 마크다운 파일(.md — 표·제목을 기호로 표현한 텍스트 파일)로 저장됩니다. 개발·디자인 팀에 그대로 공유하거나 다음 릴리스 때 비교할 수 있습니다.

4단계: 팀 다듬기 (진화)

결과가 아쉬운 부분은 팀에게 말로 피드백합니다:

  • 하네스 회고: 리포트에 심각도 '낮음'이 너무 많아 핵심이 묻혀. 낮음은 표 맨 아래 접힌 목록으로 몰고, 맨 위에 '이번 릴리스에서 먼저 고칠 3가지'를 요약으로 넣게 개선해줘.
  • 하네스 회고: 검증 담당이 지난 릴리스 리포트와 비교해서 '새로 생긴 이슈 / 해결된 이슈 / 그대로인 이슈'를 표로 보여주게 해줘.

다음 실행부터 반영됩니다. 구축은 1회, 실행은 매번 — 다음 릴리스에는 screens 폴더의 파일만 새것으로 바꿔 넣고 실행하면 같은 형식의 리포트가 나옵니다.

꼭 사람이 확인하세요

  • AI 자동 점검은 위반의 25~40%만 잡습니다. 잘 잡는 건 색 대비, 라벨 누락, 대체 텍스트 유무처럼 "기계가 규칙으로 판정 가능한" 문제입니다. 반대로 초점(포커스) 순서, 키보드만으로 끝까지 되는지, 확대 시 깨짐, 스크린리더 낭독의 자연스러움 같은 판단이 필요한 항목은 사람이 실제로 조작해봐야 합니다. 이 팀의 검증 담당이 뽑아 주는 "사람이 직접 테스트할 항목" 체크리스트를 반드시 사람이 소화하세요. AI 리포트는 "출발점"이지 "합격증"이 아닙니다.
  • WCAG 항목 번호를 그대로 믿지 말고 대조하세요. 검증 담당이 1차로 걸러 주지만, 보고서를 외부에 낼 때는 번호·이름이 W3C WCAG 2.2 공식 문서와 맞는지 사람이 한 번 더 확인하세요.
  • 대체 텍스트는 "채워졌는지"와 "제대로인지"가 다릅니다. AI는 alt가 비었다는 건 잘 잡지만 alt="이미지"처럼 채워졌으나 무의미한 경우는 통과로 볼 수 있습니다. 이미지가 실제로 전달해야 할 의미는 사람이 판단합니다.
  • 설명 파일 기반 결과는 놓친 게 많습니다. 코드 속 문제(라벨 연결, ARIA 속성 등)는 설명에 안 적히면 AI도 모릅니다. "눈에 보이는 수준의 1차 점검"으로만 쓰세요.
  • 자바스크립트로 그려지는 화면 주의. 결제·로그인 화면은 "페이지 소스 보기"로 나오는 원본 HTML이 실제 화면과 다를 수 있습니다. 가능하면 개발자에게 실제로 그려진 HTML을 받으세요.

하네스가 과한 경우

화면 한두 개를 딱 한 번 점검하는 상황이라면 팀을 만들 필요가 없습니다. Claude Code 대화창에 파일을 두고 이렇게 한 번 물어보는 걸로 충분합니다:

복사해서 쓰세요
checkout.html을 WCAG 2.2 AA로 접근성 점검해줘. 문제를 (요소·WCAG 번호·심각도·개선안) 표로 정리하고,
사람이 직접 테스트해야 할 항목은 따로 목록으로 적어줘. HTML에 없는 문제는 지어내지 마.

판단 기준은 반복성입니다. "매 릴리스마다, 같은 기준으로, 같은 형식의 리포트가 필요한가?"가 예스일 때가 하네스로 만들 시점입니다. 하네스의 이득은 구축 1회 뒤의 반복 실행에서 나옵니다.

한 걸음 더

  • 수집 담당 추가: 지금은 사람이 바뀐 화면을 screens 폴더에 넣지만, "이번 릴리스에서 바뀐 화면 목록을 받아 HTML을 모아 오는" 수집 담당을 팀에 더하면 준비 단계까지 팀이 맡습니다.
  • 팀 협업 모드(심화): 기본은 팀원에게 일을 하나씩 맡기는 방식(Subagents)입니다. 팀원들이 실시간으로 주고받으며 일하게 하려면 Agent Teams 모드(CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 환경 설정)를 쓸 수 있습니다 — 재검이 잦은 큰 릴리스에서 유용합니다.
  • 미리 만들어진 하네스에서 출발: 처음부터 만들지 않고 revfactory/harness-100(10개 도메인 100개 팀 하네스)에서 가까운 것을 설치해 고쳐 쓰는 방법도 있습니다.

참고 동향: WCAG 2.2는 2025년 10월 국제표준(ISO/IEC 40500:2025)으로 채택되어 공공·조달의 공식 기준이 되었습니다. 업계는 자동 점검(빠르게 다량 검출) + 사람 수동 점검(판단 필요 항목)을 함께 쓰는 하이브리드를 권장하며, 자동 점검이 잡는 위반은 전체의 25~40% 수준으로 봅니다. 이 사례의 "AI 팀 1차 점검 → 사람 검토·실기 테스트" 흐름이 그 방식과 같습니다.
