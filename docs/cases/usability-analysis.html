사용성 테스트 분석 팀을 만들어 라운드마다 이슈·심각도 리포트 자동화하기

따라 하기라운드마다 세션 노트를 이슈·심각도 리포트로 만들 때
항목 내용
영역 사용성 테스트 분석
난이도 중급
소요 시간 구축 약 20분(처음 한 번) + 실행 회당 약 10~15분
준비물 참가자별 세션 노트 + 태스크 성공/실패 기록을 모은 텍스트 파일 1개, revfactory/harness 설치(아래 0단계)
팀 패턴 Pipeline(정리→추출→판정→리포트로 순차 진행) + 그 안에 Producer-Reviewer(생성물을 검증 담당이 대조) 한 명 배치

이런 상황에서 쓰세요

사용성 테스트를 5~8명 돌리고 나면 참가자별 관찰 노트가 수십 장 쌓입니다. "3번 참가자는 결제 버튼을 못 찾아 헤맸고, 5번은 쿠폰 입력창을 배송지로 착각했고…" 머릿속엔 다 있는데, 이걸 이슈 목록으로 합치고 "무엇부터 고쳐야 하는지" 심각도를 매겨 팀에 공유하려면 하루가 통째로 날아갑니다.

문제는 이게 한 번이 아니라는 것입니다. 스프린트마다, 라운드마다 똑같은 정리 작업이 반복됩니다. 그때마다 정리 기준·심각도 기준이 사람 컨디션 따라 흔들리면 라운드 간 비교(지난번에 고친 게 정말 나아졌나?)도 어긋납니다. 이럴 때가 바로 프롬프트 한 번이 아니라 일하는 팀 하나(하네스) 를 만들어 둘 시점입니다. 한 번 만들어 두면 다음 라운드에는 노트 파일만 바꿔 넣고 실행 버튼 격인 문장 하나만 치면 됩니다.

팀 미리보기

하네스(자연어로 설명하면 AI가 만들어 주는 '에이전트 팀' — 역할이 나뉜 여러 AI가 순서대로 일합니다)가 만들어 줄 팀은 이렇습니다:

팀원 역할
정리 담당 (organizer) 뒤죽박죽인 참가자별 노트를 표준 형식(참가자 코드·태스크·성공여부·소요시간·관찰)으로 재구성
이슈 추출 담당 (extractor) 노트 전체에서 사용성 이슈를 뽑고, 같은 문제를 하나로 병합하며, 몇 명·누구에게서 나왔는지 집계
심각도 판정 담당 (rater) 각 이슈에 Nielsen 심각도(0~4)를 매기고 근거(실패였는지·몇 명인지)를 한 줄로 기록
검증 담당 (verifier) 인용문이 원문에 실제로 있는지, 참가자 수 집계가 맞는지 대조하고 개인정보가 남았는지 점검 — 이 팀의 안전장치
리포트 담당 (reporter) 우선순위 표 + 태스크별 성공률 + (있다면) 지난 라운드 대비 변화를 강조한 리포트 작성

핵심은 검증 담당입니다. AI가 인용을 그럴듯하게 지어내거나(환각) 참가자 수를 잘못 뭉치는 실수를, 리포트가 나가기 전에 팀 안에서 한 번 걸러 줍니다.

따라 하기

0단계: 하네스 설치 확인 (처음 한 번만)

이 사례는 revfactory/harness가 설치되어 있어야 합니다. 설치는 전체 사례집을 통틀어 처음 한 번만 하면 됩니다 — 아직이라면 하네스 설치 안내를 따라 하세요 (약 2분).

  • 설치 확인: Claude Code 대화창에 /plugin을 입력해 목록에 harness가 보이면 준비 완료. 이미 설치했다면 바로 1단계로 넘어갑니다.

1단계: 준비

세션 기록을 하나의 텍스트 파일로 모읍니다.

  1. 바탕화면이나 문서 폴더에 작업용 폴더를 하나 만듭니다. 예: usability-2026-07
  2. 참가자별 노트를 그 폴더 안에 sessions.txt(메모장/텍스트편집기로 만든 파일)로 저장합니다. 형식은 자유지만 참가자를 구분할 수 있게, 그리고 태스크 성공/실패와 소요 시간을 같이 적어 둡니다. 이게 심각도 근거의 핵심 재료입니다. 예: ``` [P1 / 40대 / 첫 구매] 태스크1(상품검색) 성공 / 45초 태스크2(장바구니 담기) 성공 / 20초 태스크3(쿠폰 적용 후 결제) 실패 — 쿠폰 입력창을 배송 메모칸으로 착각, 결국 쿠폰 없이 결제 관찰: "할인칸이 어디 있지?"라고 세 번 중얼거림. 결제 버튼이 스크롤 아래 있어 못 봄.

[P2 / 30대 / 재구매] 태스크3 성공 / 90초(오래 걸림) 관찰: 쿠폰은 찾았으나 적용 후 금액이 안 바뀌어 두 번 재시도 `` 3. 터미널을 열고 그 폴더로 이동한 뒤claude를 입력해 Claude Code를 켭니다. - **폴더로 이동 (Mac)**: 터미널에cd를 치고 한 칸 띄운 다음, 만든 폴더를 터미널 창에 끌어다 놓으면(드래그&드롭) 경로가 자동 입력됩니다. Enter를 누르면 이동 완료. (cd는 "이 폴더로 들어가라"는 명령입니다.) - **폴더로 이동 (Windows)**: 탐색기에서 만든 폴더를 연 뒤 주소창을 클릭해cmd를 입력하고 Enter 하면 그 폴더에서 터미널이 바로 열립니다. 이어서claude` 입력.

개인정보 주의: 노트에 참가자 실명·연락처가 있다면 P1, P2 같은 익명 코드로 바꾼 뒤 저장하세요. 이유는 아래 "꼭 사람이 확인하세요"에서 다시 짚습니다.

2단계: 팀 구성 (바이브코딩)

바이브코딩(vibe coding) = 코드를 직접 타이핑하지 않고, 원하는 팀·기능을 말로 설명하면 AI가 대신 만들어 주는 방식입니다. 아래처럼 팀을 글로 설계해 그대로 붙여넣기만 하면 됩니다. 세션 노트 파일명(sessions.txt)을 다르게 지었다면 그 이름만 고치세요:

복사해서 쓰세요
하네스 구성해줘: 사용성 테스트 세션 노트를 분석하는 "테스트 분석 팀"이 필요해.

참가자별 세션 노트 텍스트 파일(sessions.txt)을 입력하면, 팀이 이 순서로 일하는 구조로 만들어줘:
1) 정리 담당 — 뒤죽박죽인 노트를 참가자 코드·태스크·성공여부·소요시간·관찰의 표준 형식으로 재구성
2) 이슈 추출 담당 — 사용성 이슈를 뽑아 목록화. 같은 문제는 하나로 병합하고, 몇 명·누구에게서 관찰됐는지 집계
3) 심각도 판정 담당 — 각 이슈에 Nielsen 심각도(0~4: 4=재앙 반드시 출시 전 수정 / 3=심각 우선 수정 / 2=경미 / 1=미관 수준 / 0=문제 아님)를 매기고, 근거(실패였는지·지연이었는지·몇 명인지)를 한 줄로 기록. 단일 관찰(1명)은 '단일 관찰'로 표시하고 신중히 판정. 애매하면 '판정 보류'로 분리
4) 검증 담당 — 대표 인용문이 원문에 실제로 있는지, 참가자 수 집계가 맞는지 원문과 대조하고, 참가자 실명·연락처 같은 개인정보가 남았는지 점검
5) 리포트 담당 — 심각도 높은 순 → 같으면 관찰 참가자 수 많은 순으로 정렬한 우선순위 표 + 태스크별 성공률 + (지난 라운드 파일이 있으면) 재발/신규 이슈 비교를 담은 마크다운 리포트 작성

절대 노트에 없는 내용을 지어내지 않는 규칙, 심각도는 'AI 초안이며 사람 확정 필요'라고 리포트에 명시하는 규칙을 팀 공통 원칙으로 넣어줘.
결과는 findings.md 마크다운 파일로 저장해줘.

잠시 후 .claude/agents/ 폴더에 팀원 정의 파일들이(예: organizer.md, extractor.md, rater.md, verifier.md, reporter.md), .claude/skills/ 폴더에 팀의 작업 방법과 실행을 지휘하는 오케스트레이터(팀 전체를 순서대로 돌리는 지휘자 역할) 스킬이 생깁니다. 하네스가 마지막에 "이런 팀을 만들었고, 이 문장으로 실행하세요" 라는 요약을 보여줍니다 — 그 실행 문구를 다음 단계에서 씁니다.

3단계: 팀 실행

팀 구성이 끝났으면, 하네스가 알려 준 실행 문구(예: 사용성 테스트 분석 실행해줘)를 대화창에 입력하면 팀이 순서대로 일을 시작합니다. (구성 직후 같은 대화창에서 바로 실행해도 대개 동작하지만, 더 안정적으로 돌리려면 새 대화 세션을 열고 그 실행 문구를 입력하는 것을 권장합니다 — 새 세션은 대화창에 /clear 를 입력하거나 claude 를 다시 실행하면 시작됩니다.) 이런 식의 결과가 나옵니다(내용은 예시입니다):

이슈 관찰된 참가자(수) 관련 태스크 심각도 심각도 근거 대표 관찰 인용
쿠폰 입력창을 배송 메모칸으로 착각 P1, P4, P6 (3명) 태스크3 결제 4 3명이 쿠폰 적용 자체를 완수 못 하고 정가로 결제 "할인칸이 어디 있지?" (P1)
결제 버튼이 스크롤 아래 숨어 안 보임 P1, P3, P5 (3명) 태스크3 결제 3 3명이 결제 단계에서 30초 이상 버튼을 못 찾음 "다 됐는데 어디서 사죠?" (P5)
쿠폰 적용 후 금액이 즉시 안 바뀜 P2 (1명, 단일 관찰) 태스크3 결제 2 1명이 반복 시도했으나 결국 완수 "눌렀는데 그대로네" (P2)

태스크별 성공률 - 태스크1(상품검색): 8/8 (100%) - 태스크2(장바구니 담기): 7/8 (88%) - 태스크3(쿠폰 적용 후 결제): 3/8 (38%) ← 결제 플로우에 문제 집중

검증 담당 메모: 대표 인용 3건 모두 원문 확인됨 / 참가자 수 집계 이상 없음 / 개인정보 잔존 없음 판정 보류: P7 "글씨가 작다" — 노트 정보 부족으로 심각도 보류 ※ 심각도는 AI 초안입니다. 최종 확정은 팀이 하세요.

findings.md 파일도 같은 폴더에 저장되어, 회의 자료로 바로 공유하거나 다음 라운드와 비교할 수 있습니다.

4단계: 팀 다듬기 (진화)

결과가 아쉬운 부분은 팀에게 말로 피드백합니다. 대화창에 그대로 입력하면 됩니다:

  • 하네스 회고: 리포트에 심각도 4·3 이슈는 "재현 조건(어떤 화면·어떤 행동에서 발생)"과 "관련 참가자 관찰 코멘트 전부"를 붙인 개발 전달용 버그 리포트 섹션을 자동으로 추가하도록 리포트 담당을 개선해줘.
  • 하네스 회고: 검증 담당이 개인정보 점검 결과를 리포트 맨 위에 "개인정보 점검: 통과/미통과" 한 줄로 항상 먼저 보여주게 해줘. 미통과면 실행을 멈추고 알려주도록.

다음 실행부터 반영됩니다. 구축은 1회, 실행은 매번 — 다음 라운드에는 새 sessions.txt 만 폴더에 넣고 실행 문구만 다시 치면, 같은 기준·같은 형식의 리포트가 나옵니다. 라운드 간 비교가 흔들리지 않는 이유가 이것입니다.

꼭 사람이 확인하세요

  • 심각도 등급은 AI 초안일 뿐, 최종 판정은 사람이 합니다. Nielsen 척도는 원래 "빈도 × 영향 × 지속성"을 종합해 여러 평가자가 독립적으로 매긴 값을 평균 내도록 설계됐습니다. AI는 노트에 적힌 표면 정보(실패 여부·인원 수)로만 추정하므로, 비즈니스 임팩트가 큰 이슈(예: 결제 이탈)를 과소평가할 수 있습니다. 팀이 조정하세요.
  • "관찰된 참가자 수"를 대조하세요. 검증 담당이 1차로 걸러 주지만, 심각도 4·3 이슈는 사람도 원문 노트에서 그 참가자들이 실제로 그 문제를 겪었는지 눈으로 확인하세요. AI가 비슷한 코멘트를 잘못 뭉치거나 반대로 쪼갤 수 있습니다.
  • 인용이 진짜 원문인지 검증하세요. 검증 담당의 "원문 확인됨" 메모가 있어도, 대표 인용 몇 개는 사람이 sessions.txt에서 실제로 검색해 그대로 있는지 확인하세요. 다르면 하네스 회고: 관찰 노트 원문 그대로만 인용하도록 검증 규칙을 더 엄격히 해줘로 조입니다.
  • 단일 관찰(한 명)이라고 무시하지 마세요. 1명에게서만 나왔지만 치명적인 문제(결제 오류, 개인정보 노출 등)가 있을 수 있습니다. '단일 관찰'·'판정 보류' 항목도 사람이 한 번 훑고 직접 판단하세요.
  • 뉘앙스·감정은 AI가 놓칩니다. "성공은 했지만 표정이 굳었다", "짜증 섞인 한숨" 같은 정성적 마찰은 노트에 있어도 심각도에 잘 반영되지 않습니다. 관찰자가 느낀 신호는 사람이 보강하세요.
  • 개인정보 최종 확인은 사람 몫입니다. 검증 담당이 점검하지만, 파일을 넣기 전과 리포트를 공유하기 전 두 번 모두 사람이 확인하세요. 노트를 급히 모으면 일부 참가자만 실명이 남는 경우가 흔합니다. 익명 코드로 통일됐는지, 인용문 안에 이름이 섞이지 않았는지 훑으세요.

하네스가 과한 경우

이번 한 번만 세션 노트를 정리하는 거라면, 팀을 만들 필요 없이 프롬프트 한 번이 더 빠릅니다. Claude Code에 sessions.txt를 두고 이렇게 물으면 됩니다:

복사해서 쓰세요
sessions.txt를 읽고 사용성 이슈를 뽑아, 같은 문제는 합쳐서 몇 명에게서 나왔는지 적고,
Nielsen 심각도(0~4)와 근거를 붙인 표로 정리해줘. 노트에 없는 내용은 지어내지 마.

판단 기준은 "같은 형식의 리포트가 라운드마다 반복적으로 필요한가?" 입니다. 1회성·소규모면 위 한 줄이면 충분하고, 스프린트마다 같은 기준으로 반복된다면 그때 하네스로 승격하세요. 하네스의 값어치는 반복 실행에서 나옵니다(구축 1회, 실행 N회).

한 걸음 더

  • 팀원 추가: 라운드가 쌓이면 "추이 담당"을 붙여, 라운드별 findings.md를 모아 "이 이슈는 3라운드째 미해결" 같은 장기 추적 표를 만들게 할 수 있습니다. 하네스 회고: 지난 라운드 findings.md들을 모아 이슈별 라운드 추이를 그려주는 팀원을 추가해줘.
  • 가까운 하네스에서 출발: 처음부터 만들지 않고 미리 만들어진 revfactory/harness-100(10개 도메인 100개 팀 하네스)에서 비슷한 분석 팀을 설치해 고쳐 쓰는 것도 방법입니다.
  • 업계 동향(2026): 사용성·휴리스틱 평가에 AI로 심각도 초안과 패턴 탐지를 돕는 흐름이 넓어지고 있습니다 — ChatGPT로 인터페이스 설명에서 휴리스틱 위반을 짚어 보거나, heurilens.com 같은 도구가 자동 심각도 추정을 제공하고, Figma 플러그인이 디자인 단계에서 이슈를 표시하는 식입니다(SaaS Hero, Heurilens). 다만 이들은 대부분 초안·보조이며, 심각도 확정과 맥락 해석은 여전히 사람 몫이라는 점은 이 사례의 원칙과 같습니다.

참고: Nielsen 심각도 척도(0=문제 아님, 1=미관 수준, 2=경미, 3=심각, 4=재앙)는 Nielsen Norman Group의 표준 척도를 따랐습니다(NN/g, MeasuringU). 이 척도는 원래 여러 평가자의 독립 평가를 평균 내도록 설계됐으므로, AI 단독 판정을 최종값으로 쓰지 말고 사람 평가와 함께 쓰는 것이 원 취지에 맞습니다.
