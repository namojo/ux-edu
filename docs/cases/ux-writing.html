에러 메시지·버튼·온보딩 마이크로카피 시안 N종 뽑고 톤앤매너로 검수하기

따라 하기마이크로카피 시안을 여러 개 뽑고 톤앤매너로 검수할 때
항목 내용
영역 UX 라이팅
난이도 중급
소요 시간 약 25~35분
준비물 ① 톤앤매너 가이드(우리 팀 문서 또는 아래 예시로 즉석 작성), ② 카피가 들어갈 화면 맥락 메모, ③ Claude Code가 설치된 컴퓨터

이런 상황에서 쓰세요

버튼 라벨 하나, 에러 메시지 한 줄을 두고 반나절씩 고민한 적이 있을 겁니다. "결제 실패"라고만 띄우면 불친절하고, 길게 쓰면 버튼 안에 안 들어가고, 겨우 썼더니 다른 화면의 말투와 안 맞습니다. 시안을 여러 개 뽑아 비교하고 싶은데 혼자 짜내면 3~4개에서 아이디어가 막힙니다. 게다가 팀 톤앤매너 가이드("사과는 하되 변명하지 않는다", "버튼은 동사로 시작한다" 같은 규칙)를 매번 대조하는 건 지치는 일입니다.

이 작업을 AI에게 맡기면 시안 8~10종을 각각 다른 결(정중함·간결함·친근함)로 뽑고, 우리 가이드에 맞는지까지 표로 대조해 줍니다. 사람은 "어느 결이 이 브랜드답나"를 고르는 판단에만 집중하면 됩니다. 실제로 monday.com 같은 팀은 자사 UX 라이팅 규칙(능동태 사용, 버튼은 동사로 시작 등)을 가이드로 정리해 AI에 알려 주고(프롬프트에 함께 제시해) 마이크로카피 초안을 뽑는 방식을 쓰고 있습니다.

따라 하기

1단계: 준비

  1. 바탕화면이나 문서 폴더에 작업용 폴더를 하나 만듭니다. 예: uxwriting-결제화면
  2. 그 폴더 안에 톤앤매너 가이드를 텍스트 파일로 저장합니다. 파일 이름은 tone-guide.txt로 합니다. Windows는 메모장, Mac은 TextEdit(기본 텍스트편집기)을 씁니다. 주의: Mac의 TextEdit은 기본값이 서식 있는 문서(.rtf)라 그대로 저장하면 tone-guide.txt가 아니라 다른 형식으로 저장됩니다. 상단 메뉴 서식 → 일반 텍스트로 만들기(Make Plain Text)를 먼저 누른 뒤 .txt로 저장하세요. 우리 팀 가이드가 있으면 핵심 규칙만 붙여넣고, 없으면 아래를 그대로 써도 됩니다:

[우리 서비스 톤앤매너 규칙] 1. 사용자를 탓하지 않는다. "잘못된 입력입니다"(X) → "이메일 형식을 다시 확인해 주세요"(O) 2. 사과는 한 번, 짧게. 변명·기술 용어(서버, 세션, 토큰)는 쓰지 않는다. 3. 버튼 라벨은 동사로 시작하고 공백 제외 최대 6자. "확인"보다 "다시 시도" 선호. 4. 다음에 뭘 하면 되는지 항상 알려준다(해결 행동 제시). 5. 존댓말, 담백하게. 느낌표·이모지는 축하/성공 상황에서만.

  1. 카피가 들어갈 화면 맥락을 한 문단으로 메모해 둡니다(파일로 저장하지 않고 프롬프트에 바로 써도 됩니다). 예: "결제 단계에서 카드 한도 초과로 결제가 거절된 상황. 사용자는 장바구니로 돌아가거나 다른 카드로 재시도할 수 있음."
  2. 1단계에서 만든 폴더 안에서 터미널(명령어를 입력하는 검은 창)을 엽니다. 이 폴더 안에서 여는 게 중요합니다. 여기서 켜지 않으면 뒤에 나오는 프롬프트 첫 줄 "tone-guide.txt 파일을 먼저 읽어줘"가 파일을 못 찾아 작업이 실패합니다. 폴더 안에서 터미널을 여는 방법: - Mac(가장 쉬움): Finder에서 만든 폴더를 우클릭 → 서비스 → 폴더에서 새로운 터미널 열기. (이 메뉴가 안 보이면 시스템 설정 → 키보드 → 키보드 단축키 → 서비스에서 "폴더에서 새로운 터미널 열기"를 켜면 나타납니다.) - Windows: 폴더를 연 상태에서 위쪽 주소창(경로가 표시되는 칸)을 클릭해 글자를 지우고 cmd 를 입력한 뒤 Enter. 그 폴더를 기준으로 터미널이 열립니다. - 명령어로 하고 싶다면: 아무 터미널이나 연 뒤 cd (cd 뒤에 한 칸 띄우기)를 입력하고, 만든 폴더를 터미널 창으로 끌어다 놓으면 폴더 경로가 자동으로 채워집니다. Enter를 누르면 그 폴더 안으로 들어갑니다. (cd는 "그 폴더 안으로 들어가라"는 명령입니다.)

폴더 안에서 터미널이 열렸으면 claude 를 입력해 Claude Code를 켭니다. Claude Code는 그 폴더 안의 파일을 읽고 쓸 수 있는 AI 도구입니다.

2단계: 프롬프트 입력

아래를 복사해 붙여넣고, {중괄호} 부분만 바꾸세요:

복사해서 쓰세요
tone-guide.txt 파일을 먼저 읽어줘. 이건 우리 서비스의 UX 라이팅 톤앤매너 규칙이야.

[화면 맥락]
{결제 단계에서 카드 한도 초과로 결제가 거절된 상황. 사용자는 장바구니로 돌아가거나 다른 카드로 재시도할 수 있음.}

[요청]
이 상황의 에러 메시지 마이크로카피 시안을 8종 만들어줘. 조건:
1. 각 시안은 (a) 제목 한 줄, (b) 본문 한 줄, (c) 버튼 라벨 1~2개로 구성해줘.
2. 8종을 서로 다른 결로 뽑아줘: 정중함 위주 2종 / 간결함 위주 2종 / 친근함 위주 2종 / 안심시키기 위주 2종. 각 시안 옆에 어떤 결인지 표시해줘.
3. 표로 정리하고, 각 시안이 tone-guide.txt의 규칙 1~5를 각각 지켰는지 O/X로 대조한 열을 붙여줘. X면 어떤 규칙을 어겼는지 한 줄로 적어줘.
4. 규칙을 가장 잘 지킨 시안 2개를 맨 아래에 추천으로 뽑고, 이유를 한 줄씩 적어줘.

주의: 없는 사실(예: 구체적 고객센터 번호, 환불 정책)은 지어내지 말고, 필요하면 {대괄호}로 채울 자리만 남겨줘.

3단계: 결과 확인

이런 식의 결과가 나옵니다(실제로는 시안 8종·규칙 5개 열이 모두 나오지만, 아래는 8종 중 4종, 규칙 열 일부(1·3·4)만 발췌한 예시입니다):

# 결 제목 본문 버튼 규칙1 안탓하기 규칙3 동사·6자 규칙4 다음행동
1 정중함 결제가 완료되지 않았어요 카드 한도를 초과한 것 같아요. 다른 카드로 다시 시도해 주세요. 다시 시도 / 장바구니로 O O O
2 간결함 결제 거절됨 다른 결제 수단을 이용해 주세요. 다시 시도 O O O
3 친근함 앗, 결제가 막혔네요 카드 한도를 확인하거나 다른 카드로 결제해 볼까요? 다시 시도 O O O
4 안심 아직 결제되지 않았어요 요금은 청구되지 않았으니 안심하세요. 다른 카드로 진행할 수 있어요. 다른 카드로 O △ AI는 7자로 셈 O

위 표 4번 행의 △ 표시는 일부러 남긴 함정입니다. AI는 버튼 "다른 카드로"를 "7자라 규칙 위반(△)"으로 판정했지만, 직접 세어 보면 공백 제외 5자(다·른·카·드·로), 공백 포함 6자로 글자 수 조건은 지킵니다. 즉 이 △는 AI가 한글 글자 수를 잘못 센 예입니다("꼭 사람이 확인하세요"의 첫 항목과 이어집니다). 규칙 3이 공백 포함인지 제외인지를 tone-guide.txt에 못박아 두면 이런 혼선이 줄어듭니다.

규칙 3은 사실 조건이 두 개입니다 — "동사로 시작" 하고 "공백 제외 6자 이내" 여야 합니다. 그런데 표의 "장바구니로"(1번)·"다른 카드로"(4번)는 둘 다 조사 '로'로 끝나는 목적지 표현이라, 글자 수는 통과해도 동사로 시작하지는 않습니다. AI는 이 표에서 글자 수만 세고 동사 시작 여부는 따로 확인하지 않아 두 버튼 모두 규칙3을 O(또는 글자 수만 △)로 표시했습니다. 조건이 두 개인 규칙은 표의 O 하나만 보고 넘기지 말고, 조건별로 나눠 직접 확인해야 한다는 뜻입니다.

추천 2종 - #1 (정중함): 본문은 규칙 1,2,4,5를 지킵니다. 버튼 "장바구니로"는 글자 수는 통과하지만 동사로 시작하지는 않는 목적지 표현입니다 — 브랜드 톤상 자연스럽다고 판단되면 이 정도는 사람이 허용 범위로 볼 수 있지만, "동사로 시작"을 엄격히 지키려면 "장바구니 담기"처럼 바꿔야 합니다. - #4 (안심): "요금은 청구되지 않았다"는 안심 문구가 결제 실패 상황의 불안을 크게 줄입니다. 버튼 "다른 카드로"는 AI가 △(위반)로 표시했지만 실제 글자 수는 공백 제외 5자로 그 조건은 지킵니다. 다만 동사로 시작하지도 않는 목적지 표현이라, 규칙3의 두 조건 중 하나만 지킨 셈입니다. AI의 글자 수 판정을 곧이곧대로 믿지 말아야 하는 것과 마찬가지로, "글자 수 통과 = 규칙 완전 준수"도 아닙니다. 이런 목적지형 버튼 표현을 허용할지는 브랜드 판단으로 남겨 두세요.

규칙을 어긴 시안은 X 표시와 함께 이유가 붙어 나옵니다. 예: "규칙2 위반 — '결제 세션이 만료되었습니다'에서 '세션'은 기술 용어라 사용자에게 낯섦."

4단계: 다듬기

첫 결과가 나오면 후속 프롬프트로 원하는 방향으로 좁혀 갑니다. 아래처럼 이어서 입력하면 됩니다:

  • #4 안심 결이 마음에 들어. 이 방향으로 3개만 더 변주해줘. 대신 버튼은 전부 6자 이내로 맞춰줘.
  • 추천 2종을 온보딩 첫 화면 버튼 카피로도 응용해줘. 같은 톤앤매너 규칙을 적용하고, 이번엔 이모지는 성공/환영 맥락이니 규칙5에 따라 허용해줘.
  • 최종 표를 microcopy-시안.md 파일로 저장해줘. (microcopy-시안.md는 마크다운, 즉 표·제목을 기호로 표현한 텍스트 파일이라 회의 자료로 바로 공유 가능합니다.)

이렇게 에러 메시지 → 버튼 → 온보딩으로 같은 규칙을 이어 적용하면, 화면마다 말투가 따로 노는 문제를 줄일 수 있습니다.

꼭 사람이 확인하세요

  • 규칙 준수 O/X 판정을 그대로 믿지 마세요. AI는 "이 정도면 동사"라고 느슨하게 판정하거나, 글자 수를 잘못 셀 수 있습니다(특히 한글 글자 수). 추천 시안만이라도 버튼 글자 수를 직접 세고, "탓하지 않는가"는 사람 감각으로 다시 읽으세요.
  • 브랜드 뉘앙스는 AI가 놓칩니다. "친근함"을 지시하면 AI가 반말·과한 이모지·유행어로 흐를 수 있는데, 우리 브랜드에는 안 맞을 수 있습니다. 결(정중/친근 등)은 방향 참고용이고, 최종 선택은 "이게 우리 서비스다운가"로 사람이 판단하세요.
  • 법적·정책 문구는 반드시 검증하세요. "요금은 청구되지 않았어요", "환불됩니다" 같은 문장은 실제 결제/환불 로직과 다르면 큰 문제가 됩니다. 사실 여부는 개발·정책 담당과 확인하고, AI가 지어낸 정책 표현이 없는지 살피세요(프롬프트에서 대괄호 자리로 남기게 한 이유입니다).
  • 접근성·번역을 잊지 마세요. 화면 안에 예쁘게 들어가도 스크린리더로 읽으면 어색하거나, 영어로 번역할 때 버튼이 길어질 수 있습니다. 다국어 서비스라면 시안 확정 전에 번역 길이도 가늠하세요.
  • N종을 다 쓰려 하지 마세요. 8종은 고르기 위한 재료입니다. 최종은 1~2개로 좁히고, 가능하면 A/B 테스트로 실제 사용자 반응을 확인하는 것이 정석입니다.

한 걸음 더

이 작업이 화면마다·릴리스마다 반복된다면, 매번 프롬프트를 붙여넣는 대신 에이전트 팀(하네스) 으로 승격할 가치가 있습니다. 하네스는 역할이 나뉜 AI들이 순서대로 일하는 작은 팀입니다. UX 라이팅이라면 예를 들어:

  • 시안 생성 담당: 화면 맥락을 받아 결별 시안 N종을 뽑는다(위 2단계 프롬프트를 고정 규칙으로).
  • 톤 검수 담당: tone-guide.txt를 기준으로 규칙 위반을 잡아내고, 글자 수·금지 용어를 기계적으로 대조한다.
  • 일관성 담당: 지난 릴리스에 쓴 카피 모음과 대조해 "같은 상황인데 말투가 다른" 곳을 찾아낸다.
  • 정책 플래그 담당: 환불·요금·법적 표현이 들어간 문장을 뽑아 "사람 확인 필요"로 표시한다.

이렇게 만들어 두면 새 화면이 생길 때마다 맥락 한 줄만 넣어도 우리 톤에 맞는 시안 세트와 검수표가 같은 형식으로 나옵니다. "매번 같은 규칙으로, 같은 형식의 검수 결과가 필요하다"가 반복될 때가 하네스로 만들 시점입니다. 팀의 톤앤매너 가이드가 문서로 잘 정리되어 있을수록 이 하네스의 품질이 올라갑니다 — 가이드 정비 자체가 AI 활용의 사전 투자인 셈입니다.

외부 동향 참고: 2025~2026년 업계에서는 AI를 마이크로카피 "초안 생성 + 브랜드 보이스 일관성 점검" 용도로 쓰되 최종본이 아닌 출발점으로 삼고, A/B 테스트로 검증하는 흐름이 정착되고 있습니다. 팀의 톤앤매너 가이드를 문서로 명확히 정의할수록 AI 산출물의 정확도가 올라간다는 점(monday.com 등 사례)이 공통적으로 강조됩니다. 출처: NN/g Tone of Voice, 4951 Studios — AI for UX Writing, Definitive Guide to UX Writing 2026.
