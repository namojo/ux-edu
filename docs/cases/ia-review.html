팀 패턴 Pipeline + Producer-Reviewer — 현행 분석→대안 생성을 순차로 잇고(Pipeline), 대안을 별도 평가자가 검증(Producer-Reviewer). "Pipeline=한 사람 결과를 다음 사람이 이어받는 컨베이어벨트", "Producer-Reviewer=만드는 사람과 검사하는 사람을 나누는 구조"

이런 상황에서 쓰세요

개편 프로젝트가 시작될 때마다 현행 메뉴 구조를 펼쳐 놓고 "여기가 왜 안 되는지"를 다시 진단하고, 대안 구조를 2~3개 그려 보고, 각 대안이 사용자의 머릿속 분류(멘탈 모델)와 맞는지 카드소팅 관점으로 따져 봅니다. 매번 하는 일인데도 프로젝트마다 처음부터 다시 정리하느라 초안까지 이틀씩 걸립니다. 구조는 반복되는데 대상 서비스만 바뀌는 이 작업은 팀(하네스)으로 만들어 두면 다음 프로젝트부터는 현행 구조만 갈아 끼우고 실행하면 됩니다.

용어 메모 - IA(정보 구조, Information Architecture): 서비스의 메뉴·화면·콘텐츠를 어떤 묶음과 순서로 배치하는가에 대한 설계. - 카드소팅(card sorting): 콘텐츠 이름을 카드처럼 적어 사용자에게 직접 분류하게 하는 리서치 기법. 사용자가 무엇을 같은 그룹으로 보는지 알아내는 방법. - 멘탈 모델(mental model): 사용자가 머릿속에 이미 갖고 있는 "이건 여기 있겠지"라는 기대. - depth(깊이): 상위 메뉴에서 몇 단계 안쪽에 있는지. 예를 들어 '3depth'는 최상위에서 세 단계 안쪽(=클릭 3번 만에 닿는 위치)이라는 뜻.

팀 미리보기

하네스가 만들어 줄 팀은 이렇습니다:

팀원 역할
structure-analyst (현행 진단자) 현행 메뉴/사이트맵을 읽어 깊이·라벨 일관성·중복·고아 메뉴 등 구조 문제를 진단
ia-designer (대안 설계자) 진단 결과를 받아 개편 대안 IA를 2~3안 생성(각 안의 설계 의도 포함)
cardsort-evaluator (카드소팅 평가자) 각 대안을 사용자 멘탈 모델·카드소팅 관점에서 평가하고 안별 장단점을 비교
ia-reviewer (검증자) 라벨 중복·근거 없는 단정·과장을 잡아내고 사람이 확인할 지점을 표시

검증자(ia-reviewer)를 따로 둔 이유: AI는 그럴듯한 구조를 빠르게 만들지만 "근거 없이 단정하는" 실수를 자주 합니다. 만드는 팀원과 검사하는 팀원을 분리해야 그 실수가 걸러집니다.

따라 하기

0단계: 하네스 설치 확인 (처음 한 번만)

이 사례는 revfactory/harness가 설치되어 있어야 합니다. 설치는 전체 사례집을 통틀어 처음 한 번만 하면 됩니다 — 아직이라면 하네스 설치 안내를 따라 하세요 (약 2분).

  • 설치 확인: Claude Code 대화창에 /plugin을 입력해 목록에 harness가 보이면 준비 완료. 이미 설치했다면 바로 1단계로 넘어갑니다.

1단계: 준비

화면에서 이렇게 준비합니다.

  1. 컴퓨터에 작업 폴더를 하나 만듭니다. 예: ia-검토-2026개편.
  2. 그 안에 현행 구조를 적은 텍스트 파일을 하나 넣습니다. 파일명 예: 현행구조.md (.md=마크다운. 제목·목록을 기호로 표시하는 가벼운 문서 형식. 메모장으로 열립니다). - 들여쓰기로 메뉴 depth를 표현하면 됩니다. 예: ```
    • 홈
    • 상품
    • 신상품
    • 베스트
    • 카테고리별
    • 마이페이지
    • 주문내역
    • 쿠폰
    • 1:1 문의 ```
  3. 같은 폴더에 배경.md 파일을 만들어 서비스 목표와 주요 사용자 유형을 3~5줄 적습니다. 예: "40~50대 첫 방문 비중 높음 / 목표: 상품 탐색 이탈 줄이기 / 문제 제보: 고객문의 메뉴를 못 찾는다".
  4. 이제 이 작업 폴더 안에서 Claude Code를 실행합니다. 폴더 안에서 실행해야 팀이 현행구조.md·배경.md를 바로 읽고, 결과 리포트도 이 폴더에 저장됩니다(다른 폴더에서 실행하면 파일을 못 찾거나 리포트가 엉뚱한 위치에 저장됩니다). - macOS: Spotlight(⌘+Space)에 terminal을 입력해 터미널(검은 명령어 입력 창)을 엽니다 → 창에 cd를 입력하고 한 칸 띄운 뒤, 만든 폴더를 터미널 창 안으로 드래그하면 경로가 자동 입력됩니다 → Enter → claude 입력 후 Enter를 누르면 Claude Code가 켜집니다. (Finder 우클릭 → 서비스 → '폴더에서 새로운 터미널 열기' 메뉴가 보인다면 그걸 써도 됩니다 — 단, 이 메뉴는 기본값으로 꺼져 있는 Mac이 많습니다.) - Windows: 폴더를 연 상태에서 위쪽 주소창을 클릭해 cmd라고 입력하고 Enter를 누르면, 그 폴더 위치에서 명령어 창이 열립니다. 열린 창에 claude라고 입력하고 Enter를 누릅니다. - (하네스 설치를 아직 안 했다면, 이렇게 Claude Code를 켠 다음 하네스 설치 안내를 따라 설치하세요.)

스크린샷밖에 없다면? 현행 메뉴를 눈으로 보고 위 예시처럼 들여쓰기 목록으로 옮겨 적기만 하면 됩니다. AI가 이미지보다 텍스트 구조를 훨씬 정확히 다룹니다.

2단계: 팀 구성 (바이브코딩)

바이브코딩(vibe coding) = 코드를 직접 쓰지 않고, 원하는 팀·기능을 말로 설명하면 AI가 대신 만들어 주는 방식. 아래처럼 "이런 팀이 필요해"라고 문장으로 요청하는 것이 곧 바이브코딩입니다.

아래를 그대로 복사해 붙여넣으세요. 1단계와 같은 파일명(현행구조.md·배경.md)을 썼다면 바꿀 부분이 없고, 파일 이름을 다르게 지었다면 그 이름만 고치면 됩니다:

복사해서 쓰세요
하네스 구성해줘: IA 개편을 검토하는 팀이 필요해.
현행 메뉴/사이트맵 구조(현행구조.md)와 서비스 배경(배경.md)을 입력하면,
① 현행 구조를 진단(메뉴 깊이·라벨 일관성·중복·찾기 어려운 항목)하고,
② 개편 대안 IA를 2~3안 생성(각 안의 설계 의도 포함)하고,
③ 각 대안을 카드소팅·사용자 멘탈 모델 관점에서 평가·비교하고,
④ 근거 없는 단정과 라벨 중복을 걸러내는 검증까지 하는 팀으로.
결과는 '진단 → 대안 비교표 → 추천안과 근거 → 사람이 확인할 지점' 순서의
마크다운 리포트 한 편으로 저장해줘.

잠시 후 .claude/agents/ 폴더에 팀원 파일들이, .claude/skills/에 팀의 작업 방법이 생깁니다. 하네스가 마지막에 "이런 팀을 만들었습니다"라는 요약(팀원 목록과 실행 트리거 문구)을 보여주는데, 그 요약만 읽으면 무엇이 생겼는지 확인됩니다. 팀 미리보기 표의 4명과 비슷한 구성이 나오면 정상입니다.

3단계: 팀 실행

팀 구성이 끝난 뒤 대화창을 새로 시작하고(새 세션은 대화창에 /clear 를 입력하거나 claude 를 다시 실행하면 시작됩니다), 하네스가 알려 준 트리거 문구(예: "IA 검토 실행해줘")를 입력하면 팀이 일을 시작합니다. 이런 식의 결과가 나옵니다:

복사해서 쓰세요
# IA 검토 리포트 — 2026 개편

## 1. 현행 구조 진단
| 항목 | 진단 | 근거 |
|------|------|------|
| 메뉴 깊이 | 마이페이지 하위 3depth로 과다 | 주문내역이 3번 클릭 후 노출 |
| 라벨 일관성 | '1:1 문의'와 '고객센터' 혼용 | 두 라벨이 다른 위치에 각각 존재 |
| 찾기 어려운 항목 | 고객문의 접근 경로 불명확 | 배경.md의 실제 제보와 일치 |

## 2. 개편 대안 비교
| 기준 | A안(과업 중심) | B안(콘텐츠 중심) |
|------|----------------|------------------|
| 최상위 메뉴 수 | 4개 | 6개 |
| 고객문의 노출 | 전역 상단 고정 | 마이페이지 1depth |

4단계: 팀 다듬기 (진화)

결과가 아쉬운 부분은 팀에게 말로 피드백합니다:

  • 하네스 회고: 대안이 매번 2안뿐이야. '현행 최소 수정안'을 항상 3번째 안으로 넣게 개선해줘. (개편은 통째로 못 바꾸는 경우가 많아, 보수적 대안을 기본 포함시키는 실전 요청)
  • 하네스 회고: 카드소팅 평가가 단정적이야. 실제 카드소팅으로 검증이 필요한 항목은 '검증 필요' 태그를 붙이도록 바꿔줘.

다음 실행부터 반영됩니다. 구축은 1회, 실행은 매번 — 다음 개편 프로젝트에서는 현행구조.md와 배경.md만 새 서비스 내용으로 바꿔 넣고 3단계만 다시 실행하면 됩니다.

꼭 사람이 확인하세요

  • 카드소팅 평가는 "가설"이지 "결과"가 아닙니다. AI가 만든 구조는 논리적으로는 그럴듯하지만, 실제 사용자 집단이 콘텐츠를 어떻게 분류하는지(맥락 의존적 멘탈 모델)는 재현하지 못합니다. 2026년 UXmatters 정리와 2025년 arXiv 연구는 AI 카드소팅이 논리적으로 일관된 구조를 만들지만 특정 사용자 집단의 사고방식은 담지 못해 "실제 카드소팅의 보완재이지 대체재가 아니다"라는 점을 공통적으로 짚었습니다(UXmatters, 2026; arXiv, 2025). 추천안은 반드시 실제 사용자 대상 카드소팅·트리 테스트로 검증하세요.
  • 진단의 "근거" 칸을 사람 눈으로 대조하세요. AI가 현행 구조에 없는 메뉴를 있는 것처럼 진단하거나(환각), 배경.md에 없는 사용자 특성을 지어낼 수 있습니다. 진단 표의 '근거' 칸이 실제 입력 파일과 일치하는지 확인하는 것이 최소 안전장치입니다.
  • 라벨 뉘앙스는 AI가 자주 놓칩니다. 국내 서비스에서 '문의/상담/고객센터'처럼 미묘하게 다른 라벨의 관행적 차이는 사람이 최종 판단해야 합니다.
  • 비즈니스 제약은 입력하지 않으면 반영되지 않습니다. "이 메뉴는 제휴 계약상 최상위 고정" 같은 제약은 배경.md에 적어 주지 않으면 AI가 자유롭게 재배치합니다.

하네스가 과한 경우

이번 한 번만, 작은 서비스의 메뉴 5~6개를 훑어보는 정도라면 팀을 만들 필요가 없습니다. 그냥 대화창에 현행 구조를 붙여넣고 한 번 물어보세요:

복사해서 쓰세요
이 메뉴 구조의 문제점을 진단하고 개편 대안을 2안 제시해줘. 각 안의 근거도 같이.
(구조를 여기 붙여넣기)

판단 기준: 같은 형식의 IA 검토 리포트가 프로젝트마다 반복적으로 필요한가? 개편 프로젝트가 분기마다 돌아오고 결과 형식(진단→대안→평가)이 매번 같다면 하네스가 이득입니다. 일회성 자문이면 위 한 줄 프롬프트로 충분합니다.
