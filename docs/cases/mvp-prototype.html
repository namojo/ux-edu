아이디어를 클릭 가능한 HTML 시제품으로 만들기 (코드 한 줄 안 쓰고)

따라 하기아이디어를 클릭 가능한 시제품으로 빠르게 검증할 때
항목 내용
영역 MVP 프로토타입
난이도 중급
소요 시간 약 30~50분 (첫 화면까지는 약 10분)
준비물 검증하고 싶은 아이디어를 적은 메모(플로우 3~5단계), Claude Code가 설치된 컴퓨터, 웹 브라우저(크롬·사파리 등)

이런 상황에서 쓰세요

머릿속엔 "이런 온보딩 흐름이면 이탈이 줄 것 같은데"라는 가설이 있는데, 이걸 남에게 보여주려면 매번 디자이너에게 화면을 부탁하거나 프로토타이핑 툴에서 프레임을 수십 개 이어 붙여야 합니다. 사용성 테스트 참가자 앞에 내놓으려면 "클릭하면 다음으로 넘어가는" 정도는 되어야 하는데, 정적인 이미지 시안으로는 흐름의 어색함이 안 잡힙니다. 이 사례는 당신이 코드를 짜는 게 아니라, Claude Code에게 "이런 앱을 이렇게 만들어줘"라고 말로 설명해서, 더블클릭하면 바로 열리는 클릭 가능한 시제품(HTML 파일 하나)을 받아내는 방법입니다. 만드는 건 AI가, 검증할 흐름을 설계하고 판단하는 건 사람이 합니다.

참고: 이렇게 AI에게 프로토타입을 말로 시켜 만드는 방식을 업계에서는 "바이브 코딩(vibe coding)" 또는 "바이브 디자인"이라고 부릅니다. 2025~2026년 사이 UX 실무에 빠르게 퍼졌고, 개발 착수 전에 실제로 클릭해볼 수 있는 경험을 만들어 사용자에게 먼저 검증하는 용도로 쓰입니다.

따라 하기

1단계: 준비

만들기 전에 무엇을 검증할지부터 한 문단으로 정리합니다. 이 정리가 프로토타입 품질의 8할을 좌우합니다. AI는 흐름을 상상해주지 않습니다 — 당신이 준 흐름을 화면으로 옮겨줄 뿐입니다.

  1. 바탕화면이나 문서 폴더에 작업용 폴더를 하나 만듭니다. 예: mvp-온보딩실험
  2. 메모장(텍스트편집기)에 아래 4가지를 적어둡니다. 프롬프트에 그대로 넣을 재료입니다. - 무슨 서비스인가: 예) "사내 카페 주문 앱" - 누가 쓰나: 예) "처음 앱을 켠 신규 직원" - 검증할 핵심 흐름 (화면 순서): 예) "환영 화면 → 취향 음료 선택 → 홈(내 취향 추천) → 주문 → 완료" - 이 프로토타입으로 확인하고 싶은 것 1가지: 예) "취향을 먼저 물어보면 온보딩 이탈이 줄어드는지"
  3. 방금 만든 그 폴더 안에서 Claude Code를 켭니다. 폴더로 이동하는 것이 첫 관문이니 아래 방법 중 하나를 쓰세요. - 맥(가장 쉬움): 파인더에서 만든 폴더를 우클릭(또는 컨트롤+클릭) → 폴더에서 새로운 터미널 열기. 그러면 이미 그 폴더 안에서 터미널(명령어를 입력하는 검은 창)이 열립니다. - 윈도우: 파일 탐색기에서 그 폴더를 연 뒤, 위쪽 주소창을 클릭해 cmd 라고 입력하고 엔터. 그 폴더 안에서 명령창이 열립니다. - 위치가 헷갈리면(가장 안전): 터미널을 그냥 켜고 claude 를 입력한 뒤, 대화 첫 문장으로 이렇게 지정하세요 — 이 대화에서 만드는 파일은 전부 바탕화면의 mvp-온보딩실험 폴더에 넣어줘. 이러면 터미널 위치를 신경 쓰지 않아도 파일이 원하는 폴더에 생깁니다.

터미널이 폴더 안에서 열렸다면 claude 를 입력해 Claude Code를 켭니다. Claude Code는 그 폴더 안에 파일을 직접 만들고 고칠 수 있는 AI 도구입니다.

이 사례의 핵심은 "코드를 배우는 것"이 아닙니다. 검증할 흐름을 명확한 한국어로 설명하는 것이 당신의 일입니다. 나머지(HTML·CSS·클릭 동작 구현)는 전부 AI가 합니다.

2단계: 프롬프트 입력

아래를 복사해 붙여넣고, {중괄호} 부분만 1단계에서 정리한 내용으로 바꾸세요:

복사해서 쓰세요
사용성 테스트에 쓸 클릭 가능한 HTML 프로토타입을 만들어줘. 나는 코드를 모르니까,
결과는 index.html 파일 하나로 만들어서 더블클릭하면 브라우저에서 바로 열리게 해줘.

- 서비스: {사내 카페 주문 앱}
- 사용자: {처음 앱을 켠 신규 직원}
- 검증할 핵심 흐름(이 순서대로 화면 전환): {환영 화면 → 취향 음료 선택(복수 선택) → 홈(내 취향 기반 추천 노출) → 음료 주문 → 주문 완료}
- 이 프로토타입으로 확인하고 싶은 것: {취향을 먼저 물어보면 온보딩 이탈이 줄어드는지}

조건:
1. 화면은 위 흐름에 필요한 4~5개만. 전체 앱을 다 만들지 마.
2. 모바일 화면처럼 보이게, 데스크톱에서 열어도 가운데에 휴대폰 프레임으로 표시해줘.
3. 로그인·결제·서버 연결은 만들지 마. 버튼을 누르면 다음 화면으로 넘어가는 것까지만.
4. 음료 이름·가격 같은 데이터는 실제로 있을 법한 그럴듯한 한국어 더미로 채워줘. (테스트1, 홍길동 같은 티나는 값 말고)
5. 모든 버튼은 어딘가로 이어져야 해. 막다른 화면 없이 뒤로가기나 홈 버튼을 넣어줘.
6. 인터넷 없이도 열려야 하니까 외부 이미지·폰트 링크는 쓰지 말고, 그림은 이모지나 색 도형으로 대체해줘.

다 만들면, 비개발자인 내가 읽을 수 있게 "화면 순서 / 이 시제품으로 검증되는 것과 안 되는 것 /
수정 요청하는 법"을 담은 README.md도 같이 만들어줘.

이 프롬프트를 넣으면 Claude Code가 ux-mvp-prototype 스킬(MVP 제작 규칙을 담은 사내 지침서)을 자동으로 참고해, 위 조건에 맞는 index.html과 README.md를 폴더 안에 만들어 줍니다.

3단계: 결과 확인

Claude Code가 파일을 다 만들면, 이런 식으로 알려줍니다:

복사해서 쓰세요
index.html 을 만들었습니다. 아래 4개 화면을 클릭으로 완주할 수 있습니다:
1. 환영 화면 → [시작하기] / [나중에 할게요]
2. 취향 선택 (아메리카노·라떼·디카페인·티·에이드·달콤 6개 칩, 복수 선택)
3. 홈 — "'라떼, 디카페인' 취향에 맞춰 골랐어요" 배너 + 추천 카드
4. 주문 완료 — 대기번호(A-27), 픽업 위치(3층 빈살롱)

흐름은 5단계(환영 → 취향 → 홈 → 주문 → 완료)로 적었지만 실제 화면은 4개입니다. MVP에서는 '주문'을 별도 화면으로 만들지 않고, 홈에서 음료 카드를 한 번 탭하면 바로 완료 화면으로 넘어가도록 압축했기 때문입니다. 화면 수가 흐름 단계보다 적다고 무언가 빠진 게 아닙니다. 실제 개발 때 '주문 상세·수량·옵션' 화면을 여기에 끼워 넣게 됩니다.

여기서 가장 중요한 행동: 만들어진 index.html 파일을 파일 탐색기(윈도우)나 파인더(맥)에서 찾아 더블클릭해 실제로 열어봅니다. 브라우저에 휴대폰 모양 화면이 뜨고, 버튼을 눌러 처음부터 끝까지 클릭으로 넘어가 보세요.

  • Claude Code에게 방금 만든 프로토타입을 브라우저에서 열어줘 라고 하면 대신 열어주기도 합니다.
  • 화면이 상상과 다르면, 그 자리에서 말로 고치면 됩니다(4단계).

이때 함께 만들어진 README.md(표·제목을 기호로 표현한 설명용 텍스트 파일)에는 이런 표가 들어 있어, 사용성 테스트 진행자가 그대로 읽고 테스트를 진행할 수 있습니다:

순서 화면 무엇을 하나 다음으로
1 환영 화면 서비스 소개, 온보딩 시작 시작하기 → 취향 선택
2 취향 선택 6개 칩에서 복수 선택 저장 → 홈
3 홈 취향 기반 추천 노출 음료 카드 탭 → 주문 완료
4 주문 완료 대기번호(A-27)·픽업 위치(3층 빈살롱) 안내 홈으로

4단계: 다듬기

첫 시제품이 나오면, 마음에 안 드는 부분을 말로 고칩니다. 아래는 어디까지 말로 고칠 수 있는지 보여주는 예시입니다(당신 프로토타입의 실제 상태에 맞춰 바꿔 쓰세요 — 이미 되어 있는 것도 있고, 없는 것도 있습니다):

  • 취향 선택 화면이 너무 밋밋해. 각 음료 칩에 이모지를 넣고, 선택하면 색이 진해지게 해줘.
  • 주문 완료 화면에 "예상 픽업 5분 뒤"라는 시간 안내를 대기번호 옆에 추가해줘.
  • 추천 카드 각각에 가격 뱃지를 더 크게 강조해줘.

핵심 원칙 하나: "기존 화면 구조는 그대로 두고, 말한 부분만 고쳐줘" 라고 덧붙이세요. 이렇게 해야 이미 진행한 사용성 테스트 결과와 다음 버전을 비교할 수 있습니다. 처음부터 다시 만들면 무엇이 흐름 개선 덕분이었는지 알 수 없게 됩니다.

수정이 끝나면 index.html을 다시 더블클릭(또는 브라우저 새로고침)해 바뀐 걸 확인합니다.

꼭 사람이 확인하세요

  • "열리고 클릭된다"와 "흐름이 좋다"는 다른 문제입니다. AI는 당신이 준 순서를 충실히 화면으로 옮길 뿐, 그 순서가 사용자에게 좋은지는 판단하지 못합니다. 흐름의 타당성은 반드시 사람이 — 되도록 실제 사용성 테스트로 — 검증하세요. (NN/g은 AI 프로토타입을 두고 "멀리서 보면 그럴듯하지만 가까이 보면 부족하다"고 지적합니다. 화면이 예쁘게 나왔다고 UX가 검증된 게 아닙니다.)
  • 모든 버튼을 직접 눌러 막다른 화면이 없는지 확인하세요. AI가 흐름 중 한 버튼을 빠뜨려 "눌러도 아무 일 없는" 곳을 남길 수 있습니다. 테스트 참가자는 이걸 "고장"으로 인식해 이후 반응이 오염됩니다. 처음부터 끝까지, 그리고 뒤로가기까지 한 번씩 다 눌러보세요.
  • 더미 데이터가 진짜 정보처럼 오해되지 않게 하세요. AI가 채운 가격·메뉴·대기시간은 전부 그럴듯하게 지어낸 값입니다(환각). 참가자나 이해관계자에게 보여줄 때 "실제 데이터 아님"을 명시하고, 화면 안 숫자를 사실로 인용하지 마세요.
  • 접근성은 자동으로 챙겨지지 않습니다. AI가 만든 화면은 색 대비가 약하거나, 키보드만으로 조작이 안 되거나, 화면낭독기 라벨이 빠지는 경우가 흔합니다. 이건 사용성 테스트 통과 여부와 별개로 반드시 점검할 지점입니다. 필요하면 이 화면들 색 대비랑 키보드 조작 접근성 관점에서 문제 있는 곳 짚어줘라고 이어서 물어보세요.
  • 이건 시제품이지 제품이 아닙니다. 새로고침하면 상태가 초기화되고, 로그인·결제·저장은 없습니다. "잘 되니까 이대로 출시하면 되겠다"가 아니라 "흐름을 검증했으니 이제 제대로 개발하자"가 올바른 다음 단계입니다.

한 걸음 더

이런 프로토타입 제작이 반복된다면 — 예를 들어 매주 여러 아이디어를 시제품으로 찍어내 A/B로 비교하거나, 만들 때마다 접근성·더미데이터 점검을 빼먹지 않아야 한다면 — 에이전트 팀(하네스) 으로 승격할 가치가 있습니다. 하네스는 역할이 나뉜 AI들이 순서대로 일하는 작은 팀입니다. 예를 들어:

  • 프로토타입 제작 담당: 위 2단계 프롬프트 규칙(모바일 프레임·더미데이터·막다른 화면 금지)을 고정으로 적용해 index.html 생성
  • 검수 담당: 모든 버튼이 연결됐는지, 색 대비·키보드 접근성에 문제가 없는지 자동 점검하고 리포트
  • 변형 담당: 같은 흐름의 A안/B안(예: 취향 질문을 먼저 vs 나중에)을 두 벌 만들어 나란히 비교할 수 있게 준비
  • 테스트 대본 담당: 만들어진 화면에 맞춰 사용성 테스트 진행 시나리오와 관찰 체크리스트를 자동 작성

"매번 같은 규칙으로 시제품을 찍고, 매번 같은 항목을 검수해야 한다"가 반복될 때가 하네스로 만들 시점입니다. 이 사례집의 실제 완성 예시(mvp/onboarding-smoke/)가 바로 이 방식으로 만들어진 결과물이니, 열어서 참고하세요.

외부 동향 확인: 2026년 7월 기준, AI에게 말로 시켜 클릭 가능한 프로토타입을 만드는 "바이브 코딩/바이브 디자인"은 UX 실무의 주류 흐름으로 자리잡았고, 개발 착수 전 사용자 검증 용도로 널리 쓰입니다. 다만 접근성 누락·품질 편차·"보기엔 좋지만 실제로는 부족함" 문제가 함께 지적되어, 사람의 검증이 필수라는 점이 반복 강조됩니다. 참고: NN/g — AI Prototyping in Real Design Contexts, Smashing Magazine — Intent Prototyping, Microsoft Design — Vibe coding makes prototyping closer to users.
