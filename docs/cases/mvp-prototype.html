구현·검수 팀을 만들어 아이디어를 클릭 가능한 MVP 프로토타입으로 뽑아내기

따라 하기구현·검수 팀을 부려 시제품을 반복 검증할 때
항목 내용
영역 MVP 프로토타입
난이도 중급
소요 시간 구축 약 20분 + 실행 회당 약 15분
준비물 화면 아이디어 메모 1장(글로 써도 됨), revfactory/harness 설치 (아래 0단계)
팀 패턴 Pipeline + Producer-Reviewer — 설계 → 구현 → 검수 → 수정 루프를 도는 "생성-검증" 팀

이런 상황에서 쓰세요

머릿속엔 화면 흐름이 있는데, 사용성 테스트에 쓸 클릭 가능한 화면이 없어 매번 개발자·디자이너의 손을 기다린다면. "로그인 → 홈 → 상세 → 예약 완료" 같은 흐름을 직접 눌러보게 만들고 싶은데, 피그마로 일일이 연결하기엔 시간이 없고 코드는 못 짜겠다면. 이 사례의 핵심은 당신이 코드를 짜는 게 아니라, 화면을 만들고 검수하는 팀을 말로 부리는 것입니다. 같은 일이 프로젝트마다 반복되기 때문에 팀을 한 번 만들어 두면 매번 아이디어만 바꿔 넣으면 됩니다.

프로토타입(prototype): 실제로 개발하기 전에, 아이디어를 눌러보고 검증하려고 빠르게 만든 가짜 화면. MVP(Minimum Viable Product): 핵심 흐름만 담은 최소 형태의 시제품.

팀 미리보기

하네스가 만들어 줄 팀은 이렇습니다:

팀원 역할
화면 기획자 (planner) 당신의 아이디어 메모를 화면별 목록·구성요소·화면 간 이동 규칙으로 정리한 설계 명세로 변환
프로토타입 구현자 (builder) 설계 명세를 보고 클릭 가능한 HTML 화면(파일 하나로 열리는 프로토타입)을 실제로 만듦
UX 검수자 (reviewer) 만들어진 화면을 사용성·일관성·접근성·흐름 완결성 관점에서 점검하고 고쳐야 할 이슈 목록을 냄
수정 반영 (builder 재실행) 새 팀원이 아니라, 앞의 구현자(builder)를 다시 불러 검수 이슈를 반영해 화면을 고치는 재실행 단계 — "검수 → 수정"을 정해진 횟수만큼 반복

에이전트(agent): 하나의 역할을 맡아 일하는 AI 담당자. 여러 에이전트가 모이면 "팀"이 됩니다. HTML: 웹 브라우저(크롬 등)에서 열리는 화면을 담은 파일 형식. 더블클릭하면 화면이 뜹니다.

이 팀의 묘미는 검수자가 구현자와 별개로 존재한다는 점입니다. 만든 사람이 스스로 검수하면 놓치는 것을, 검수 전담이 잡아냅니다. 당신은 두 사람 사이의 "수정 루프"를 몇 바퀴 돌릴지만 정하면 됩니다.

따라 하기

0단계: 하네스 설치 (처음 한 번만)

Claude Code(터미널에서 대화로 일을 시키는 AI 도구. 터미널 = 명령어를 입력하는 검은 창) 대화창에 아래 두 줄을 차례로 붙여넣습니다:

복사해서 쓰세요
/plugin marketplace add revfactory/harness
/plugin install harness@harness-marketplace

플러그인(plugin): Claude Code에 기능을 추가하는 확장. 위 두 줄이 "하네스"라는 팀 제작 기능을 켭니다.

이미 다른 사례에서 설치했다면 이 단계는 건너뜁니다.

1단계: 준비

  1. 바탕화면에 작업 폴더를 하나 만듭니다. 예: 예약앱-프로토타입.
  2. 그 안에 화면 아이디어를 적은 메모 파일 하나를 넣습니다. 거창할 필요 없이 글로 흐름을 적으면 됩니다. 파일 이름 예: 아이디어.md (.md = 마크다운. 서식 없이 글만 쓰는 가벼운 문서 형식).

아이디어 메모 예시(이 정도면 충분합니다): 운동시설 예약 앱 MVP - 홈: 오늘 예약 가능한 시설 목록, 각 항목에 "예약" 버튼 - 상세: 시설 사진 자리, 시간대 선택, "이 시간 예약" 버튼 - 확인: 선택한 시설·시간 요약, "확정" 버튼 - 완료: "예약되었습니다" 메시지, "홈으로" 버튼 목표 사용자: 30대 직장인. 톤: 깔끔하고 신뢰감. 3. 그 폴더 안에서 터미널(명령어를 입력하는 검은 창)을 열고 claude 라고 입력하면 Claude Code가 켜집니다. - macOS: Spotlight(⌘+Space)에 terminal을 입력해 터미널을 엽니다 → 창에 cd를 입력하고 한 칸 띄운 뒤, 만든 폴더를 터미널 창 안으로 드래그하면 경로가 자동 입력됩니다 → Enter → claude 입력 후 Enter. (Finder 우클릭 → 서비스 → '폴더에서 새로운 터미널 열기' 메뉴가 보인다면 그걸 써도 됩니다 — 단, 이 메뉴는 기본값으로 꺼져 있는 Mac이 많습니다.) - Windows: 만든 폴더를 파일 탐색기에서 열고, 폴더 안 빈 공간에서 마우스 오른쪽 클릭 → "터미널에서 열기"를 고른 뒤 claude 입력 후 Enter. ("터미널에서 열기"가 안 보이면 Shift를 누른 채 우클릭하면 나옵니다.)

2단계: 팀 구성 (바이브코딩)

아래를 그대로 복사해 붙여넣으세요. 1단계에서 만든 아이디어 파일 이름이 다르면 그 이름만 고치면 됩니다:

복사해서 쓰세요
하네스 구성해줘: UX 아이디어를 클릭 가능한 HTML MVP 프로토타입으로 만드는 프로토타입 팀이 필요해.
아이디어 메모 파일을 입력하면 (1) 화면 기획자가 화면별 설계 명세로 정리하고,
(2) 구현자가 클릭 가능한 HTML 프로토타입을 만들고,
(3) UX 검수자가 사용성·일관성·접근성·흐름 완결성 관점에서 이슈 목록을 내고,
(4) 그 이슈를 구현자가 반영해 수정하는 "검수→수정" 루프를 2회 도는 팀으로.
결과물은 브라우저에서 바로 열리는 HTML 파일들과, 검수 이슈·수정 내역 리포트로 저장해줘.
나는 코드를 못 짜니까, 내가 하는 일은 아이디어를 주고 검수 방향을 정하는 것까지야.

바이브코딩(vibe coding): 코드를 직접 쓰지 않고, 하고 싶은 일을 말로 설명하면 AI가 만들어 주는 방식.

잠시 후 .claude/agents/ 폴더에 팀원 파일들(planner, builder, reviewer 등)이, .claude/skills/에 팀의 작업 방법과 오케스트레이터(팀 전체를 순서대로 지휘하는 지휘자 역할 스킬)가 생깁니다. 하네스가 마지막에 "이런 팀을 만들었습니다" 하고 팀원 목록과 실행 방법을 요약해 보여줍니다 — 그 요약을 읽으면 무엇이 만들어졌는지 확인됩니다. 팀 미리보기 표와 같은 구성인지 눈으로 대조하세요.

3단계: 팀 실행

새 대화에서 오케스트레이터 트리거 문구(하네스가 알려준 실행 문장. 보통 아래와 같은 형태)를 입력하면 팀이 일을 시작합니다:

복사해서 쓰세요
프로토타입 만들어줘. 입력은 아이디어.md 파일이야.

팀은 기획 → 구현 → 검수 → 수정 순으로 돌아가고, 이런 식의 결과가 나옵니다.

만들어지는 파일

복사해서 쓰세요
예약앱-프로토타입/
├── prototype/
│   ├── index.html      ← 홈 (더블클릭하면 브라우저에 뜸)
│   ├── detail.html     ← 상세
│   ├── confirm.html    ← 확인
│   └── done.html       ← 완료
└── report/
    └── ux-review.md    ← 검수 이슈 + 수정 내역 리포트

검수 리포트(ux-review.md)의 축약 실물

# 화면 이슈 심각도 1차 수정 결과
1 상세 시간대 버튼이 선택돼도 표시가 안 바뀜 — 무엇을 골랐는지 알 수 없음 높음 선택된 시간대에 파란 테두리·체크 표시 추가
2 전체 "예약/확정/완료" 버튼 색이 화면마다 달라 일관성 없음 중간 주요 버튼 색을 한 가지로 통일
3 완료 "홈으로" 링크만 있고 뒤로가기 흐름이 막힘 중간 상단에 뒤로가기 추가
4 상세 이미지 자리에 대체 텍스트 없음 — 스크린리더(화면 내용을 소리로 읽어 주는 보조 프로그램) 사용자가 내용 모름 높음 alt(이미지를 설명하는 대체 텍스트) 추가

이제 index.html을 더블클릭해 직접 눌러보며 흐름을 확인하면 됩니다. 사용성 테스트 참가자에게 이 파일을 열어주면 바로 실험할 수 있습니다.

4단계: 팀 다듬기 (진화)

결과가 아쉬운 부분은 팀에게 말로 피드백합니다:

  • 하네스 회고: 검수자가 시각 디자인 지적은 잘하는데 '흐름이 도중에 막히는지'는 자주 놓쳐. 검수 항목에 "모든 버튼이 실제로 다음 화면으로 연결되는지" 확인을 반드시 넣도록 검수자를 개선해줘.
  • 하네스 회고: 프로토타입이 데스크톱 기준으로만 나와. 우리 사용성 테스트는 모바일 화면으로 하니까, 구현자가 기본으로 모바일 세로 화면(폭 375px 정도) 기준으로 만들도록 바꿔줘.

다음 실행부터 반영됩니다. 구축은 1회, 실행은 매번 — 다음 프로젝트에서는 아이디어.md만 새로 써 넣고 3단계만 다시 하면 됩니다.

꼭 사람이 확인하세요

  • "작동하는 것처럼 보인다"와 "정말 연결됐다"는 다릅니다. 검수자가 통과시켰어도, 반드시 당신이 직접 첫 화면부터 끝까지 눌러보세요. AI는 버튼이 있으면 연결됐다고 착각(환각 = AI가 사실이 아닌 것을 사실처럼 말하는 현상)하는 경우가 있습니다.
  • AI가 채운 예시 내용은 진짜가 아닙니다. 시설 이름·가격·시간·후기 같은 값은 그럴듯하게 지어낸 가짜입니다. 사용성 테스트에서 참가자가 오해하지 않도록, 실제 데이터로 바꾸거나 "예시 데이터"임을 화면에 표시하세요.
  • 접근성 검수는 시작일 뿐 완결이 아닙니다. 대체 텍스트 유무 정도는 잘 잡지만, 실제 스크린리더로 읽었을 때의 자연스러움, 색 대비, 키보드만으로 조작 가능한지는 사람이 최종 확인해야 합니다.
  • 브랜드 톤·미묘한 뉘앙스는 놓칩니다. "깔끔하고 신뢰감"이라고 적어도 AI가 해석한 톤이 당신의 의도와 다를 수 있습니다. 결과를 보고 방향을 말로 다시 잡아 주세요.

하네스가 과한 경우

화면 한두 장을 딱 한 번만 급하게 봐야 한다면, 팀을 만들 필요 없이 프롬프트 한 번으로 충분합니다:

복사해서 쓰세요
이 아이디어로 클릭 가능한 HTML 프로토타입 화면 2개(홈, 상세)만 빠르게 만들어줘. 파일로 저장해줘: {아이디어 붙여넣기}

판단 기준은 하나입니다 — 같은 형식의 프로토타입을 프로젝트마다 반복해서 만들 것인가? 반복된다면(대부분의 UX 팀이 그렇습니다) 검수자까지 갖춘 팀을 구성하는 값어치가 있습니다. 1회성이면 위 한 줄이 낫습니다.

한 걸음 더

  • 팀원 추가: "카피라이터" 에이전트를 넣어 화면 속 문구(버튼 이름, 안내 문장)의 톤을 다듬게 하거나, "모바일/데스크톱 반응형 검수자"를 추가할 수 있습니다. 하네스 회고로 요청하면 됩니다.
  • 심화 — 팀 구조 직접 수정: 검수→수정 루프 횟수를 늘리거나, 검수자를 "사용성 검수자"와 "접근성 검수자" 둘로 나눠 Fan-out/Fan-in(여러 관점이 병렬로 검토한 뒤 결과를 합치는 패턴)으로 바꿀 수 있습니다.
  • 이웃 하네스: 처음부터 만들기 부담스러우면 revfactory/harness-100(10개 도메인 100개 팀 하네스)에서 가까운 프로토타입 팀을 설치해 수정하는 것이 빠릅니다.

참고: 하네스 도입 효과에 대한 A/B 연구(revfactory/claude-code-harness, n=15)에서 품질 점수 49.5 → 79.3(+60%), 결과 편차 −32%로 보고되었습니다(저자 측정, 소표본). 프로토타입처럼 검수 관점이 여럿 필요한 작업일수록 팀 구성의 개선 폭이 큽니다.
