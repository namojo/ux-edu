따라 하기경쟁 서비스 여럿을 병렬 조사해 비교표로 만들 때
항목 내용
영역 경쟁사 UX 벤치마킹
난이도 중급
소요 시간 구축 약 20분 + 실행 회당 약 15분 (화면 캡처·관찰 메모는 사람 몫으로 별도)
준비물 경쟁 서비스별 온보딩 화면 캡처, 각 서비스를 화면마다 한 줄씩 풀어쓴 관찰 메모 텍스트 파일, revfactory/harness 설치 (아래 0단계)
팀 패턴 Fan-out/Fan-in — 서비스마다 조사원을 한 명씩 붙여 동시에 정리(Fan-out)한 뒤, 한 명이 그 결과를 하나의 비교표로 엮는(Fan-in) 방식

이런 상황에서 쓰세요

"우리 가입 절차가 경쟁사보다 긴가요?"라는 질문이 회의에서 나올 때마다, 경쟁 앱 서너 개를 직접 깔아 가입해 보고 스크린샷을 찍은 뒤 파워포인트에 나란히 붙여 표를 만들곤 합니다. 화면은 다 모았는데, 막상 서비스별로 하나씩 붙잡고 "몇 단계인지, 어디서 이탈이 날 것 같은지, 우리가 배울 점은 뭔지"를 순서대로 정리하다 보면 반나절이 훌쩍 갑니다. 게다가 A를 자세히 보고 나면 지쳐서 C는 대충 보게 되고, 결국 세 서비스를 같은 기준·같은 깊이로 비교했는지 자신이 없습니다.

이 작업의 핵심은 "서비스가 여러 개"라는 점입니다. 서비스마다 조사원을 한 명씩 붙여 동시에 정리하게 하면, 사람이 하나씩 순서대로 볼 때 생기는 "뒤로 갈수록 대충 보는" 편향이 사라집니다. 화면을 모으고 관찰 메모를 남기는 것은 사람이, 서비스별 정리를 병렬로 돌리고 하나의 비교표로 엮는 것은 팀이 맡습니다. 이렇게 "같은 항목으로, 주기적으로, 여러 대상을" 비교하는 일이 반복된다면 프롬프트를 매번 붙여넣는 대신 하네스(에이전트 팀)로 한 번 만들어 두는 편이 낫습니다.

하네스(harness): "무엇을 하는 팀인지" 말로 설명하면, 역할이 나뉜 여러 AI(에이전트)와 그들의 작업 방법을 자동으로 만들어 주는 도구입니다. 코드를 쓰는 게 아니라 팀을 말로 설계한다고 생각하면 됩니다.

팀 미리보기

하네스가 만들어 줄 팀은 이렇습니다. 이 사례의 묘미는 조사원이 여러 명이고, 이들이 서비스별로 동시에 일한다는 점입니다:

팀원 역할
서비스 조사원 (서비스 수만큼, 병렬) 각자 서비스 1개의 관찰 메모(화면 캡처는 참고용 보조)를 맡아, 총 단계 수·필수 정보·소셜 로그인 등 정해진 항목으로 정리. 서로 기다리지 않고 동시에 작업
비교 종합원 조사원들이 각자 정리한 결과를 같은 기준으로 나란히 놓아 하나의 비교표로 엮고, 서비스별 강점·약점과 "우리가 참고할 점"을 덧붙임 (Fan-in)
사실 검증원 완성된 표의 사실 칸(단계 수, 필수 정보 등)이 원본 메모와 일치하는지 한 줄씩 대조하고, 빈칸에 추측이 들어갔으면 "메모 부족"으로 되돌림

왜 병렬(Fan-out)이 여기서 특히 유용한가: 사람은 A→B→C를 순서대로 보지만, 조사원 3명은 A·B·C를 동시에 봅니다. 세 서비스가 서로 완전히 독립적이라(A를 봐야 B를 볼 수 있는 게 아님) 순서가 필요 없고, 그래서 병렬의 이득이 가장 직관적으로 드러나는 작업입니다. 경쟁사가 3개든 6개든, 조사원을 그 수만큼 붙이면 됩니다.

따라 하기

0단계: 하네스 설치 확인 (처음 한 번만)

이 사례는 revfactory/harness가 설치되어 있어야 합니다. 설치는 전체 사례집을 통틀어 처음 한 번만 하면 됩니다 — 아직이라면 하네스 설치 안내를 따라 하세요 (약 2분).

  • 설치 확인: Claude Code 대화창에 /plugin을 입력해 목록에 harness가 보이면 준비 완료. 이미 설치했다면 바로 1단계로 넘어갑니다.

1단계: 준비

핵심은 팀에게 넘기기 전에, 각 화면을 사람이 직접 보고 말로 풀어 적는 것입니다. AI는 여러분의 메모를 정해진 항목으로 정렬하는 데는 뛰어나지만, 화면을 여러분만큼 정확히 "보지는" 못합니다. 그래서 관찰은 사람이 합니다.

  1. 바탕화면이나 문서 폴더에 작업용 폴더를 하나 만듭니다. 예: onboarding-bench-2026
  2. 경쟁 서비스 3종의 온보딩(첫 실행 ~ 가입 완료)을 직접 진행하며 화면을 순서대로 캡처합니다. 파일 이름을 순서대로 붙이면 나중에 편합니다. 예: A_01_시작.png, A_02_이메일입력.png …
  3. 같은 폴더 안에 서비스마다 메모 파일을 따로 만듭니다 — notes_A.txt, notes_B.txt, notes_C.txt. (그냥 메모장/텍스트편집기로 만든 파일입니다.) 파일을 나눠 두면 조사원 한 명이 파일 하나씩 맡아 병렬로 일하기 좋습니다. 각 파일에 화면마다 관찰한 것을 한 줄씩 적습니다:

[서비스 A] 1. 시작 화면 — "3초면 시작" 문구 + 큰 버튼 하나. 회원가입/로그인 선택 없음. 2. 이메일 입력 — 이메일만 요구. 비밀번호는 다음 단계로 분리. 3. 소셜 로그인 — 카카오/애플/구글 3개. 이메일보다 위에 배치. 4. 관심사 선택 — 6개 카드 중 3개 이상 선택 강제. 스킵 버튼 없음. 5. 완료 — 바로 홈. 튜토리얼 오버레이 4장 순차 노출.

  • 세 파일 모두 위와 같은 형식으로, 화면마다 한 줄씩 적으세요. 한 서비스만 자세히 적고 나머지를 대충 적으면 비교표가 한쪽으로 치우칩니다. (병렬 조사원을 붙여도, 재료인 메모가 불균형하면 결과도 불균형합니다.)
  • 화면 개수가 서비스마다 달라도 괜찮습니다. 그대로 적으면 "A는 5단계, B는 7단계"처럼 비교됩니다.
  • "스킵 버튼 없음", "필수 입력이 몇 개" 같은 판단이 필요한 관찰을 넣을수록 표가 풍부해집니다.
  1. 이 폴더 안에서 Claude Code를 켭니다. Claude Code는 켜진 폴더 안의 파일만 읽으므로, 반드시 onboarding-bench-2026 폴더 안에서 켜야 메모와 이미지를 읽습니다. - macOS: Spotlight(⌘+Space)에 terminal을 입력해 터미널(검은 명령어 입력 창)을 엽니다 → 창에 cd를 입력하고 한 칸 띄운 뒤, 만든 폴더를 터미널 창 안으로 드래그하면 경로가 자동 입력됩니다(cd는 "지정한 폴더로 이동" 명령입니다) → Enter → claude 입력 후 Enter를 누르면 Claude Code가 켜집니다. (Finder 우클릭 → 서비스 → '폴더에서 새로운 터미널 열기' 메뉴가 보인다면 그걸 써도 됩니다 — 단, 이 메뉴는 기본값으로 꺼져 있는 Mac이 많습니다.) - Windows: 파일 탐색기로 폴더를 연 뒤 주소창을 클릭해 cmd 입력 후 Enter. - 터미널이 그 폴더에서 열렸으면 claude 를 입력합니다.

2단계: 팀 구성 (바이브코딩)

바이브코딩(vibe coding): 코드를 직접 쓰지 않고, 만들고 싶은 팀을 말로 설명해 AI가 팀을 짜게 하는 방식.

아래를 복사해 붙여넣고, {중괄호} 부분만 바꾸세요. 서비스가 3개보다 많으면 개수만 늘려 적으면 됩니다.

복사해서 쓰세요
하네스 구성해줘: 경쟁사 온보딩 플로우를 벤치마킹하는 팀이 필요해.

입력은 서비스별 관찰 메모 파일(notes_A.txt, notes_B.txt, notes_C.txt — 각 서비스의
온보딩을 화면마다 한 줄씩 적은 것)과, 선택적으로 A_·B_·C_로 시작하는 화면 캡처야.
화면 캡처는 참고용 보조일 뿐, 판단·기재의 근거는 메모 파일이야.
서비스는 {A=우리 유사 경쟁사}, {B=시장 1위}, {C=신생 스타트업} 3종이야.

팀 구성은 이렇게 해줘:
1. 서비스마다 조사원을 한 명씩 붙여서, 각자 자기 서비스 메모 파일 하나만 맡아
   동시에(병렬로) 아래 정해진 항목으로 정리하게 해:
   총 단계 수 / 가입 필수 정보(이메일·전화·이름 등) / 소셜 로그인 제공 여부와 종류 /
   건너뛰기(스킵) 가능한 단계 여부 / 첫 가치 경험까지 걸리는 체감 단계 / 완료 후 첫 화면.
2. 비교 종합원이 조사원들의 결과를 같은 기준으로 나란히 놓아 하나의 비교표로 엮고,
   표 아래에 서비스별 "강점"·"약점"을 각 2~3개, 마지막에 "우리가 참고할 점" 3가지를
   제안으로(제안이라고 표시해서) 붙이게 해.
3. 사실 검증원이 표의 사실 칸이 원본 메모와 일치하는지 대조하고,
   메모로 판단 안 되는 칸은 "메모 부족"으로 비워두게 해.

절대 규칙: 화면 캡처는 참고용 보조일 뿐, 판단·기재의 근거는 메모 파일뿐이야. 메모에 없는 것은 캡처에 보여도 지어내지 마.
결과는 마크다운 비교표 파일(bench.md)로 저장해줘.

마크다운(markdown): 표·제목을 |나 # 같은 기호로 표현하는 가벼운 텍스트 형식입니다. 그대로 회의 자료에 붙여넣거나 문서 도구로 옮기기 좋습니다.

잠시 후 .claude/agents/ 폴더에 팀원 파일들이, .claude/skills/에 팀의 작업 방법이 생깁니다. 하네스가 마지막에 "이런 팀을 만들었습니다" 요약을 보여 주는데, 거기에 위 팀 미리보기 표와 같은 종류의 조사원·종합원·검증원이 있으면 성공입니다. (조사원이 "서비스 수만큼" 병렬로 잡혔는지 확인하세요.)

3단계: 팀 실행

새 대화창에 아래처럼 입력하면 팀이 움직입니다 (정확한 트리거 문구는 2단계 끝에 하네스가 알려 줍니다):

복사해서 쓰세요
온보딩 벤치마킹 실행해줘

조사원 3명이 각자 파일을 맡아 동시에 정리하고, 종합원이 하나로 엮은 뒤, 검증원이 대조합니다. 이런 식의 결과가 나옵니다(내용은 예시입니다):

비교 항목 서비스 A 서비스 B 서비스 C
총 단계 수 5단계 7단계 3단계
필수 정보 이메일만 이메일+전화+이름 없음(둘러보기 먼저)
소셜 로그인 카카오/애플/구글 구글만 카카오/애플
스킵 가능 단계 없음(관심사 강제) 프로필 사진만 스킵 대부분 스킵 가능
첫 가치 경험까지 가입 후(5단계) 가입 후(7단계) 1단계(가입 전 체험)
완료 후 첫 화면 홈+튜토리얼 4장 홈 직행 둘러보기 화면

관찰된 강점 / 약점 (일부) - 서비스 C 강점: 가입 없이 먼저 써보게 해 진입 장벽이 가장 낮음. 필수 입력 0개. - 서비스 B 약점: 전화번호 인증까지 7단계 — 메모상 가장 길고 이탈 위험 구간으로 보임. - 서비스 A 약점: 관심사 3개 선택 강제(스킵 없음)로 흐름이 끊길 소지.

우리가 참고할 점 (제안) 1. C처럼 "가입 전 둘러보기"를 넣어 첫 가치 경험을 가입 앞으로 당기는 안 검토 2. B의 전화번호 필수 요구는 반면교사 — 우리 필수 정보를 최소화할 여지 점검 3. A의 튜토리얼 4장은 완료 후에도 이탈을 부를 수 있어, 스킵 제공 여부 확인

검증원 메모: "첫 가치 경험까지 - 서비스 B" 칸은 메모에 완료 후 동작 기록이 없어 "메모 부족" 처리했다가, 7단계 완료 화면 메모를 근거로 채움. 확인 요망.

4단계: 팀 다듬기 (진화)

결과가 아쉬운 부분은 팀에게 말로 피드백합니다. 다음 실행부터 반영됩니다:

  • 하네스 회고: 비교 항목에 "온보딩 중 광고·프로모션 노출 여부"를 하나 추가해줘. 모든 조사원이 그 항목도 채우도록.
  • 하네스 회고: 종합원이 만든 표 맨 위에 "3줄 요약"을 붙여줘 — 경영진 보고용으로. 검증원은 그 요약이 표와 어긋나지 않는지도 확인해줘.

구축은 1회, 실행은 매번 — 다음 분기에는 새 스크린샷과 새 메모 파일만 폴더에 넣고 온보딩 벤치마킹 실행해줘만 다시 입력하면, 같은 기준의 비교표가 다시 나옵니다.

꼭 사람이 확인하세요

  • 표의 "사실" 칸이 메모와 일치하는지 대조하세요. 검증원을 팀에 넣었지만, 검증원도 AI입니다. 특히 세 서비스를 나란히 맞추는 과정에서 빈칸을 그럴듯하게 메우려는 경향(환각)이 남을 수 있으니, "메모 부족"으로 비워야 할 칸에 추측이 들어갔는지 notes_*.txt와 한 줄씩 맞춰 보세요. 위 예시의 "검증원 메모"처럼 팀이 스스로 "확인 요망"을 남긴 칸은 특히 사람이 봐야 합니다.
  • "첫 가치 경험까지", "이탈 위험" 같은 판단 칸은 AI의 해석일 뿐입니다. 여러분의 관찰 메모를 재료로 추론한 것이라, 실제 사용자 데이터(이탈률)가 아닙니다. 근거로 삼되 결론으로 확정하지 마세요.
  • 관찰 자체의 편향을 경계하세요. 병렬 조사원은 여러분이 메모에 적은 것까지만 정확합니다. 세 서비스를 다른 컨디션(다른 기기, 다른 날, 서둘러 본 것)에서 봤다면 비교가 불공정해집니다. 같은 조건·같은 깊이로 관찰한 메모를 넣으세요.
  • "참고할 점" 제안은 아이디어일 뿐입니다. 경쟁사가 그렇게 한 데는 우리가 모르는 사정(규제, 타깃 차이)이 있을 수 있습니다. 그대로 우리 설계로 복사하지 말고 우리 맥락에 맞는지 판단을 거치세요.
  • 최신성을 확인하세요. 경쟁사 온보딩은 수시로 바뀝니다. 캡처한 날짜를 메모와 표에 남겨 "언제 기준 비교인지"를 항상 함께 공유하세요.

하네스가 과한 경우

경쟁사 2~3개를 딱 한 번만 비교하는 일회성 작업이라면, 팀을 만들 필요 없이 Claude Code에 프롬프트 한 번으로 충분합니다:

복사해서 쓰세요
notes_A.txt, notes_B.txt, notes_C.txt를 읽고, 세 서비스 온보딩을 같은 기준(총 단계 수·필수
정보·소셜 로그인·스킵 여부·첫 가치 경험·완료 후 첫 화면)으로 비교하는 표를 만들어줘.
메모에 없는 건 지어내지 말고, 판단 안 되는 칸은 "메모 부족"으로 비워둬.

판단 기준은 "같은 형식의 비교표가 반복적으로 필요한가?" 입니다. 분기마다, 혹은 온보딩뿐 아니라 결제·해지 플로우까지, 혹은 경쟁사가 5개 이상으로 늘어난다면 — 그때가 하네스로 승격할 시점입니다. 조사원이 여러 명이고 매번 같은 항목으로 돌린다는 점에서, 반복이 시작되는 순간 팀의 이득(병렬 처리 + 고정된 기준 + 자동 검증)이 프롬프트를 매번 다듬는 수고를 넘어섭니다.

한 걸음 더

이 팀은 이렇게 키울 수 있습니다:

  • 추이 담당(에이전트 추가): 지난 분기 bench.md와 이번 표를 비교해 "경쟁사가 이번에 바꾼 부분만" 하이라이트하는 변화 리포트를 만들게 합니다. 벤치마킹을 정기적으로 돌릴수록 이 "무엇이 달라졌나"가 가장 값진 산출물이 됩니다.
  • 플로우 확장: 조사원에게 온보딩뿐 아니라 결제·해지 플로우 메모도 맡기면, 하나의 팀이 여러 여정을 같은 방식으로 비교합니다.
  • 가까운 하네스에서 출발: 처음부터 만들지 않고, revfactory/harness-100(10개 도메인 100개 팀 하네스)에서 비슷한 팀을 설치해 항목만 우리 것으로 바꾸는 방법도 있습니다.

하네스 도입 효과 참고: 저자 측정 소표본 A/B 연구(n=15)에서 하네스 사용 시 결과 품질 49.5 → 79.3(+60%), 결과 분산 −32%로 나타났고, 작업이 복잡할수록 개선 폭이 컸습니다. (근거 · 저자 측정·소표본이라는 단서와 함께 읽으세요.)

외부 동향 확인(2026-07 웹 조사): 2026년 SaaS/UX 팀은 경쟁사 온보딩 벤치마킹에서 수작업 스크린샷·스프레드시트를 AI 기반 분석으로 대체해 분석 시간을 "몇 주에서 몇 시간으로" 줄이고 있으며, 여러 서비스에 동일 과제를 부여해 나란히 비교하는 병렬(parallel) 방식과 "AI가 묶은 결과는 사람이 반드시 검증"하는 원칙이 공통적으로 확인됩니다. 참고: How US SaaS Teams Use AI for UX Competitor Analysis (2026), How to Run a UX Benchmark Study 2026 (ParallelHQ), UX Competitor Analysis Guide 2026 (UXCam).
