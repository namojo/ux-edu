문서화 팀을 만들어 수십 개 컴포넌트 문서를 같은 형식으로 찍어내기

따라 하기수십 개 컴포넌트에 같은 문서 형식을 적용할 때
항목 내용
영역 디자인 시스템 문서화
난이도 중급
소요 시간 구축 약 30분 + 실행 회당 약 10~15분(컴포넌트 20개 기준)
준비물 컴포넌트 목록과 속성 정보(간단한 표나 메모면 충분), revfactory/harness 설치(아래 0단계)
팀 패턴 Fan-out/Fan-in(컴포넌트별로 초안을 병렬 생성한 뒤 하나의 형식으로 통합) + Producer-Reviewer(초안 생성 담당과 형식·용어 검수 담당을 분리)

이런 상황에서 쓰세요

디자인 시스템에 버튼, 인풋, 모달, 토스트, 드롭다운… 컴포넌트가 30개쯤 되는데 문서는 절반만 채워져 있고, 그마저도 사람마다 형식이 제각각입니다. 누구는 "사용법"이라 쓰고 누구는 "How to use"라 씁니다. 새 컴포넌트가 추가될 때마다, 또는 문서 형식을 한번 바꾸기로 결정할 때마다 수십 개를 똑같은 손질로 다시 만져야 합니다. 같은 형식을 수십 번 반복 적용하는 일 — 이게 바로 문서화 팀 하네스가 빛나는 지점입니다. 한 개를 잘 쓰는 게 아니라, 스무 개를 똑같이 찍어내는 게 문제이기 때문입니다.

팀 미리보기

하네스가 만들어 줄 팀은 이렇습니다:

팀원 역할
doc-drafter (초안 작성자) 컴포넌트 하나마다 정해진 문서 틀(개요·사용 시점·속성표·주의사항)에 맞춰 초안을 씁니다. 컴포넌트가 20개면 20개를 병렬로 나눠 씁니다
format-unifier (형식 통일자) 병렬로 나온 초안들의 섹션 제목·표 열 순서·마크다운 문법을 하나의 형식으로 맞춥니다. "사용법"/"How to use"처럼 갈라진 표현을 정합니다
term-reviewer (용어 검수자) 팀에서 정한 용어집(예: "버튼"은 "버튼", "Primary"는 "주요 동작")과 대조해 표기 흔들림을 잡아냅니다. 검증 담당

Fan-out/Fan-in은 "여러 개를 동시에 만든 뒤 하나로 합친다", Producer-Reviewer는 "만드는 사람과 검사하는 사람을 나눈다"는 뜻입니다. 문서를 대량으로, 그러나 일관되게 만들어야 하므로 두 패턴을 함께 씁니다.

따라 하기

0단계: 하네스 설치 확인 (처음 한 번만)

이 사례는 revfactory/harness가 설치되어 있어야 합니다. 설치는 전체 사례집을 통틀어 처음 한 번만 하면 됩니다 — 아직이라면 하네스 설치 안내를 따라 하세요 (약 2분).

  • 설치 확인: Claude Code 대화창에 /plugin을 입력해 목록에 harness가 보이면 준비 완료. 이미 설치했다면 바로 1단계로 넘어갑니다.

1단계: 준비

먼저 이 작업을 담을 폴더를 하나 정합니다. 예를 들어 바탕화면에 design-docs라는 폴더를 만들고, 앞으로 만들 input 폴더도 결과 파일도 모두 이 폴더 안에 둡니다. Claude Code는 반드시 이 폴더에서 열어야 뒤에 나오는 프롬프트가 input/components.md 같은 파일을 제대로 찾습니다. (폴더에서 여는 방법: 터미널을 열어 cd로 그 폴더로 이동한 뒤 Claude Code를 실행하거나, 파일 탐색기에서 폴더를 오른쪽 클릭해 "터미널에서 열기"를 쓴 뒤 실행합니다. 바탕화면 등 엉뚱한 위치에 input 폴더를 만들면 팀이 파일을 못 찾습니다.)

그다음 문서로 만들 컴포넌트 정보를 한 파일에 모읍니다. 완벽할 필요 없습니다 — 컴포넌트 이름과 속성 정도면 됩니다.

  1. 위에서 정한 폴더(예: design-docs) 안에 input이라는 폴더를 하나 만듭니다.
  2. 그 안에 components.md라는 파일(마크다운 = 서식이 있는 텍스트 파일. 메모장으로도 열립니다)을 만들고, 이런 식으로 적습니다:
복사해서 쓰세요
## Button
- 속성: variant(primary/secondary/ghost), size(sm/md/lg), disabled(true/false)
- 용도: 사용자가 동작을 실행할 때

## Input
- 속성: type(text/email/password), placeholder, error(문자열)
- 용도: 사용자에게 값을 입력받을 때

## Modal
- 속성: open(true/false), title, onClose
- 용도: 중요한 확인/입력을 화면 위에 띄울 때
  1. 팀이 지켜야 할 용어집이 있다면 input/glossary.md에 함께 넣습니다. 예: Primary → 주요 동작, disabled → 비활성. 없으면 빈 input/glossary.md 파일이라도 만들어 두세요(팀이 스스로 초안을 채워 줍니다) — 파일 자체가 없으면 뒤에서 검수 담당이 대조할 파일을 못 찾아 실행이 막힐 수 있습니다.
  2. Claude Code를 (아직 안 켰다면) 위에서 준비한 폴더에서 켭니다.

2단계: 팀 구성 (바이브코딩)

바이브코딩 = 코드를 직접 쓰지 않고, 원하는 것을 말로 설명하면 AI가 대신 만들어 주는 방식입니다. 여기서는 "이런 팀이 필요해"라고 말로 설계하면 하네스가 팀을 구성해 줍니다.

아래를 복사해 붙여넣고, {중괄호} 부분만 여러분 상황에 맞게 바꾸세요:

복사해서 쓰세요
하네스 구성해줘: 디자인 시스템 컴포넌트 문서를 대량으로 찍어내는 문서화 팀이 필요해.
input/components.md 에 있는 컴포넌트 목록과 속성을 입력하면,
(1) 컴포넌트마다 정해진 문서 틀(개요 → 언제 쓰나 → 속성표 → 주의사항 → 사용 예시)에
맞춰 초안을 병렬로 작성하고,
(2) 초안들의 섹션 제목·표 형식·마크다운 문법을 하나로 통일하고,
(3) input/glossary.md 용어집과 대조해 표기 흔들림을 검수하는 팀으로.
결과는 컴포넌트별 마크다운 파일(docs/{컴포넌트명}.md)로 저장하고,
마지막에 어떤 컴포넌트에서 용어가 흔들렸는지 검수 리포트도 남겨줘.

잠시 후 .claude/agents/ 폴더에 팀원 파일들(doc-drafter.md, format-unifier.md, term-reviewer.md 같은 것)이, .claude/skills/에 팀의 작업 방법과 오케스트레이터(팀 전체를 순서대로 지휘하는 관리자 스킬)가 생깁니다.

하네스는 작업을 마치면 무엇을 만들었는지 요약을 화면에 보여줍니다 — 팀원 목록과 각자의 역할, 실행 트리거 문구(팀을 움직이게 하는 시작 명령)가 거기 적혀 있으니 그 요약만 읽으면 됩니다. 폴더를 직접 뒤질 필요 없습니다.

3단계: 팀 실행

새 대화에서 아래처럼 입력하면 팀이 일을 시작합니다(정확한 트리거 문구는 2단계 요약에 나온 것을 씁니다):

복사해서 쓰세요
컴포넌트 문서화 실행해줘

이런 식의 결과가 나옵니다. 컴포넌트별 파일(docs/Button.md)은 예를 들면:

복사해서 쓰세요
# Button

## 개요
사용자가 동작을 실행하도록 유도하는 기본 인터랙션 요소.

## 언제 쓰나
- 폼 제출, 다이얼로그 확인 등 명확한 동작이 필요할 때
- 단순 화면 이동만 필요하면 Button 대신 Link 사용

## 속성
| 속성 | 값 | 기본값 | 설명 |
|------|-----|--------|------|
| variant | primary / secondary / ghost | primary | 시각적 강조 수준. 주요 동작은 primary |
| size | sm / md / lg | md | 버튼 크기 |
| disabled | true / false | false | 비활성 상태 여부 |

## 주의사항
- 한 화면에 primary 버튼은 하나만 두는 것을 권장
- disabled 상태에도 이유를 툴팁 등으로 안내

그리고 검수 리포트(docs/_review.md)는 이런 식입니다:

복사해서 쓰세요
# 용어 검수 리포트

| 컴포넌트 | 발견 | 위치 | 권장 표기 |
|----------|------|------|-----------|
| Modal | "닫기 버튼" / "close" 혼용 | 주의사항 | 닫기 버튼 |
| Toast | "사라짐" / "dismiss" 혼용 | 개요 | 자동 해제 |
| Input | 섹션 제목 "사용법"(타 문서는 "언제 쓰나") | 제목 | 언제 쓰나 |

컴포넌트가 20개든 40개든, 형식이 통일된 문서 묶음과 "어디가 흔들렸는지"가 한 번에 나옵니다.

4단계: 팀 다듬기 (진화)

결과가 아쉬운 부분은 팀에게 말로 피드백합니다:

  • 하네스 회고: 속성표에 "필수 여부" 열을 하나 추가하는 방향으로 doc-drafter를 개선해줘.
  • 하네스 회고: 검수 리포트가 흔들린 것만 나열하는데, 각 컴포넌트가 검수를 통과했는지 O/X 요약표도 맨 위에 넣어줘.

다음 실행부터 반영됩니다. 구축은 1회, 실행은 매번 — 새 컴포넌트 10개가 추가되면 input/components.md에 이어 적고 실행만 다시 하면, 기존 문서와 똑같은 형식으로 10개가 더 찍혀 나옵니다.

꼭 사람이 확인하세요

  • 속성의 기본값과 동작은 AI가 지어낼 수 있습니다(환각). 여러분이 준 components.md에 기본값을 안 적었다면, 팀이 "그럴듯한" 기본값을 추측해 채웁니다. 속성표의 기본값·필수 여부는 실제 코드나 디자인 소스와 반드시 대조하세요. 이 부분이 이 사례에서 가장 위험한 지점입니다.
  • "주의사항"과 "언제 쓰나"의 디자인 판단은 팀의 관례를 못 담을 수 있습니다. "primary 버튼은 화면당 하나" 같은 규칙이 여러분 조직과 다르면 AI 초안이 오히려 잘못된 가이드를 퍼뜨립니다. 디자인 원칙에 해당하는 문장은 디자이너가 직접 검토하세요.
  • 용어 검수는 "흔들림 후보"까지입니다. term-reviewer가 "혼용 의심"이라 짚어도, 실제로 둘 다 맞는 맥락일 수 있습니다. 최종 표기 결정은 사람이 합니다 — 팀은 찾아주는 역할, 판단은 사람의 역할입니다.

하네스가 과한 경우

컴포넌트가 두세 개뿐이거나, 문서를 딱 한 번만 만들고 끝이라면 팀을 만드는 30분이 아깝습니다. 그럴 땐 그냥 한 번 물어보세요:

복사해서 쓰세요
아래 컴포넌트 정보로 [개요/언제 쓰나/속성표/주의사항] 형식의 마크다운 문서를 만들어줘: {붙여넣기}

판단 기준은 하나입니다 — "같은 형식의 문서가 앞으로도 반복적으로 필요한가?" 컴포넌트가 계속 늘어나거나, 형식을 한번 정하면 전체에 일괄 적용해야 하는 상황이라면 하네스가 이깁니다. 일회성이면 프롬프트 한 줄이 이깁니다.

한 걸음 더

  • 디자인 토큰 검수자 추가: 문서 안 색상·간격 값이 실제 디자인 토큰(색·여백 등을 정의한 표준 값)과 맞는지 대조하는 팀원을 하나 더 붙일 수 있습니다. 하네스 회고: 문서에 나온 색상·간격 값이 tokens.json과 일치하는지 검사하는 token-checker를 팀에 추가해줘.
  • 번역 팀원 추가: 한국어 문서를 영어로도 내보내야 한다면, format-unifier 뒤에 번역 담당을 붙여 이중 언어 문서를 한 번에 뽑을 수 있습니다.
  • 이미 만들어진 하네스에서 출발: 처음부터 설계하기 부담되면 revfactory/harness-100(10개 도메인 100개 팀 하네스)에서 가까운 문서화 팀을 설치해 여러분 형식에 맞게 고치는 것도 방법입니다.

참고: 업계 동향

디자인 시스템 문서를 AI와 자동화로 대량 생산하는 흐름은 이미 자리 잡고 있습니다. Typeform 엔지니어링 팀은 문서화를 규모에 맞춰 AI·자동화로 처리한 사례를 공개했고, Storybook(컴포넌트를 모아 보여주는 대표적 도구)은 스토리·코드에서 문서를 자동 생성하는 autodocs 기능과, AI 에이전트가 최신 컴포넌트 정보에 접근하도록 돕는 MCP(AI가 외부 도구·데이터에 연결되는 표준 방식) 애드온을 제공합니다. 이 사례의 "초안 병렬 생성 → 형식 통일 → 검수" 흐름은 그 실무 흐름을 하네스 팀 구조로 옮긴 것입니다.

출처: Design System Documentation at Scale (Typeform), Storybook Autodocs, Using Storybook with AI

A/B 연구(revfactory/claude-code-harness, n=15, 저자 측정, 소표본): 하네스 사용 시 품질 점수 49.5 → 79.3(+60%), 분산 −32%. 작업 난이도가 높을수록 개선 폭이 컸습니다 — 수십 개를 똑같이 다뤄야 하는 이런 반복 작업이 특히 이득을 봅니다.
