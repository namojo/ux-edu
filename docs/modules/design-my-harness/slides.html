슬라이드 개요 (강사용) — 내 반복 업무를 팀 구조로 직접 설계·진화

완성 슬라이드가 아니라 슬라이드별 제목과 말할 요점입니다. 필요 시 pptx 제작 스킬로 완성 슬라이드를 만드세요.

시간 배정: 도입·시연 30분 (슬라이드 1~7) — 실습 45분 진행 중 브릿지 슬라이드 1장(8) — 공유·정리 15분 (슬라이드 9~11)

1. 타이틀

제목: 내 반복 업무를 팀 구조로 직접 설계·진화 — L3

말할 요점 - 오늘은 사례집 없이 진행하는 첫 모듈이다. "따라 하기"에서 "직접 설계"로 넘어가는 날. - 90분 + 과제(1~2주 뒤 산출물 리뷰)로 구성된다는 것을 먼저 알린다.

2. 여기까지 온 여정

제목: 설치 → 구성 → 진화, 오늘은 혼자 힘으로

말할 요점 - L1(first-contact, first-harness): 설치 + 첫 구성 경험. - L2(voc-team, research-persona-team, mvp-team): 사례가 써 준 구성 프롬프트를 자기 데이터로 3번 재현. - 오늘 L3: 구성 프롬프트를 직접 쓴다. 사례가 대본이 아니라, 지금까지의 경험이 대본이다. - 참가 조건 확인: L2 2개 이상 수료 여부를 손 들어 확인(미수료자는 진행자가 개별 지원).

3. 이 프로젝트 자체가 하네스로 만들어졌다

제목: 지금 보는 이 교육 자료도 팀이 만들었습니다

말할 요점 - 화면에 harness-ux/.claude/agents/ 폴더를 실제로 띄운다. - 팀원: 커리큘럼 설계(curriculum-designer) · 자료 제작(edu-material-writer) · 사례 조사(ux-case-researcher) · MVP 구현(mvp-builder) · 검수(ux-enablement-reviewer). - "역할이 나뉜 AI 팀 + 오케스트레이터"라는 구조를 실물로 확인시킨다.

4. 검증 담당은 왜 손이 묶여 있는가

제목: 만드는 사람과 검사하는 사람은 다르다

말할 요점 - ux-enablement-reviewer.md의 tools: 줄을 보여준다 — Edit·Write가 없다. - 검증 담당이 직접 고칠 수 있으면 "내가 만들고 내가 검사"가 되어 검증의 의미가 사라진다. - 오늘 캔버스에도 검증 담당을 반드시 넣어야 하는 이유가 여기서 나온다는 것을 연결한다.

5. 팀 아키텍처 6패턴 (복습)

제목: 오늘 가장 많이 쓰는 두 가지

말할 요점 - 6패턴 전체를 짧게 나열: Pipeline · Fan-out/Fan-in · Expert Pool · Producer-Reviewer · Supervisor · Hierarchical. - 오늘 실습에서 대부분 쓰게 될 것은 Pipeline(수집→분류→검증→리포트 순서)과 Producer-Reviewer(생성-검증 짝). 둘을 섞어도 된다고 안내. - 지금까지 L2에서 만든 VoC/리서치/MVP 팀도 대부분 이 두 패턴이었음을 상기시킨다.

6. harness-100 — 만들지 않고 설치해 고쳐 쓰기

제목: 모든 걸 직접 설계할 필요는 없다

말할 요점 - revfactory/harness-100: 10개 도메인 100개 팀 하네스. - 판단 기준: 비슷한 팀이 있으면 설치 후 회고로 수정이 빠르다 / 회사 특유의 형식·기준이 강하면 직접 설계가 낫다. - 오늘은 직접 설계 경로로 진행하되, 워크시트에 harness-100 검토란이 있음을 미리 안내.

7. 오늘의 실습 미리보기

제목: 캔버스 → 구성 → 실행 → 회고

말할 요점 - 4단계를 화면에 순서대로 띄운다: ① 역할 분해 캔버스 작성 ② 구성 프롬프트로 옮겨 하네스 구성해줘 ③ 새 세션에서 트리거 문구로 실행 ④ 하네스 회고로 1회 진화. - 검증 담당은 필수, 역할 개수는 3~5개라는 제약을 다시 강조. - 데이터 없이 와도 진행자 배포 표본으로 참여 가능함을 안내(단, 가능하면 자기 데이터 권장).

8. (실습 중 브릿지) 좋은 구성 프롬프트란

제목: 짧은 프롬프트 vs 구체적인 프롬프트

말할 요점 - 캔버스 작성 중 막힌 조가 보이면 이 슬라이드로 잠깐 멈춰서 보여준다. - "무엇을 하는 팀인지 + 입력 + 역할별 산출 + 검증 대상 + 최종 형식" 5요소가 다 들어가야 함을 사례집 프롬프트(voc-mining 2단계)로 다시 예시.

9. 하네스 회고 — 오늘 처음 직접 써 본다

제목: 아쉬운 점 → 회고 문장

말할 요점 - 지금까지 L2 모듈에서는 회고 예시 문장을 그대로 썼다. 오늘은 자기 실행 결과를 보고 직접 아쉬운 점을 찾아 문장을 쓴다. - 회고 문장 틀 반복 노출: "하네스 회고: {아쉬운 점}. {팀원}을 {개선 방향}으로 개선해줘." - 한 번에 완벽해지지 않아도 된다는 것, 여러 번 나눠 회고하는 것이 정상임을 안내.

10. 공유

제목: 옆 사람과 캔버스 비교하기

말할 요점 - 시간이 남는 조부터 캔버스와 트리거 문구를 공유. - "어떤 역할로 나눴는지"보다 "검증 담당이 정확히 뭘 대조하는지"에 집중해서 들어보라고 안내(가장 자주 허술해지는 지점).

11. 과제 & 마무리

제목: 다음 라운드, 그리고 설치 → 구성 → 진화의 완주

말할 요점 - 과제 3가지 확인: 다음 실무 라운드 실행 / 회고 1회 이상 추가 / 결과+회고 문장+막힌 점을 1~2주 뒤 리뷰에 제출. - 프로그램 전체를 완주했음을 짚는다: 설치(first-contact) → 첫 구성(first-harness) → 사례로 반복(L2 3개) → 직접 설계(오늘). - 종료 설문 3문항 안내: ① 이번 주 실무에 쓸 것인가 ② 가장 유용했던 사례는 ③ 막힌 지점은 (③은 하네스 자체의 다음 진화 입력이 된다는 것을 알린다).
