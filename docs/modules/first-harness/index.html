"하네스 구성해줘" — 내 손으로 만든 첫 팀 (실습 가이드)

L1⏱ 90분모듈 2 / 6
항목 내용
레벨 / 시간 L1 / 90분
시간 배분 도입·시연 25분 — 실습 50분 — 공유·정리 15분
선수 조건 first-contact 수료 — Claude Code 실행, 파일 읽히기, revfactory/harness 플러그인 설치 완료
오늘의 한 문장 코드를 쓰지 않고, 말로 팀을 설계하고 그 팀이 대신 일하게 만든다

이 가이드는 강사 없이 화면만 보고도 따라 할 수 있도록 "화면에 무엇이 보이는지" 기준으로 적었습니다. 순서대로 따라오세요.

시작 전 확인 (30초 체크)

아래 3가지가 안 되어 있으면 오늘 실습을 진행할 수 없습니다. first-contact 모듈을 먼저 완료하세요.

  • [ ] 터미널(검은 대화창)에서 claude를 실행하면 대화창이 뜬다
  • [ ] Claude Code에게 파일을 하나 읽혀 요약을 받아 본 적이 있다
  • [ ] /plugin install harness@harness-marketplace로 하네스 플러그인 설치를 완료했다 (확인 방법: Claude Code 대화창에 /plugin을 입력해 설치된 목록에 harness가 있는지 확인. 확실치 않으면 아래 두 줄을 그냥 다시 실행해도 됩니다 — 이미 설치돼 있으면 별문제 없이 넘어갑니다)

💡 설치가 안 되어 있다면? 설치가 안 되어 있다면 first-contact 실습 가이드의 하네스 설치 단계를 따라 하세요 — 전체 교육에서 처음 한 번만 하면 됩니다. 설치 확인: 대화창에 /plugin을 입력해 목록에 harness가 보이면 준비 완료.

STEP 1. 오늘 무엇이 다른가 (5분, 강사 시연 함께 보기)

지금까지는 Claude Code에게 "이거 해줘"를 한 번씩 시켰습니다. 오늘부터는 다릅니다 — "이런 일을 하는 팀을 만들어줘"라고 말하면, 여러 명의 담당(에이전트)으로 나뉜 팀이 자동으로 만들어집니다. 이것이 하네스(harness — 에이전트 팀 아키텍처를 자동으로 만들어 주는 도구)입니다.

강사가 화면으로 보여주는 것: - A/B 비교 근거 데이터: 하네스로 만든 팀이 낸 결과물 품질 점수 49.5 → 79.3 (+60%), 결과의 들쭉날쭉함(분산) −32% (저자 측정, n=15 소표본 — 참고용 수치입니다) - 하네스가 만들어 내는 폴더 구조 미리보기:

복사해서 쓰세요
내 작업 폴더/
├── .claude/
│   ├── agents/          ← 팀원 정의 파일 (예: collector.md, classifier.md, verifier.md, reporter.md)
│   └── skills/          ← 팀의 작업 방법 + 팀을 지휘하는 오케스트레이터

여기서 꼭 기억할 용어 둘: - 팀원(에이전트): .claude/agents/ 안에 파일 하나씩으로 저장되는, 각자 역할을 맡은 AI - 오케스트레이터: 팀원들에게 순서대로 일을 시키는 "팀장 역할"의 스킬. 실행할 때는 오케스트레이터를 부르는 한 문장(트리거 문구)만 입력하면 됩니다

STEP 2. 오늘 쓸 데이터 준비 (2분)

이 폴더의 sample-reviews.txt를 실습 폴더(예: first-harness-실습)에 넣습니다. first-contact에서 쓴 것과 같은 배달앱 리뷰 20건입니다 — 이미 폴더에 있다면 그대로 써도 됩니다.

STEP 3. "하네스 구성해줘" — 팀 만들기 (10분)

Claude Code 대화창에 아래를 그대로 복사해 붙여넣고 실행(Enter)합니다.

복사해서 쓰세요
하네스 구성해줘: 고객 리뷰를 분석하는 팀이 필요해.
리뷰 텍스트 파일을 입력하면,
(1) 리뷰를 모아 정리하고
(2) 불만/칭찬 주제별로 분류하고
(3) 리포트에 넣을 대표 인용문이 원문에 실제로 있는지 검증하고
(4) 주제별 건수와 대표 인용을 정리한 리포트를 만들어주는
팀으로 만들어줘. 최종 결과는 마크다운 파일로 저장해줘.

📎 마크다운이 뭔가요? 제목·표·목록을 기호 몇 개(#, -, | 등)로 표현하는 가벼운 문서 형식입니다. 워드처럼 열리고, 사내 위키나 노션에 그대로 붙여 넣기 좋습니다.

이 문구는 voc-mining.md의 팀 구성 프롬프트를 첫 실습용으로 더 단순화한 것입니다(CS 티켓·설문·분기 비교는 뺐습니다). 오늘의 목표는 "완벽한 팀"이 아니라 "팀을 처음 만들어 보는 경험"입니다.

입력하고 나면 화면에 하네스가 여러 파일을 만드는 과정이 지나갑니다. 잠시 기다리세요.

💡 이렇게 나오면 정상입니다: 생성 대기 시간 팀을 만드는 데는 보통 수 분(2~5분 내외)이 걸립니다. 화면에 파일 이름이 하나씩 지나가거나 잠깐 멈춘 것처럼 보여도 오류가 아닙니다. 커서가 깜빡이며 아무 반응이 없어 보여도 30초~1분 정도는 그냥 기다려 보세요. 이 대기 시간 자체가 "팀 하나가 지금 만들어지고 있다"는 신호입니다.

💡 권한 확인 창이 뜬다면? 파일을 새로 만들거나 폴더 구조를 바꿀 때 "이 작업을 허용하시겠습니까?" 같은 확인 창이 뜰 수 있습니다. first-contact에서 겪은 것과 같은 창입니다 — 허용(Yes/Allow)을 선택하면 계속 진행됩니다.

구성이 끝나면 하네스가 마지막에 "팀 구성 요약"과 "이렇게 실행하세요"라는 문장(트리거 문구)을 알려줍니다. 이 문장을 화면에 그대로 남겨 두거나 메모해 두세요 — STEP 5에서 씁니다.

STEP 4. 만들어진 팀 확인하기 — 검증 담당 찾기 (8분)

이제 진짜로 팀이 만들어졌는지 눈으로 확인할 차례입니다.

  1. Finder(파일 탐색기)나 VS Code 같은 도구로 실습 폴더를 엽니다.
  2. .claude/agents/ 폴더를 엽니다. 팀원 파일이 여러 개 보일 것입니다(예: collector.md, classifier.md, verifier.md, reporter.md — 실제 이름은 세션마다 조금씩 다를 수 있습니다).
  3. 그중 검증·확인·verify와 관련된 이름의 파일을 하나 열어 봅니다. 무엇을 검증하는 역할인지 한두 줄이 적혀 있을 것입니다.

💡 이름만으로 못 찾겠다면 (폴백) verifier, reviewer, qa, validator처럼 이름이 다르게 나올 수도 있고, 아예 별도 파일이 아니라 다른 팀원 역할 설명 안에 검증 업무가 녹아 있을 수도 있습니다. 이럴 땐 순서대로 해보세요. 1. .claude/agents/ 안의 파일을 하나씩 열어, 맨 위 역할 설명에서 "검증", "확인", "대조", "사실 확인" 같은 말이 있는지 찾습니다. 2. 그래도 안 보이면 .claude/skills/ 폴더를 열어 검증 관련 스킬이 있는지 봅니다(팀원이 아니라 스킬 안에 검증 단계가 들어 있는 구조일 수 있습니다). 3. 그래도 못 찾겠으면 강사(TA)를 불러 함께 확인합니다. 오늘 확인해야 하는 것은 "파일 하나를 콕 집는 것"이 아니라 이 팀 안에 검증 역할이 존재한다는 것 자체입니다.

💡 오늘 가장 중요하게 짚을 것: 이 팀에는 결과를 만드는 팀원만 있는 게 아니라, 결과를 의심하고 확인하는 역할(검증 담당)이 따로 있습니다. 이것을 Producer-Reviewer 패턴(생성 담당-검증 담당을 분리하는 팀 구조)이라고 부릅니다. AI는 그럴듯한 인용문을 지어내거나(환각) 실수를 눈치채지 못할 수 있는데, 검증 담당을 팀에 따로 두면 이 위험을 구조적으로 줄일 수 있습니다. 오늘부터 이후 모든 실습에서 "이 팀에 검증 담당이 있는가"를 계속 확인하게 될 것입니다.

💡 팀원 이름이나 개수가 예시와 달라도 정상입니다 아래 STEP 6에서 자세히 다루지만, 하네스는 매번 똑같은 파일을 찍어내지 않습니다. collector가 gatherer로, verifier가 fact-checker로 불릴 수도 있습니다. 이름이 다르다고 잘못된 것이 아닙니다 — "수집 → 분류 → 검증 → 리포트"라는 역할 흐름이 있는지, 검증 역할이 존재하는지를 확인하는 것이 핵심입니다.

💡 오늘의 확인 범위: 오늘은 검증 담당이 팀에 "있다"는 것만 확인합니다. 리포트 속 인용문을 원문과 실제로 한 줄씩 대조하는 검증 실습은 다음 시간(voc-team)에서 배웁니다 — 그전까지는 STEP 5에서 받은 리포트의 인용문을 최종 사실로 단정하지 마세요.

STEP 5. 팀 실행해서 첫 결과물 받기 (12분)

  1. 새 세션을 엽니다 — 가장 간단한 방법은 지금 창에 /clear를 입력하는 것입니다. 터미널에서 claude를 새로 켜는 방법을 쓴다면, 반드시 실습 폴더 안에서 켜야 방금 만든 팀(.claude/agents/)이 인식됩니다. 다른 위치(예: 홈 디렉토리)에서 켜면 팀을 못 찾을 수 있습니다. (팀을 "만드는 것"과 "돌리는 것"을 분리하면 동작이 더 깔끔합니다.)
  2. STEP 3 마지막에 하네스가 알려준 트리거 문구를 입력합니다. 예시 형태는 이렇습니다(실제 문구는 여러분 화면에 나온 것을 그대로 쓰세요):
복사해서 쓰세요
리뷰 분석 실행해줘. 분석할 파일은 sample-reviews.txt야.
  1. 팀원들이 순서대로 일하는 과정이 화면에 지나가고, 마지막에 리포트 파일 경로를 알려줍니다. 그 파일을 열어 확인합니다. 리포트 파일(.md)은 VS Code로 열면 미리보기(우측 위 책 모양 아이콘)로, 또는 파일을 브라우저 창에 끌어다 놓으면 표·제목이 정리된 형태로 볼 수 있습니다. 더블클릭해서 기호(#, | 등)가 그대로 보여도 오류가 아니라 마크다운 원문입니다.
  2. 다시 한번 실행해 봅니다. 같은 트리거 문구를 한 번 더 입력하거나, 새 세션을 열어 재실행해 보세요(이때도 실습 폴더 안에서 열어야 합니다). "구축은 1회, 실행은 반복" — 팀을 다시 만들지 않고도 몇 번이든 돌릴 수 있다는 것을 몸으로 확인하는 단계입니다.

💡 이렇게 나오면 정상입니다: 결과가 세션마다 조금씩 다른 것 같은 트리거 문구로 다시 실행해도, 주제 이름이나 문장 표현이 지난번과 약간 다르게 나올 수 있습니다(예: "배달 지연"이 "배송 지연"으로). AI가 매번 똑같은 계산을 반복하는 프로그램이 아니라 언어로 판단하기 때문에 생기는 자연스러운 편차입니다. 완전히 다른 결론(예: 없던 주제가 갑자기 1위로 뒤바뀜)이 아니라면 정상 범위입니다.

STEP 6. "프롬프트 한 번이냐, 팀이냐" 판단해 보기 (10분)

이번엔 같은 sample-reviews.txt에 팀을 만들지 않고 프롬프트 한 번만 던져 봅니다. 정확한 비교를 위해 /clear로 새 세션을 연 뒤 아래를 입력하세요. 같은 세션에서 하면 방금 만든 팀의 결과가 참고되어 프롬프트 한 번이 실제보다 잘 나올 수 있습니다.

복사해서 쓰세요
이 리뷰 파일을 읽고 불만 주제를 많은 순으로 5개만 뽑아서, 각 주제별 대표 문장 1개씩 알려줘.

STEP 5에서 받은 팀의 결과와 지금 받은 결과를 나란히 비교해 보세요.

  • 프롬프트 한 번: 빠르다. 그 자리에서 바로 나온다. 대신 형식이 매번 다르게 나올 수 있고, 인용문 진위를 확인해 주는 담당이 없다.
  • 팀(하네스): 만드는 데 몇 분이 걸렸다. 대신 형식이 고정되어 있고, 검증 담당이 인용을 확인해 준다.

판단 기준은 세 가지입니다 — 이 세 가지 중 둘 이상에 해당하면 팀(하네스)을 만드는 편이 이득입니다. 1. 반복성: 이번 한 번이 아니라 매주/매달/매분기 되풀이되는 일인가 2. 형식 고정: 매번 같은 틀(표·항목)로 정리해야 하는가 3. 검증 필요: 인용·수치·개인정보처럼 사람이 매번 확인해야 하는 위험이 있는가

자세한 기준과 사례는 voc-mining.md의 "하네스가 과한 경우" 절을 참고하세요 — "이번 한 번만 훑어보면 되는 상황이면 팀을 만들 필요가 없다"고 명확히 설명하고 있습니다.

강사가 이어서 harness-100(revfactory/harness-100, 미리 만들어진 100개 팀 하네스 모음)을 짧게 소개합니다 — 앞으로는 매번 처음부터 만들지 않고, 비슷한 팀을 설치해 고쳐 쓰는 방법도 있습니다. 이 내용은 mvp-team·design-my-harness 모듈에서 다시 다룹니다.

공유·정리 (15분)

옆 사람과 화면을 맞대고 서로의 .claude/agents/ 폴더에서 검증 담당 이름을 하나씩 짚어 소개해 보세요.

오늘의 성공 기준 (아래 4가지를 모두 했다면 완료입니다)

  • [ ] 하네스 구성해줘로 팀을 1개 만들었다
  • [ ] .claude/agents/(또는 .claude/skills/) 안에서 이 팀에 검증 역할이 존재한다는 것을 짚어낼 수 있다
  • [ ] 오케스트레이터 트리거 문구로 팀을 실행해 첫 결과물(리포트 파일)을 화면에 띄웠다
  • [ ] 같은 데이터에 프롬프트 한 번을 던져 보고 팀의 결과와 비교했다
